### السؤال 1 (متوسط)
عند إضافة عقدة إلى نهاية قائمة مترابطة، يجب تمرير مؤشر البداية بالعنوان:
أ) صح
ب) خطأ
**الإجابة الصحيحة: أ**
**التعليل:**
لتعديل قيمة مؤشر (مثل مؤشر بداية القائمة `head`) من داخل تابع بحيث يبقى التعديل ساري المفعول بعد عودة التابع للمستدعي، يجب تمرير المؤشر "بالعنوان" (أي بمؤشر إلى المؤشر، أو بمرجع إليه) لا بالقيمة. فإذا كانت القائمة فارغة عند الإضافة، يجب أن يشير `head` إلى العقدة الجديدة، وهذا التعديل لن ينعكس على المتحول الأصلي في المستدعي إلا إذا مُرِّر بالعنوان.

هذا امتداد مباشر لمبدأ "التمرير بالمرجع/بالمؤشر يسمح بتعديل المتحول الأصلي، بعكس التمرير بالقيمة" الذي شرحته محاضرة المؤشرات الأولى: تمرير المؤشر نفسه بالقيمة يسمح بتعديل ما يشير إليه، لكن لا يسمح بتغيير عنوانه هو نفسه — وهذا بالضبط ما نحتاجه أحياناً عند تحديث `head` نفسه.

*ملاحظة: لم يرد نص صريح بالمحاضرة يغطي القوائم المترابطة بالتفصيل (تُشرح لاحقاً)، لكن الإجابة معتمدة مباشرة على مبدأ "تمرير المؤشر بالعنوان لتعديله هو نفسه" المشروح صراحة في محاضرة المؤشرات الأولى.*

### السؤال 2 (صعب)
ناتج عملية الطباعة في الكود التالي هو:
```cpp
main() {
    int x;
    int *xptr = &x, *yptr = &y;
    x = y;
    if (xptr == yptr)
        cout << "equal";
    else
        cout << "not equal";
}
```
أ) equal
ب) خطأ لا يمكن مقارنة المؤشرات
ج) not equal
د) خطأ لا يمكن أخذ عنوان متحول لا يملك قيمة ابتدائية
**الإجابة الصحيحة: ج**
**التعليل:**
`xptr` يخزّن عنوان المتحول `x`، و`yptr` يخزّن عنوان متحول مختلف تماماً (`y`). عنوانا `x` و`y` هما دوماً خانتان ذاكريتان مختلفتان طالما أنهما متحولان منفصلان — هذا صحيح بصرف النظر التام عن **قيمتيهما**. لذلك حتى بعد تنفيذ `x = y;` (التي تجعل قيمتي المتحولين متساويتين)، يبقى `xptr` و`yptr` يخزّنان عنوانين مختلفين، فتكون المقارنة `xptr == yptr` دوماً خاطئة (`false`) وتُطبع `not equal`.

أ) خطأ ناتج عن خلط شائع بين "تساوي القيم" و"تساوي العناوين" — تعليمة `x = y` تُساوي القيمتين لكنها لا تُغيّر عنوان أي منهما.
ب) خطأ لأن مقارنة المؤشرات بـ `==` عملية صحيحة تماماً في `C++‎`، وتقارن العناوين المخزَّنة فيها مباشرة.

**النقطة الجوهرية هنا** (والتي شُرحت في بداية محاضرة المؤشرات): المؤشر يخزّن **عنواناً** لا قيمة، و`&` تُعطي عنوان متحول موجود. طالما `x` و`y` متحولان منفصلان في الذاكرة، فعنوانا `&x` و`&y` مختلفان دائماً بصرف النظر التام عمّا تحمله من قيم — وهذا بالضبط الفخ الذي يختبره هذا السؤال.

### السؤال 3 (سهل)
لجمع قيمة ptr1 مع ptr2 وتخزين الناتج في ptr1 في البرنامج التالي:
```cpp
void add(int &ptr1, int &ptr2) {
    ptr1 = ptr1 + ptr2;
}
main() {
    int ptr1 = 2, ptr2 = 3;
}
```
أ) `add(ptr1, *ptr2);`
ب) `add(*ptr1, *ptr2);`
ج) `add(ptr1, ptr2);`
د) `add(&ptr1, &ptr2);`
**الإجابة الصحيحة: ج**
**التعليل:**
رغم تسميتهما `ptr1` و`ptr2`، فإن المتحولين في `main` معرَّفان كـ `int` عاديين (`int ptr1 = 2, ptr2 = 3;`) وليسا مؤشرين فعليين. التابع `add` يستقبل وسطاءه **بالمرجع** (`int &ptr1, int &ptr2`)، والاستدعاء الصحيح لتابع يستقبل مراجع هو تمرير المتحولات مباشرة بأسمائها دون أي عامل `&` أو `*` إضافي — المترجم هو من "يأخذ المرجع" ضمنياً عند الاستدعاء.

أ) و ب) خطآن لأنهما يستخدمان `*` (فك إشارة) على متحولات `int` عادية ليست مؤشرات أصلاً — خطأ ترجمة.
د) خطأ لأنه يمرر عناوين (`&ptr1`, `&ptr2`) بينما التابع يتوقع مراجع لقيم `int` مباشرة لا مؤشرات `int*`.

هذا السؤال يختبر تمييزاً دقيقاً بين "التمرير بالمرجع" (`&` في **تعريف** التابع فقط) و"التمرير بالمؤشر" (يتطلب `&`/`*` عند **الاستدعاء**) — وهو تمييز محوري وردت مقارنته صراحة في محاضرة المؤشرات الأولى: كلاهما يتيح تعديل الأصل، لكن بصياغة استدعاء مختلفة تماماً.

### السؤال 4 (متوسط)
ناتج عملية الطباعة في الكود التالي هو:
```cpp
main() {
    int x = 1;
    int *xptr = &x, *yptr = &y;
    if (xptr == yptr) cout << "True";
    else cout << "False";
}
```
أ) True
ب) 1
ج) False
د) خطأ في الترجمة
**الإجابة الصحيحة: ج**
**التعليل:**
`xptr` يخزّن عنوان `x`، و`yptr` يخزّن عنوان متحول آخر مختلف (`y`). عنوانا متحولين منفصلين مختلفان دائماً، بصرف النظر التام عن قيمتيهما. لذلك `xptr == yptr` خاطئة دوماً، وتُطبع `False`.

ب) خطأ لأن المقارنة `if` تطبع نصاً (`True`/`False`) لا قيمة عددية.
د) خطأ لأن مقارنة مؤشرين بـ `==` عملية صحيحة نحوياً في `C++‎`، لا تسبب أي خطأ ترجمة.

هذا تكرار لنفس الفخ المفاهيمي: طالما `x` و`y` متحولان مختلفان، فعنوانا `&x` و`&y` مختلفان دائماً مهما كانت قيمتاهما — المؤشر يخزّن **عنواناً**، والمقارنة بين مؤشرين تقارن العناوين لا القيم.

### السؤال 7 (متوسط)
ما هو خرج (طباعة) البرنامج التالي:
```cpp
void s1(int *a, int b) {
    int temp = *a;
    *a = b;
    b = temp;
}
main() {
    int v1 = 5, v2 = 9;
    s1(&v1, v2);
    cout << "v1=" << v1 << ", v2=" << v2 << endl;
}
```
أ) v1=9 v2=5
ب) v1=5 v2=9
ج) v1=9, v2=9
د) جميع الإجابات خاطئة
**الإجابة الصحيحة: ج**
**التعليل:**
`a` مؤشر يشير فعلياً إلى `v1` (تمرير بالمؤشر)، بينما `b` نسخة محلية من `v2` (تمرير بالقيمة). `*a = b;` تكتب مباشرة في ذاكرة `v1` الأصلية فتصبح `9`. أما `b = temp;` فتُعدّل فقط النسخة المحلية `b` داخل التابع، ولا تصل هذه التعديلات إطلاقاً إلى `v2` الأصلي في `main` لأنه لم يُمرَّر لا بمؤشر ولا بمرجع. لذلك بعد الاستدعاء: `v1=9` (تغيّر فعلياً) و`v2=9` (لم يتغيّر، بقي على قيمته الأصلية).

أ) خطأ لأنه يفترض أن كلا المتحولين تبادلا قيمتيهما (`swap` كامل)، بينما فقط `v1` تأثر فعلياً.
ب) خطأ لأنه يفترض عدم حدوث أي تعديل إطلاقاً، متجاهلاً تأثير `*a = b`.

هذا مثال دقيق على "تمرير جزئي": معامل واحد بالمؤشر (`a`) يسمح بالتعديل الحقيقي، بينما معامل آخر بالقيمة (`b`) يبقى معزولاً تماماً عن المتحول الأصلي — حتى لو بدا الكود وكأنه ينفذ عملية "تبديل" (`swap`) كاملة.

### السؤال 8 (متوسط)
ما هو خرج (طباعة) البرنامج التالي:
```cpp
main() {
    int x = 5, y = 3;
    int *p = &x, *q = &y;
    x = 7; *p = 10;
    cout << "x=" << x << ", y=" << y << "\t";
    *p = *q = 20;
    cout << "x=" << x << ", y=" << y << endl;
}
```
أ) x=3, y=10 x=10, y=20
ب) x=10, y=3 x=10, y=20
ج) x=10, y=3 x=20, y=20
د) x=7, y=3 x=10, y=20
**الإجابة الصحيحة: ج**
**التعليل:**
`p` يشير إلى `x`، `q` يشير إلى `y`. بعد `x=7;` ثم `*p=10;` (تكتب في `x` عبر `p`)، تصبح `x=10` و`y` ما زالت `3` — الطباعة الأولى: `x=10, y=3`. بعدها `*p = *q = 20;` تُقيَّم من اليمين لليسار: أولاً `*q = 20` تجعل `y=20`، ثم يُسند ناتج هذه العملية (القيمة 20) إلى `*p`، فتصبح `x=20` أيضاً. الطباعة الثانية: `x=20, y=20`.

أ) و د) خطآن لأنهما يفترضان قيماً ابتدائية أو وسيطة غير صحيحة لـ `x` قبل الطباعة الأولى.
ب) خطأ لأنه يتجاهل تأثير `*p = *q = 20` على `x` في الطباعة الثانية (يُبقيها 10 بدل تحديثها لـ 20).

الإسناد المتسلسل `a = b = c` في `C++‎` يُنفَّذ دائماً من اليمين لليسار، وهذا يعني أن كلا المؤشرين هنا ينتهي بهما الأمر يُشيران فعلياً لقيمة `20` — حتى لو كانا يشيران لمتحولين مختلفين تماماً (`x` و`y`) في الأصل.

### السؤال 9 (متوسط)
في الكود التالي ناتج عملية الطباعة هو:
```cpp
main() {
    int m = 0, n = 0;
    int *xptr = &m, *yptr = &n;
    if (*xptr != *yptr)
        cout << "No";
    else
        cout << "Yes";
}
```
أ) No
ب) Yes
ج) لا يطبع شيء
د) خطأ لا يمكن المقارنة
**الإجابة الصحيحة: ب**
**التعليل:**
هنا المقارنة تتم على **القيم المُشار إليها** (`*xptr` و`*yptr`) لا على العناوين نفسها — وهذا يختلف جوهرياً عن أسئلة سابقة قارنت `xptr == yptr` مباشرة. بما أن `m` و`n` كلاهما يساوي `0`، فإن `*xptr = 0` و`*yptr = 0` متساويتان فعلياً، فيكون الشرط `*xptr != *yptr` خاطئاً، وتُنفَّذ الجملة `else`، فتُطبع `Yes`.

أ) خطأ ناتج عن الخلط بين مقارنة **عناوين** المؤشرات (دائماً مختلفة لمتحولين منفصلين) ومقارنة **القيم** المُشار إليها عبر `*` (قد تكون متساوية رغم اختلاف العناوين).
د) خطأ لأن مقارنة القيم المفكوكة (`*xptr`, `*yptr`) عملية عادية تماماً وصحيحة نحوياً.

لاحظي الفرق الدقيق عن سؤال مشابه سابق قارن `xptr == yptr` (عناوين، دائماً مختلفة) مقابل هذا السؤال الذي يقارن `*xptr != *yptr` (قيم، قد تتساوى) — نفس المتحولات لكن مستوى مقارنة مختلف تماماً ينتج نتيجة معاكسة.

### السؤال 10 (متوسط)
في الكود التالي ناتج عملية الطباعة هو:
```cpp
main() {
    int x = 5, y = 10, *p, *q;
    p = q = &x;
    *p = *q = y;
    cout << x << "\t" << y;
}
```
أ) 5 5
ب) 5 10
ج) 10 10
د) 10 5
**الإجابة الصحيحة: ج**
**التعليل:**
`p` و`q` يشيران **كلاهما لنفس المتحول** `x` (وليس أحدهما لـ `x` والآخر لـ `y`). التعليمة `*p = *q = y;` تُنفَّذ من اليمين لليسار: أولاً `*q = y` تكتب `10` في `x` (لأن `q` يشير إلى `x`)، ثم `*p = 10` تكتب نفس القيمة في نفس الخانة (`x` أيضاً، لأن `p` يشير لها أيضاً) — عملية زائدة لكن غير ضارة. أما `y` نفسه فلم يُشِر إليه أي مؤشر إطلاقاً، فتبقى قيمته الأصلية `10` كما هي دون أي تغيير. النتيجة: `x=10, y=10`.

أ) خطأ لأنه يفترض عدم حدوث أي تعديل على `x`.
ب) و د) خطآن لأنهما يفترضان اختلافاً بين قيمتي `x` و`y` النهائيتين، بينما كلاهما ينتهي بهما الأمر إلى `10` (لأسباب مختلفة: `x` تغيّرت فعلياً، و`y` كانت أصلاً `10`).

المفتاح هنا هو ملاحظة أن **كلا** المؤشرين `p` و`q` يشيران لنفس المتحول (`x`)، وليس كل واحد منهما لمتحول مختلف كما في أسئلة أخرى مشابهة — تفصيل صغير في التعريف يقلب النتيجة النهائية بالكامل.

المؤشر يدل على عنوان متحول في الذاكرة بالتالي يتعامل مع هذا المتحول ويعدل ويقرأ قيمته بطريقة:

ب) غير مباشرة
**الإجابة الصحيحة: ب**
**التعليل:**
المؤشر لا "يحمل" القيمة نفسها، بل يحمل فقط عنوانها. للوصول للقيمة الفعلية أو تعديلها يجب أولاً "المرور" عبر هذا العنوان بعملية فك الإشارة (`dereferencing`, الرمز `*`) — وهذه هي بالضبط معنى "التعامل غير المباشر": خطوة وسيطة إلزامية (المرور بالعنوان) قبل الوصول للقيمة الفعلية، بعكس المتحول العادي الذي يحمل قيمته مباشرة.

هذا هو جوهر التعريف الافتتاحي لمحاضرة المؤشرات الأولى: المؤشر "لا يخزن قيمة تقليدية... يستخدم لإدارة الذاكرة"، والوصول لما يشير إليه يتطلب دائماً خطوة `dereferencing` وسيطة.

### السؤال 14 (سهل)
`*` و `&` هما عمليتان متعاكستان في المؤشرات:
أ) صح
ب) خطأ
**الإجابة الصحيحة: أ**
**التعليل:**
`&` تأخذك من **قيمة** موجودة إلى **عنوانها** (`&x` تُعطي عنوان `x`)، بينما `*` تأخذك من **عنوان** إلى **القيمة** المخزَّنة فيه (`*ptr` تُعطي قيمة ما يشير إليه `ptr`). تطبيق إحداهما ثم الأخرى مباشرة يُعيدك لنقطة البداية (`*(&x)` تساوي `x` نفسها)، وهذا بالضبط معنى كونهما "متعاكستين".

هذه إحدى "أبرز النقاط الذهبية" الصريحة في محاضرة المؤشرات الأولى: "`&` تأخذك من القيمة إلى عنوانها، و `*` تأخذك من العنوان إلى القيمة — وهما عمليتان متعاكستان تماماً".

### السؤال 55–60 (مجموعة أسئلة على نص/كود مشترك)

**في السجلات وليكن لديك السجل:**
```cpp
struct student {
    int number;
    char name[30];
    int age;
    float credit;
};
```
**والتصريح عن متحولات سجلية (سجلات) منه:**
```cpp
student s1, s2, s3, s[10];
```
**أجب على الأسئلة الستة التالية (13-18):**

**السؤال 55:** لا يجوز تكرار نفس اسم المتحول (العضو) في نفس السجل:
أ) صح
ب) خطأ
**الإجابة الصحيحة: أ**
**التعليل:**
كل حقل داخل `struct` واحد يجب أن يحمل اسماً فريداً؛ محاولة تعريف حقلين بنفس الاسم داخل نفس السجل تُنتج خطأ ترجمة مباشرة (`redefinition`)، تماماً كما لا يجوز تعريف متحولين بنفس الاسم في نفس النطاق (`scope`) في أي كود عادي.

**السؤال 56:** يمكن أن يكون أحد أعضاء السجل هو سجل آخر مصرح عنه سابقاً:
أ) صح
ب) خطأ
**الإجابة الصحيحة: أ**
**التعليل:**
تضمين سجل داخل سجل آخر أمر مسموح ومفيد تماماً (مثلاً `struct Address {...}; struct Person { Address addr; ...};`)، طالما أن النوع المُضمَّن **مُعرَّف سابقاً بالكامل** (`complete type`) قبل استخدامه كحقل.

القيد الوحيد هو عدم تضمين **نفس** نوع السجل داخل نفسه مباشرة (`Complex xc;` داخل تعريف `Complex` نفسه) — لأن ذلك يتطلب حجماً غير محدد النهاية (حجم لا نهائي نظرياً)، وهذا مختلف تماماً عن تضمين سجل **آخر** مُعرَّف مسبقاً، وهو ما يسأل عنه هذا السؤال تحديداً.

**السؤال 57:** التصريح `student *a, &b;` يعتبر صحيحاً:
أ) صح
ب) خطأ
**الإجابة الصحيحة: ب**
**التعليل:**
هذا السطر يُعرِّف متحولين معاً: `a` مؤشر (`student *a`)، و`b` مرجعاً (`student &b`). المشكلة أن المراجع (`reference`) في `C++‎` يجب أن تُهيَّأ (تُربَط بمتحول موجود) فوراً عند تعريفها — لا يمكن ترك مرجع بلا تهيئة كما يمكن مع مؤشر عادي. بما أن `b` هنا معرَّفة بلا أي تهيئة (`= شيء ما`)، فالسطر يفشل في الترجمة.

هذا الخطأ سببه محاولة معاملة `&` هنا كجزء من نمط "مؤشر" مشابه لـ `*`، بينما هي في الحقيقة تُعرِّف **مرجعاً** لا مؤشراً — وقواعد التهيئة مختلفة تماماً بين الاثنين.

**السؤال 58:** لطباعة عناصر s1 نستعمل التعليمة `cout << s1;`:
أ) صح
ب) خطأ
**الإجابة الصحيحة: ب**
**التعليل:**
المترجم لا يعرّف تلقائياً أي سلوك لعامل `<<` مع أنواع `struct` معرَّفة من طرف المستخدم؛ يجب تحميله زائداً (`operator overloading`) صراحة قبل أن يصبح `cout << s1` قابلاً للترجمة أصلاً — وإلا فهو خطأ ترجمة مباشر.

**السؤال 59:** التعليمة التالية: `if (s1 == s2)` تعتبر صحيحة:
أ) صح
ب) خطأ
**الإجابة الصحيحة: ب**
**التعليل:**
تماماً كعامل `<<`، لا يوفّر المترجم افتراضياً عامل مقارنة (`operator==`) لمقارنة سجلَين `struct` ككتلة واحدة؛ يجب تعريفه صراحة، وإلا فمحاولة `s1 == s2` مباشرة تُعتبر خطأ ترجمة.

**السؤال 60:** في مصفوفة السجلات s[10] والمصرح عنها أي مما يلي غير صحيح؟
أ) يكون الإسناد والتعامل من خلال المعامل نقطة للأعضاء `s[10]`
ب) `s[10]` تحوي عشر سجلات من النمط student
ج) يمكن إسناد قيمة عضو من s1 إلى العضو المقابل له من `s[1]`
د) حجم `s[10]` هو 42 بايت
**الإجابة الصحيحة: د**
**التعليل:**
حجم سجل `student` **الواحد** هو `4 (int) + 30 (char[30]) + 4 (int) + 4 (float) = 42` بايتاً تقريباً. لكن `s[10]` ليست سجلاً واحداً، بل **مصفوفة من 10 سجلات** كاملة، فحجمها الفعلي هو `10 × 42 = 420` بايتاً تقريباً، لا 42 بايتاً. هذا الخيار يخلط بين حجم **عنصر واحد** وحجم **المصفوفة بأكملها**، فهو العبارة غير الصحيحة المطلوبة في السؤال.

أ) صحيحة: الوصول لأعضاء أي عنصر `s[i]` يتم عبر `.` تماماً كأي متحول سجل عادي (`s[i].number`).
ب) صحيحة تماماً بحكم تعريف المصفوفة `student s[10];`.
ج) صحيحة: الإسناد بين حقول مقابلة من سجلات مختلفة (حتى بين متحول منفرد وعنصر مصفوفة) عملية عادية ومسموحة (`s[1].number = s1.number;`).

هذا خطأ حسابي كلاسيكي يجب الانتباه له دائماً عند التعامل مع مصفوفات السجلات: `sizeof(النوع)` يصف حجم **عنصر واحد**، بينما حجم المصفوفة الكامل يتطلب ضربه بعدد العناصر.

### السؤال 74 (متوسط)
الحلقة `while (cin >> var)` تنتهي عند الضغط (إدخال) على:
أ) `^Z`
ب) `^C`
ج) `^S`
د) `^E`
**الإجابة الصحيحة: أ**
**التعليل:**
عندما تُستخدم `cin >> var` كشرط لحلقة `while`، فإنها تعتمد على القيمة المنطقية لحالة الدفق (`stream state`) بعد محاولة القراءة. الاختصار `^Z` (`Ctrl+Z`) هو إشارة "نهاية الإدخال" (`End Of Input`) القياسية من لوحة المفاتيح في الأنظمة المبنية على `Windows`، وعند إدخالها يفشل `cin` في قراءة قيمة جديدة، فتتحول حالته إلى `false` وتتوقف الحلقة تلقائياً.

ج) و د) ليستا اختصارات قياسية معروفة لهذا الغرض.

هذا امتداد مباشر لمبدأ `eof()` المشروح في محاضرة الملفات — لكن هنا مطبَّق على الإدخال القياسي (`cin`) بدل ملف: فشل عملية القراءة (سواء بسبب نهاية ملف أو إشارة يدوية من المستخدم) يُترجَم دائماً إلى قيمة منطقية خاطئة توقف أي حلقة شرطها هو عملية القراءة نفسها.

### السؤال 81–91 (مجموعة أسئلة على نص/كود مشترك)

**بفرض لدينا الكود التالي:**
```cpp
struct Person { 
    char name[50];
    char address[255]; 
    long phoneNumber; 
};

class PhoneBook {
private:
    Person** book; 
    int currentIndex;
public:
    void addNewPerson(Person* p);
    Person getPerson(int i);
    int getPeopleCount();
    void deletePerson(int index);
    void writeToFile(ofstream* f);
    void loadFromFile(ifstream* f);
    PhoneBook(); 
    ~PhoneBook();
};
```
يعبر هذا الكود عن دفتر هواتف حيث يعبر العضو الخاص `currentIndex` عن فهرس آخر عنصر تمت إضافته للدفتر (ليس عدد العناصر) والتابعين `writeToFile` و `loadFromFile` يتعاملان مع ملفات ثنائية والمطلوب:

**السؤال 81:** ما هو الكود اللازم لبناء الصف PhoneBook بحيث يحتوي على عدد أعظمي وقدره 50 اسم
أ) `PhoneBook::PhoneBook() { book = new Person[50]; currentIndex = -1; }`
ب) `PhoneBook::PhoneBook() { book = new Person*[50]; currentIndex = 0; }`
ج) `PhoneBook::PhoneBook() { book = new Person*[50]; currentIndex = -1; }`
د) `PhoneBook::PhoneBook() { book = new Person[50]; currentIndex = 0; }`
**الإجابة الصحيحة: ج**
**التعليل:**
الحقل `book` معرَّف من نوع `Person**` أي مؤشر يشير إلى مصفوفة من المؤشرات، وليس مصفوفة من الأغراض مباشرة. لذلك يجب حجزه بـ `new Person*[50]` (مصفوفة من 50 مؤشراً) لا `new Person[50]` (مصفوفة من 50 غرضاً فعلياً). وبما أن `currentIndex` يمثّل فهرس آخر عنصر تمت إضافته وليس عدد العناصر، فعند دفتر فارغ لا يوجد أي عنصر بعد، لذلك تُهيَّأ بـ `-1` لا `0` (لأن `0` تعني وجود عنصر واحد عند الفهرس صفر).

أ) خطأ لأنها تحجز `Person[50]` (أغراضاً مباشرة) بدل مصفوفة مؤشرات، ما يتعارض مع نوع `book`.
ب) خطأ لأنها تبدأ `currentIndex` من `0` رغم أن الدفتر فارغ، ما يجعل `getPeopleCount` يحسب عنصراً وهمياً واحداً.
د) يجمع بين خطأي أ و ب معاً.

هذا السؤال يختبر فهم الفرق الجوهري بين "مصفوفة أغراض" و"مصفوفة مؤشرات لأغراض"، وهو نمط شائع عند بناء بنى بيانات ديناميكية الحجم تحتاج لاحقاً حذف/إضافة عناصر مفردة دون نقل كامل الأغراض.

**السؤال 82:** للحصول على عدد الأسماء الموجود في الدفتر فإن التابع getPeopleCount يجب أن يكتب بالشكل التالي:
```cpp
int PhoneBook::getPeopleCount() {
    return currentIndex + 1;
}
```
أ) صح
ب) خطأ
**الإجابة الصحيحة: أ**
**التعليل:**
بما أن `currentIndex` يمثّل فهرس (index) آخر عنصر تمت إضافته وليس عددهم، فإن عدد العناصر الفعلي يساوي دائماً `currentIndex + 1` (لأن الفهرسة تبدأ من صفر). مثلاً لو أُضيف عنصر واحد فقط، يصبح `currentIndex = 0`، وعدد العناصر الحقيقي هو `1 = 0 + 1`.

هذه العلاقة (`index = count - 1`) نمط متكرر جداً عند التعامل مع مصفوفات ديناميكية الحجم، ويجب دائماً الانتباه لمعنى المتحول المُستخدم لتتبع الحجم: هل هو "آخر فهرس مشغول" أم "عدد العناصر الفعلي"؟ الخلط بينهما مصدر شائع لأخطاء "off-by-one".

**السؤال 83:** عند إضافة اسم جديد للسجل يجب أن يحتوي التابع addNewPerson على الكود التالي:
```cpp
if (currentIndex == 49) return;
```
أ) صح
ب) خطأ
**الإجابة الصحيحة: أ**
**التعليل:**
المصفوفة `book` محجوزة بحجم 50 مؤشراً، فأعلى فهرس صالح فيها هو `49` (فهرسة من 0 إلى 49). إذا كان `currentIndex` يساوي `49` فهذا يعني أن كل المقاعد الخمسين مشغولة بالفعل (`currentIndex+1 = 50`)، وبالتالي يجب إيقاف عملية الإضافة فوراً لتفادي الكتابة خارج حدود المصفوفة (`buffer overflow`).

هذا الفحص هو مثال كلاسيكي على "حارس الحدود" (`boundary guard`) الضروري في أي بنية بيانات ذات سعة ثابتة مبنية فوق مصفوفة — نفس الفكرة التي تظهر لاحقاً عند التعامل مع الملفات الثنائية ذات السعة المحدودة سلفاً.

**السؤال 84:** أي مما يلي هو التحقيق السليم لكود حذف شخص من دفتر الهواتف:
أ) ```cpp
void PhoneBook::deletePerson(int index) {
    delete book[index];
    for(int i = index; i < currentIndex - 1; i++)
        book[i] = book[i+1];
    book[currentIndex - 1] = 0;
}
```
ب) ```cpp
void PhoneBook::deletePerson(int index) {
    for(int i = index; i < currentIndex - 1; i++)
        book[i] = book[i+1];
    book[currentIndex - 1] = 0; 
    currentIndex--;
}
```
ج) ```cpp
void PhoneBook::deletePerson(int index) {
    delete book[index];
    for(int i = index; i < currentIndex - 1; i++)
        book[i] = book[i-1];
    book[currentIndex - 1] = 0; 
    currentIndex--;
}
```
د) ```cpp
void PhoneBook::deletePerson(int index) {
    delete book[index];
    for(int i = index; i < currentIndex - 1; i++)
        book[i] = book[i+1];
    book[currentIndex - 1] = 0; 
    currentIndex--;
}
```
**الإجابة الصحيحة: د**
**التعليل:**
الحذف الصحيح لعنصر من مصفوفة مؤشرات يتطلب أربع خطوات مجتمعة: (1) تحرير ذاكرة الغرض المحذوف فعلياً بـ `delete book[index]` لتفادي تسرب الذاكرة، (2) إزاحة كل العناصر التالية خانة واحدة لليسار (`book[i] = book[i+1]`) لسدّ الفراغ، (3) تصفير آخر خانة أصبحت مكررة، و(4) إنقاص `currentIndex` ليعكس الفهرس الجديد لآخر عنصر. الخيار (د) هو الوحيد الذي يجمع كل هذه الخطوات الأربع بالترتيب والاتجاه الصحيحين.

أ) خطأ لأنها لا تُنقص `currentIndex` بعد الحذف، فيبقى الدفتر "يعتقد" أن العنصر المحذوف ما زال موجوداً.
ب) خطأ لأنها لا تستدعي `delete book[index]` إطلاقاً، ما يسبب تسرب ذاكرة (`memory leak`) للغرض المحذوف.
ج) خطأ لأن اتجاه الإزاحة معكوس (`book[i] = book[i-1]` بدل `book[i+1]`)، ما يعيد نسخ عناصر سابقة للخانة بدل سحب العناصر اللاحقة، فيُخرِّب محتوى المصفوفة بدل ضغطها.

لاحظي أن هذا النمط (تحرير → إزاحة → تصفير → تحديث الفهرس) هو القالب القياسي لحذف عنصر من أي مصفوفة ديناميكية، وأي إخلال بترتيب أو اتجاه إحدى خطواته الأربع يُنتج خطأً منطقياً دقيقاً يصعب اكتشافه بالعين المجردة دون تتبع دقيق.

**السؤال 85:** يتم تحقيق التابع writeToFile باستخدام الكود التالي:
```cpp
void PhoneBook::writeToFile(ofstream* f) {
    f->seekp(0, ios::beg);
    for(int i = 0; i <= currentIndex; i++) {
        f->seekp(i * sizeof(Person), ios::beg);
        // [الفراغ]
    }
    f->close();
}
```
إن الكود الواجب تعبئته في الفراغ في السطر قبل الأخير هو:
أ) `f->write(book[i]);`
ب) `f->write((char*)book[i], sizeof(Person));`
ج) `f->write((string*)book[i], sizeof(Person));`
د) `f->write((int*)book[i], sizeof(Person));`
**الإجابة الصحيحة: ب**
**التعليل:**
تابع `write` في مكتبة `fstream` يتوقع دوماً وسيطين: مؤشراً من نوع `const char*` يشير إلى بداية كتلة البايتات المراد كتابتها، وعدد البايتات المطلوب كتابته. بما أن `book[i]` هو `Person*` (مؤشر لغرض)، يجب تحويله أولاً إلى `char*` عبر قصر صريح `(char*)` قبل تمريره، مع تحديد حجم الكتابة بـ `sizeof(Person)` ليقرأ كامل بنية السجل كبايتات خام.

أ) خطأ لأنها لا تحدد عدد البايتات إطلاقاً (وسيط ناقص)، ولا تجري القصر المطلوب لـ `char*`.
ج) خطأ لأن `write` لا تقبل مؤشر `string*` — هذا يخلط بين صف `std::string` وبين مصفوفة المحارف الخام المطلوبة.
د) خطأ لأن القصر إلى `int*` غير منطقي هنا؛ لا علاقة لـ `Person` بنوع `int`، والقصر الصحيح دوماً إلى `char*` عند الكتابة الثنائية.

هذا النمط — التحويل الإلزامي إلى `char*` مع تمرير `sizeof(النوع)` — هو حجر الأساس لكل عمليات القراءة/الكتابة الثنائية في `C++`، لأن `read`/`write` لا "يفهمان" أنواع البيانات المخصصة، بل يتعاملان معها فقط كتسلسل بايتات خام.

**السؤال 86:** لتحقيق عملية قراءة من الملف الثنائي ضمن التابع loadFromFile يجب تحديد عدد السجلات الموجودة ضمن الملف باستخدام الكود التالي:
أ) `file->seekg(0); long size = file->tellg(); int stored = (int)size / sizeof(Person);`
ب) `file->seekg(0, ios::beg); long size = file->tellg(); int stored = (int)size / sizeof(Person);`
ج) `file->seekg(0, ios::end); long size = file->tellg(); int stored = (int)size / sizeof(Person);`
د) كل ما سبق خاطئ
**الإجابة الصحيحة: ج**
**التعليل:**
لمعرفة حجم الملف الكلي (ومن ثم عدد السجلات) يجب أولاً نقل مؤشر القراءة `get` إلى **نهاية** الملف عبر `ios::end`، فتُصبح قيمة `tellg()` هي عدد البايتات الكلي للملف من بدايته حتى موقعه الحالي (أي حجم الملف بالكامل). بعدها تُقسَّم هذه القيمة على `sizeof(Person)` للحصول على عدد السجلات المخزَّنة.

أ) و ب) خطأ لأنهما ينقلان المؤشر إلى **بداية** الملف (`ios::beg` هو السلوك الافتراضي أصلاً لـ `seekg(0)`)، فتكون قيمة `tellg()` دوماً صفراً، ما يعطي `stored = 0` بغض النظر عن المحتوى الفعلي للملف.

هذا النمط — `seekg(0, ios::end)` ثم `tellg()` ثم القسمة على حجم السجل — هو الطريقة القياسية لحساب عدد السجلات في أي ملف عشوائي بدون معرفة عددها مسبقاً، وقد ظهر بنفس الصياغة في شرح المحاضرة عن الوصول العشوائي.

**السؤال 87:** لقراءة السجلات من الملف علينا تحريك مؤشر القراءة بمقدار:

ج) `personIndex * sizeof(Person)`
د) كل ما سبق خاطئ

**التعليل:**
المعادلة الأساسية للوصول العشوائي هي: موقع السجل رقم `i` = `i × sizeof(السجل)`. بما أن الفهرسة تبدأ من الصفر، فالسجل رقم `personIndex` يبدأ تماماً عند البايت رقم `personIndex * sizeof(Person)` من بداية الملف، دون طرح أو إضافة أي قيمة إضافية.

هذه المعادلة (`i * sizeof(Struct)`) هي جوهر مفهوم "الوصول العشوائي": بدل قراءة كل السجلات بالترتيب حتى نصل للمطلوب، نحسب موقعه مباشرة وننتقل إليه فوراً.

**السؤال 88:** إن الكود التالي هو الكود المناسب للهادم:
```cpp

}
```
أ) صح
ب) خطأ
**الإجابة الصحيحة: ب**
**التعليل:**
بما أن `currentIndex` هو فهرس آخر عنصر (وليس عدد العناصر)، فإن عدد العناصر الفعلي المخزَّن هو `currentIndex + 1`. الحلقة هنا تتوقف عند `i < currentIndex`، أي أنها **تتجاهل آخر عنصر فعلياً** (الموجود عند الفهرس `currentIndex` نفسه) ولا تُحرر ذاكرته، ما يسبب تسرب ذاكرة (`memory leak`) لعنصر واحد على الأقل في كل تشغيل.

**السؤال 89:** لما تم تمرير الملفات باستخدام المؤشرات:
أ) لأن المؤشرات أسهل في التعامل
ب) لأن المؤشرات أسرع من ناحية التنفيذ
ج) لتجنب استخدام الباني الناسخ وبالتالي هدر الذاكرة
د) كل ما سبق خاطئ
**الإجابة الصحيحة: ج**
**التعليل:**
كائنات الملفات مثل `ifstream`/`ofstream` هي كائنات "لا يجوز نسخها" (`non-copyable`) في `C++‎`، لأنها تحمل موارد فريدة (مقبض ملف مفتوح) لا معنى لتكرارها. لو مُرِّرت بالقيمة (`by value`) لحاول المترجم استدعاء باني نسخ (`copy constructor`) للكائن، وهو أمر إما ممنوع (خطأ ترجمة) أو مكلف/خطير إن كان مسموحاً به. لذلك تُمرَّر دوماً بالمؤشر أو بالمرجع لتفادي أي محاولة نسخ لكائن الملف نفسه.

أ) و ب) صحيحتان جزئياً بشكل عام عن المؤشرات، لكنهما ليستا السبب **المحدد** المذكور في المحاضرة لتمرير كائنات الملفات تحديداً؛ السبب الجوهري هنا مرتبط تحديداً بمنع النسخ لا بالسهولة أو السرعة فقط.

هذه الفكرة تمتد من فكرة "تمرير بالمرجع لتفادي النسخ" التي تكررت في محاضرة السجلات (Records)، لكنها هنا أكثر إلزامية: نسخ كائن ملف ليس مجرد إهدار أداء، بل قد يكون غير معرَّف السلوك المصدر أو خطأ ترجمة كامل.

**السؤال 90:** إذا علمت أن الصف fstream يرث كلاً من الصف ifstream والصف ofstream هل يمكن الاستعاضة عنهما بالصف fstream في التوابع writeToFile و loadFromFile:

**التعليل:**

هذا تماماً ما شُرح في محاضرة الملفات العشوائية: `fstream` هو الخيار المعتاد عندما نحتاج القراءة والكتابة لنفس الملف ضمن نفس الجلسة البرمجية، بدل فتح الملف مرتين بصفين مختلفين.

**الإجابة الصحيحة: أ**
**التعليل:**
هذا استدعاء صحيح تماماً للباني ذي الوسطاء `Rectangle(int w, int l)`، حيث يُعرَّف الغرض `r` مباشرة بقيم `width=5` و`length=10` دون الحاجة لأقواس فارغة أو خطوات إضافية.

**السؤال 101:** تستطيع قراءة Access إلى قيمة كل من width و length لأي غرض مشتق من الصف السابق من خلال:
أ) `area()`
ب) مباشرة
ج) الإجابة A & B صحيحتان
د) كل ما سبق خاطئ
**الإجابة الصحيحة: د**
**التعليل:**
الحقلان `width` و`length` معرَّفان `private` — وهذا يمنع الوصول المباشر إليهما ليس فقط من خارج الصف، بل أيضاً من أي صف **وارث** (مشتق) منه، لأن `private` تبقى مخفية حتى عن الأبناء (لتصبح متاحة لهم كان يجب تعريفها `protected` لا `private`). أما `area()` فهي تُعيد **حاصل الضرب** `width * length` كقيمة واحدة مجمَّعة، لا القيمتين المنفصلتين لكل من `width` و`length` بذاتيهما — فلا تُتيح فعلياً "قراءة" أيّ منهما بشكل مستقل.

بما أن لا الوصول المباشر ممكن (بسبب `private`) ولا `area()` تُرجع القيمتين الفعليتين (بل ناتج عملية عليهما)، فلا يوجد خيار سابق يحقق فعلياً المطلوب، والإجابة الصحيحة هي (د).

هذا يطابق تماماً تحذيراً صريحاً من محاضرة الوراثة: "الحقول التي يحتاجها الابن للوصول المباشر يجب أن تكون `protected` وليست `private` في الأب" — وبما أن `Rectangle` لم تستخدم `protected` هنا، فلا وصول مباشر متاح للأبناء إطلاقاً.

**السؤال 102:** يعتبر `Rectangle(int w, int l)`:
أ) Default constructor
ب) Copy constructor
ج) Constructor with parameters
د) كل ما سبق صحيح
**الإجابة الصحيحة: ج**
**التعليل:**
`Rectangle(int w, int l)` يستقبل وسيطين من نوع `int` لتهيئة الغرض بقيم محددة عند الإنشاء — هذا هو تعريف "الباني ذو الوسطاء" (`Constructor with parameters`) بالضبط.

أ) خطأ لأن الباني الافتراضي (`Default Constructor`) لا يستقبل أي وسطاء إطلاقاً — بينما هذا يستقبل اثنين.
ب) خطأ لأن الباني الناسخ (`Copy Constructor`) يستقبل تحديداً غرضاً من **نفس نوع الصف** بالمرجع (`Rectangle& other`)، لا قيمتين عدديتين منفصلتين كما هنا.

### السؤال 110 (سهل)
عند التعريف عن عنصر بيانات data member أو تابع على أنه خاص private في صف لا يمكن الوصول إليه إلا من قبل توابع الصف نفسه و:
أ) التوابع الصديقة للصف
ب) لا يوجد أي نوع آخر من التوابع يمكنه الوصول إليها
ج) الابن
د) يمكن الوصول إليه من خارج الصف
**الإجابة الصحيحة: أ**
**التعليل:**

ب) خطأ لأنه يتجاهل استثناء `friend` تماماً.
ج) خطأ لأن الأبناء **لا** يصلون لحقول `private` للأب؛ الوصول الموروث للأبناء يقتصر على `protected` و`public` فقط، وهذه نقطة تكررت صراحة كخطأ شائع في محاضرة الوراثة.
د) خطأ لأن هذا يصف تماماً `public` لا `private`.

هذه بالضبط أول نقطة في قاموس مصطلحات محاضرة الصفوف (الجزء الثاني): الصداقة (`friend`) "تُمنح صراحة من الصف المالك، وليست تلقائية ولا تبادلية ولا متعدية" — وهي الاستثناء الوحيد المصمَّم عمداً لكسر عزلة `private` بشكل محكوم ودقيق.

### السؤال 112 (سهل)
لكي تسمح لأبناء الصف بالوصول إلى عناصر البيانات الخاصة علينا أن نستخدم:
أ) `Get, set`
ب) `public` محدد
ج) `protected` محدد
د) `private` محدد
**الإجابة الصحيحة: ج**
**التعليل:**
محدد الوصول `protected` مصمَّم خصيصاً لهذه الحالة الوسطى: يجعل الحقل مرئياً ومباشر الوصول لصف نفسه **ولكل أصنافه الوارثة** (الأبناء)، لكنه يبقى مخفياً تماماً عن أي كود خارج شجرة الوراثة.

أ) خطأ لأن `getter`/`setter` توابع عامة (`public`) تتيح الوصول لأي كود خارجي، وليست آلية خاصة بالأبناء تحديداً.
ب) خطأ لأن `public` تفتح الوصول للجميع بلا قيود، وهذا يُلغي فائدة التغليف بالكامل، لا يقتصر فقط على الأبناء.
د) خطأ لأن `private` تمنع الوصول حتى عن الأبناء أنفسهم — وهي بالضبط عكس المطلوب في هذا السؤال.

هذه بالضبط الفكرة المحورية في مقارنة `private` مقابل `protected` من محاضرة الوراثة: "`private` مخفي حتى عن الأبناء، `protected` مرئي للأبناء" — وهذا هو معيار الاختيار الأساسي بين المحددين الثلاثة عند تصميم أي شجرة وراثة.

**بفرض لدينا السجل Student الذي يعبر عن طالب من خلال رقمه الجامعي وعلامات سبع مواد معرفاً كما يلي:**
```cpp
struct Student {
    int id;
    int marks[7];
};
```
**والصف Class يعبر عن صف من الطلاب أي يحتوي على أكثر من سجل Student بالشكل التالي:**
```cpp
class Class {
private:
    Student stds;
    int numberOfStudents;
public:
    Class() {}
    void addStudent(int id, int marks) {}
    void printStudentInfo(int index) {
        if (index > numberOfStudents) 
            cout << "This student don't exists" << endl;
        else 
            cout << stds[index];
    }
    void avgPerMark(double res) {}
    int numberOfStudents() { return numberOfStudents; }
};
```
*ملاحظة: النص الأصلي للسجل `stds` يستخدمه لاحقاً كمصفوفة/مؤشر (`stds[index]`, `new Student[20]`) رغم أنه معرَّف هنا كمتحول مفرد `Student stds;` — على الأغلب فُقد الرمز `*` في عملية الاستخراج (أي أن التعريف الأصلي كان `Student* stds;`). اعتمدنا هذا التصحيح المنطقي في كل إجابات هذه المجموعة لأنه يطابق استخدام الحقل في بقية الأسئلة.*

**السؤال 121:** بفرض أننا نريد أن نعدل الصف Class ليحوي عمليات خاصة بتعديل علامة طالب، بتعريف الصف Student هل يمكن تعريف مصفوفة من المؤشرات وبالتالي يمكننا تخفيض استهلاك الذاكرة إذ لا يتم إنشاء مقعد إلا عند الحاجة إليه؟
أ) صح
ب) خطأ
**الإجابة الصحيحة: أ**
**التعليل:**
هذا تصميم صحيح ومعروف: بدل حجز مصفوفة كاملة من الأغراض `Student` دفعة واحدة (`new Student[20]`)، يمكن تعريف الحقل كمصفوفة من **مؤشرات** (`Student**` أو `Student* stds[20]`) بحيث يبقى كل عنصر فارغاً (`nullptr`) حتى يُضاف طالب فعلي إليه عبر `new Student(...)`. هذا يوفّر الذاكرة في الحالات التي لا تُستخدم فيها كل المقاعد فعلياً.

هذا بالضبط نفس فكرة `Person** book` في مسألة دفتر الهواتف: مصفوفة من المؤشرات تسمح بحجز ذاكرة كل عنصر بشكل مستقل ووقت الحاجة إليه فقط، بدل حجز كتلة واحدة ثابتة الحجم مسبقاً لكل العناصر دفعة واحدة.

**السؤال 122:** هل يمكن الوصول للمتحول stds ضمن الصف Class من الصف الابن ClassPractical، وإذا لا يمكن كيف بالإمكان ذلك؟
أ) نعم يمكن الوصول ولا حاجة لأي تعديل
ب) من الأفضل حتى تحقق عملية الوصول بشكل آمن بحيث لا يرى المتحول stds إلا الأبناء للصف Class أن نستخدم محدد الوصول protected للمتحول stds
ج) يجب استخدام محدد الوصول public للمتحول stds
د) كل الإجابات السابقة خاطئة
**الإجابة الصحيحة: ب**
**التعليل:**
بما أن `stds` معرَّف حالياً `private`، فهو غير مرئي إطلاقاً لأي صف وارث مثل `ClassPractical` — حتى لو كان الحقل "موروثاً" فعلياً في ذاكرة الغرض. الحل الصحيح هو تغيير محدد الوصول إلى `protected`، الذي يمنح الوصول المباشر للصف نفسه ولكل أبنائه فقط، بلا كشفه لأي كود خارج شجرة الوراثة بالكامل كما يفعل `public`.

أ) خطأ لأن `private` تمنع الوصول عن الأبناء دائماً، بصرف النظر عن الوراثة.
ج) خطأ لأن `public` تفتح الوصول للعالم الخارجي بأكمله، وهذا أوسع بكثير مما هو مطلوب (فقط الأبناء).

هذا يطابق تماماً الفكرة المحورية في مقارنة `private` مقابل `protected`: الأولى مخفية حتى عن الأبناء، والثانية مصمَّمة خصيصاً لتكون مرئية للصف وأبنائه فقط دون الخارج.

**السؤال 123:** كيف يمكن أن نعرف الباني بحيث يقوم بتعريف 20 مقعد للصف الواحد:
أ) `Class() { stds = new Student[20]; }`
ب) `Class() { stds = new Student[20]; numberOfStudents = 0; }`
ج) `Class() { stds = new Student[20]; numberOfStudents = 20; }`
د) لا يوجد أي كود في التابع
**الإجابة الصحيحة: ب**
**التعليل:**
الباني الصحيح يجب أن يقوم بأمرين معاً: حجز مساحة 20 مقعداً (`new Student[20]`)، **و** تصفير عدّاد الطلاب الفعليين `numberOfStudents = 0` (لأن الصف الجديد لا يحتوي أي طالب مضاف بعد، رغم توفر 20 مقعداً محجوزاً).

أ) خطأ لأنها تترك `numberOfStudents` بقيمة غير مُعرَّفة (`garbage`)، ما قد يُسبب سلوكاً غير متوقع لاحقاً عند إضافة طلاب أو حساب المعدلات.
ج) خطأ لأنها تخلط بين "عدد المقاعد الكلي" (20) و"عدد الطلاب الفعليين المضافين" (0 عند الإنشاء) — وهما قيمتان مختلفتان تماماً هنا.

الفرق بين "السعة الكلية المحجوزة" و"العدد الفعلي المستخدم حالياً" هو تمييز جوهري تكرر عبر أكثر من مسألة في هذه المادة (`currentIndex` في دفتر الهواتف، `numberOfStudents` هنا)؛ الخلط بينهما مصدر متكرر للأخطاء المنطقية.

**السؤال 124:** إما أنه أردنا تحميل العملية `>>` على هذا السجل بحيث يمكن طباعة اسم الطلاب وقائمة علاماته من خلال `cout << std` العملية يجب أن تعرف بالشكل التالي:
أ) `friend ostream& operator<<(ostream& out, Student std)`
ب) `friend ostream operator<<(ostream out, Student std)`
ج) `ostream& operator<<(ostream out, Student std)`
د) `operator<<(ostream& out, Student std)`
**الإجابة الصحيحة: أ**
**التعليل:**
لتحميل عامل `<<` بحيث يعمل مع `cout << std`، يجب استيفاء ثلاثة شروط معاً: (1) أن يكون التابع `friend` لأن الطرف الأيسر للعامل (`ostream`) ليس من نوع `Student`، (2) أن يُعيد `ostream&` **بمرجع** لا بقيمة (لأن كائنات الدفق `ostream` لا يجوز نسخها، وإعادة المرجع تسمح بتسلسل عمليات `<<` متتالية)، و(3) أن يستقبل `ostream& out` بمرجع أيضاً للسبب ذاته. الخيار (أ) هو الوحيد المستوفي للشروط الثلاثة معاً.

ب) خطأ لأنها تُعيد `ostream` بالقيمة، وهذا يتطلب نسخ كائن الدفق — وهو غير مسموح أصلاً.
ج) خطأ لأنها ليست `friend`، فيفترضها المترجم تابعاً عضواً يتوقع أن يكون الطرف الأول من نوع `Student` ضمنياً، ما يتعارض مع توقيع العملية المطلوب.
د) خطأ لأنها بلا نوع إرجاع محدد إطلاقاً — تعريف تابع غير مكتمل الصياغة.

هذا يطابق تماماً نمط "تابع صديق للطباعة" الموصوف في محاضرة السجلات: `friend ostream& operator<<(ostream& cout, Complex& n){ ...; return cout; }` — نفس البنية بالضبط، فقط باستبدال `Complex` بـ `Student`.

**السؤال 126:** هل التابع printStudentInfo معرف بشكل صحيح؟
أ) صح
ب) خطأ
**الإجابة الصحيحة: ب**
**التعليل:**

هذا نفس نمط الخطأ الذي ظهر في مسألة دفتر الهواتف بخصوص فحص الحدود قبل الوصول لعنصر — فحص `>` بدل `>=` عند التحقق من صلاحية فهرس هو من أكثر أخطاء "الحدود المنزاحة بواحد" شيوعاً، ويجب دائماً التأكد أن الفهرس الأعظمي المسموح به هو `العدد الفعلي - 1` لا `العدد الفعلي` نفسه.

**السؤال 128:** يحسب التابع avgPerMark متوسط علامات كل مادة، أي مثلاً متوسط علامة البرمجة في الصف 60:
```cpp
void avgPerMark(double res[]) {
    for(int i = 0; i < 7; i++) res[i] = 0;
    for(int i = 0; i < 20; i++) {
        for(int j = 0; j < 7; j++)
            res[j] += stds[i]->marks[j];
    }
    for(int i = 0; i < 20; i++) res[i] /= 20;
}
```
أ) صح
ب) خطأ
**الإجابة الصحيحة: ب**
**التعليل:**
التحقيق يحتوي خطأين منطقيين واضحين: أولاً، حلقة الجمع تستخدم `i < 20` (السعة الكلية للمقاعد) بدل `i < numberOfStudents` (عدد الطلاب المضافين فعلياً)، ما يعني أنها تجمع قيماً من مقاعد فارغة/غير مهيأة (`garbage values`) ضمن الحساب. ثانياً، حلقة القسمة الأخيرة `for(int i=0;i<20;i++) res[i]/=20;` تتجاوز حدود المصفوفة `res` التي يُفترض أن تحمل 7 عناصر فقط (متوسط لكل مادة من المواد السبع)، فتصل لذاكرة خارج حدود المصفوفة عند `i` من 7 إلى 19.

كلا الخطأين مثال مباشر على أهمية استخدام العدد **الفعلي** للعناصر المستخدمة (`numberOfStudents`, `7`) بدل السعة الكلية المحجوزة (`20`) عند إجراء أي عملية تكرارية — خلط الاثنين ينتج قراءة بيانات غير صالحة ووصولاً خارج حدود المصفوفات.

**السؤال 130:** يلزمنا إضافة التابع readfromfile لقراءة معلومات الصف من ملف الثنائية. يمكن حساب عدد الطلاب الفعلي في الشعبة:
أ) `file.seekp(0); int number = file.tellp() / sizeof(Student);`
ب) يمكن الاستفادة منه بتعريف مصفوفة بشكل مباشر
ج) لا يمكن حساب عدد الطلاب
د) كل الإجابات السابقة خاطئة
**الإجابة الصحيحة: د**
**التعليل:**
الخيار (أ) يستخدم أدوات القراءة الخاطئة: `seekp`/`tellp` مخصصتان لمؤشر **الكتابة** (`put pointer`)، بينما القراءة تعتمد دائماً على `seekg`/`tellg` (مؤشر `get`) — استخدام الأدوات الخاطئة هنا خطأ منهجي حتى لو "بدا" الكود منطقياً ظاهرياً. الخيار (ب) غامض وغير محدد تقنياً (لا يصف آلية حساب فعلية). الخيار (ج) خاطئ لأن حساب عدد الطلاب من حجم الملف **ممكن تماماً** وهو بالضبط ما تشرحه محاضرة الملفات العشوائية. بما أن كل الخيارات الثلاثة الأولى غير صحيحة كما وردت بالضبط، فالإجابة الصحيحة هي (د).

الطريقة الصحيحة الفعلية (غير المذكورة في أي خيار سابق) هي: `file.seekg(0, ios::end); long size = file.tellg(); int count = size / sizeof(Student);` — تماماً كما وردت في خوارزمية "معرفة عدد السجلات في الملف" من محاضرة الملفات العشوائية.
