## الجزء الأول: ملخص منظم (اقرأ قبل المحاضرة!)

### 📍 عن هذه المحاضرة
> هذه المحاضرة تشرح مفهوم الدالة `function` في `C++`: كيف نكتبها، كيف نستدعيها، طرق تمرير القيم لها، وأخيراً مفهوم الاستدعاء الذاتي `recursion`.

### 🎯 ستتعلم
- ما هي الدالة ولماذا تُستخدم بدلاً من كتابة كل الكود داخل `main()`.
- الفرق بين تصريح الدالة `prototype` وتعريفها `definition`.
- الفرق بين تمرير المعاملات `call by value` و`call by reference`.
- مفهوم الاستدعاء العودي `recursion` وكيف يُستخدم لحل مسائل مثل `factorial` و`Fibonacci` و`Tower of Hanoi`.

### 📚 المتطلبات السابقة
- المتغيرات وأنواع البيانات (`int`, `float`, `char`) — تحتاجها لفهم أنواع القيم المُعادة والمعاملات.
- الجمل الشرطية `if` — تُستخدم كـ `base condition` في كل دالة عودية.
- بنية برنامج `C++` الأساسية ودالة `main()`.

### 💡 الأفكار الرئيسية
1. **الدالة (Function):** وحدة كود مستقلة لها اسم، تُنفَّذ مهمة محددة، وتُستدعى متى احتجناها بدل تكرار كتابتها.
2. **تمرير المعاملات (Value vs Reference):** يحدد هل التعديل داخل الدالة يؤثر على المتغير الأصلي خارجها أم لا — فرق جوهري يسبب أخطاء منطقية شائعة.
3. **الاستدعاء العودي (Recursion):** أسلوب تفكر فيه الدالة بلغة "المشكلة الكبيرة = نسخة أصغر من نفسها + حالة توقف"، بديل أنيق لبعض الحلقات لكنه أثقل على الذاكرة.

### 🔗 كيف تتصل هذه المحاضرة بالمحاضرات الأخرى؟
- **السابقة:** الجمل الشرطية والحلقات علّمتك التحكم بتدفق البرنامج داخل `main()` ← الآن نبني عليها لتقسيم البرنامج إلى دوال.
- **القادمة:** ستُستخدم الدوال لاحقاً في `arrays`، `structures`، والبرمجة الكائنية (`classes`) حيث كل `method` هي دالة مرتبطة بكائن.

### ⚠️ الأخطاء الشائعة الواجب تجنبها
- ❌ الظن بأن `call by value` يُعدّل المتغير الأصلي دائماً.
- ❌ نسيان `return` في دالة تُعيد قيمة، أو نسيان `base case` في دالة عودية فيسبب استدعاءً لا نهائياً.
- ❌ الخلط بين `Parameters` (في تعريف الدالة) و`Arguments` (عند الاستدعاء).

### 2. بنية الدالة في ++C

#### 2.1. الدالة main()

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_1.2"} -->

#### ⬅️ الربط مع السابق
بعد أن فهمنا لماذا نحتاج الدوال، أول دالة نلتقيها فعلياً في أي برنامج هي `main()`.

#### 💡 الفكرة الأساسية
**كل برنامج `C++` يحتوي دالة رئيسية اسمها `main()` وهي أول دالة تُستدعى تلقائياً عند تشغيل البرنامج.**

#### 💻 الكود
```cpp
int main() {
    return 0;   // ends the program successfully
}
```

#### شرح كل سطر:
1. `int main()` → تعريف الدالة الرئيسية، النوع `int` يعني أنها تُعيد رقماً صحيحاً لنظام التشغيل.
2. `return 0;` → إنهاء البرنامج بنجاح (القيمة صفر تعني "لا يوجد خطأ").
3. `}` → إغلاق جسم الدالة.

**المكتبات المطلوبة (Imports):**
> لا حاجة لأي `#include` لتشغيل هذا الكود وحده، لكن أي طباعة أو إدخال يتطلب `#include <iostream>`.

**الناتج المتوقع (لقطة الشاشة):**
> لا يوجد ناتج مطبوع؛ البرنامج ينتهي مباشرة برمز خروج 0.

#### 📖 الشرح
`main()` هي نقطة الدخول الإلزامية لأي برنامج `C++` — بدونها لن يعرف المترجم من أين يبدأ التنفيذ. يبدأ تنفيذ البرنامج منها، وهي أول دالة يتم استدعاؤها تلقائياً عند تشغيل البرنامج، دون أن يستدعيها المبرمج بنفسه.

#### 💡 التشبيه:
> تشبه `main()` باب الدخول الرئيسي لمبنى — بغض النظر عن عدد الغرف (الدوال) داخل المبنى، الدخول يبدأ دائماً من هذا الباب.
> **وجه الشبه:** الباب الرئيسي = `main()`، الغرف الأخرى = بقية الدوال.

#### 🎯 الملخص السريع
- كل برنامج `C++` يحوي `main()` واحدة.
- تنفيذ البرنامج يبدأ منها تلقائياً.
- `return 0;` تنهي البرنامج بنجاح.

#### 📚 التطبيق
كل دالة أخرى تكتبها ستُستدعى من داخل `main()` بشكل مباشر أو غير مباشر.

#### 2.2. الشكل العام للدالة

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_2.1"} -->

#### ⬅️ الربط مع السابق
بعد أن رأينا `main()` كمثال، هنا نعمم الشكل لأي دالة يمكن أن تكتبها.

#### 💡 الفكرة الأساسية
**كل دالة في `C++` تتبع الصيغة العامة: `return_type function_name(parameters) { statements; return value; }`.**

#### 💻 الكود
```cpp
return_type function_name(parameters) {
    // statements
    return value;
}
```

#### شرح كل سطر:
1. `return_type` → نوع القيمة التي ستُعيدها الدالة (مثل `int`, `float`, أو `void` إن لم تُعِد شيئاً).
2. `function_name(parameters)` → اسم الدالة والمعاملات التي تستقبلها (اختيارية).
3. `// statements` → التعليمات التي تُنفَّذ داخل جسم الدالة.
4. `return value;` → إعادة القيمة النهائية للمستدعي.

#### 📐 التعريف / الصيغة
تتكون كل دالة من أربعة عناصر:
- **Return Type:** نوع القيمة المرجعة.
- **Function Name:** اسم الدالة.
- **Parameters:** المعاملات (اختيارية).
- **Body:** جسم الدالة.

#### 📖 الشرح
هذا الهيكل ثابت لكل دالة تكتبها بغض النظر عن حجمها أو مهمتها. فهم هذه الأربعة أجزاء يجعل قراءة أي دالة جديدة أسهل، لأنك تعرف مسبقاً أين تبحث عن كل معلومة.

#### 🎯 الملخص السريع
- 4 عناصر ثابتة: نوع الإرجاع، الاسم، المعاملات، الجسم.
- المعاملات اختيارية، لكن الاسم والنوع إلزاميان.

#### 📚 التطبيق
هذا القالب هو ما ستستخدمه لكتابة أي دالة لاحقاً، من دوال بسيطة إلى دوال معقدة في المشاريع.

### 3. تعريف وتصريح الدالة

#### 3.1. الفرق بين التصريح والتعريف (Prototype vs Definition)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_2.3"} -->

#### ⬅️ الربط مع السابق
بعد أن كتبنا دالة `sum` كاملة في 2.3، نتعلم هنا كيف نُخبر المترجم بوجودها *قبل* كتابتها بالكامل.

#### 💡 الفكرة الأساسية
**تصريح الدالة `Function Prototype` يخبر المترجم بوجود دالة قبل استخدامها، أما تعريف الدالة فهو تحقيقها وتنفيذها الفعلي.**

#### 💻 الكود
```cpp
int sum(int, int);          // 1. Function Prototype (declaration)

int sum(int a, int b) {     // 2. Function Definition
    return a + b;
}
```

#### شرح كل سطر:
1. `int sum(int, int);` → تصريح: يخبر المترجم أن دالة اسمها `sum` موجودة، تأخذ عددين صحيحين وتُعيد `int` — بدون جسم، وينتهي بفاصلة منقوطة.
2. `int sum(int a, int b) { return a + b; }` → التعريف الكامل: يحتوي على أسماء المعاملات والجسم الفعلي.

#### 📖 الشرح
النقطة **1️⃣ تصريح الدالة (Function Prototype)** تخبر المترجم بوجود دالة قبل استخدامها. أما النقطة **2️⃣ تعريف الدالة** فهي تحقيقها وتنفيذها الفعلي. الفرق الجوهري: التصريح مجرد "إعلان" بلا جسم، بينما التعريف يحوي الكود الفعلي الذي يُنفَّذ.

#### 💡 التشبيه:
> التصريح يشبه إعلان توظيف يقول "سيُعيَّن مهندس اسمه أحمد لاحقاً"، بينما التعريف هو اليوم الذي يبدأ فيه أحمد فعلياً العمل وينجز المهام.
> **وجه الشبه:** الإعلان = `prototype`، بداية العمل الفعلي = `definition`.

#### 🎯 الملخص السريع
- `Prototype`: اسم + نوع الإرجاع + أنواع المعاملات فقط، بدون جسم.
- `Definition`: يحوي الجسم الكامل وتنفيذ المنطق.

#### 📚 التطبيق
هذا التمييز ضروري عند تنظيم الكود في ملفات `.h` (رأس) و`.cpp` (تنفيذ) في مشاريع أكبر لاحقاً.

#### 3.2. لماذا نستخدم Function Prototype؟

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_3.1"} -->

#### ⬅️ الربط مع السابق
بعد أن عرفنا "ما هو" `prototype`، هنا نفهم "متى ولماذا" نحتاجه فعلياً.

#### 💡 الفكرة الأساسية
**نحتاج `Function Prototype` عندما تكون الدالة معرَّفة ومكتوبة بعد `main()`، لأن المترجم يقرأ الكود من الأعلى للأسفل.**

#### 📖 الشرح
عندما تكون الدالة معرَّفة ومكتوبة بعد `main()`، فإن المترجم — الذي يقرأ الملف تسلسلياً من الأعلى للأسفل — سيصل إلى استدعاء الدالة داخل `main()` قبل أن يرى تعريفها، فيعطي خطأ. `Prototype` يحل هذه المشكلة لأنه:
- يمنع أخطاء الترجمة.
- يجعل الكود أوضح ومنظّماً، لأن القارئ يرى أسماء كل الدوال المتوفرة في أعلى الملف.

#### 🤔 تفعيل الفهم (اسأل نفسك):
> **سؤال:** ماذا يحدث لو استدعيت دالة داخل `main()` قبل أن تكتب تعريفها الكامل، وبدون كتابة `prototype` لها في الأعلى؟
> **لماذا هذا مهم؟** لأنه يوضح أن ترتيب الكود مهم في `C++`، على عكس بعض اللغات الأخرى.

#### 🎯 الملخص السريع
- `Prototype` ضروري عند وجود الدالة بعد `main()`.
- يمنع أخطاء الترجمة.
- ينظّم الكود ويجعله أوضح.

#### 📚 التطبيق
سنرى هذا مطبقاً مباشرة في "مثال كامل" التالي حيث `sum` مُعرَّفة بعد `main()`.

#### ⚠️ أخطاء شائعة

#### الفهم الخاطئ ❌:
الاعتقاد بأن `Prototype` ضروري دائماً حتى لو كانت الدالة مكتوبة قبل `main()`.

#### الفهم الصحيح ✅:
`Prototype` ضروري فقط عندما تُستدعى الدالة قبل أن يراها المترجم مكتوبة (أي أنها معرَّفة لاحقاً في الملف). إن كانت الدالة مكتوبة قبل `main()` أصلاً، لا حاجة للتصريح المنفصل.

#### 4.2. مثال كامل

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_4.1"} -->

#### ⬅️ الربط مع السابق
هذا المثال يجمع كل ما تعلمناه: `prototype`، `main()`، تعريف الدالة بعد `main()`، والاستدعاء.

#### 💡 الفكرة الأساسية
**برنامج كامل يوضّح كيف تتعايش `Prototype` و`main()` وتعريف الدالة بعد `main()` في ملف واحد.**

#### 💻 الكود
```cpp
#include <iostream>
using namespace std;

int sum(int, int);          // prototype

int main() {
    int x = 2, y = 4;
    cout << sum(x, y);      // calls sum() before its definition appears
    return 0;
}

int sum(int a, int b) {     // definition after main()
    return a + b;
}
```

#### شرح كل سطر:
1. `#include <iostream>` → استيراد مكتبة الإدخال/الإخراج لاستخدام `cout`.
2. `using namespace std;` → السماح باستخدام `cout` مباشرة بدون كتابة `std::cout`.
3. `int sum(int, int);` → تصريح مسبق يسمح لـ `main()` باستدعاء `sum` قبل رؤية تعريفها.
4. `int main() {` → بداية نقطة الدخول للبرنامج.
5. `int x = 2, y = 4;` → تعريف متغيرين محليين.
6. `cout << sum(x, y);` → استدعاء `sum` بتمرير `x` و`y`، وطباعة الناتج مباشرة.
7. `return 0;` → إنهاء `main()`.
8. `int sum(int a, int b) { return a + b; }` → التعريف الفعلي للدالة، مكتوب بعد `main()` بفضل التصريح المسبق.

**المكتبات المطلوبة (Imports):**
> `#include <iostream>`

**الناتج المتوقع (لقطة الشاشة):**
> `6`

#### 📖 الشرح
هذا المثال يثبت عملياً سبب أهمية `Prototype`: لولا السطر `int sum(int, int);` في الأعلى، لأعطى المترجم خطأً عند وصوله لسطر `cout << sum(x, y);` لأنه لم "يرَ" بعد تعريف `sum`.

#### 🎯 الملخص السريع
- الترتيب الشائع: `includes` → `prototypes` → `main()` → تعريفات الدوال الأخرى.
- الناتج هنا هو `6` لأن `x + y = 2 + 4`.

### 5. أنواع الدوال حسب القيمة المرجعة

#### 5.1. الدوال التي ترجع قيمة

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_4.2"} -->


#### شرح كل سطر:
1. `float average(int a, int b)` → الدالة تُعيد قيمة من نوع `float` رغم أن معاملاتها `int`.
2. `return (a + b) / 2.0;` → القسمة على `2.0` (وليس `2`) تضمن أن الناتج عشري وليس صحيحاً مقطوعاً.

**الناتج المتوقع (لقطة الشاشة):**

> إن طلبت من آلة صرف نقود أن تُعيد لك "عملة معدنية" فقط، فلن تستطيع إعادة فكة ورقية حتى لو كانت أدق — نوع الإرجاع المعلن يقيّد ما يمكن إعادته.

#### 🎯 الملخص السريع
- `return` تعيد القيمة للمستدعي.
- نوع الإرجاع المُعلن يجب أن يطابق نوع القيمة الفعلية.

#### 5.2. الدوال بدون قيمة مرجعة (void)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_5.1"} -->

#### ⬅️ الربط مع السابق
بعد الدوال التي تُعيد قيمة، نتعرف الآن على النوع المقابل الذي لا يُعيد شيئاً.

#### 💡 الفكرة الأساسية
**الدالة من نوع `void` لا تُعيد أي قيمة، لكن يمكن أن يكون لها آثار جانبية `side effects` مثل الطباعة.**

#### 💻 الكود
```cpp
void display() {
    cout << "Hello World";   // side effect: prints text, returns nothing
}
```

#### شرح كل سطر:
1. `void display()` → `void` تعني عدم وجود قيمة إرجاع.
2. `cout << "Hello World";` → أثر جانبي (طباعة) يحدث أثناء تنفيذ الدالة، لكنه ليس "قيمة مُعادة".

**الناتج المتوقع (لقطة الشاشة):**
> `Hello World`

#### 📖 الشرح
الدوال من نوع `void` لا تعيد أي قيمة — لا يوجد `return value;` بداخلها (أو تحتوي `return;` فارغة لإنهاء الدالة مبكراً). لكنها قد يكون لها آثار جانبية، مثل الطباعة على الشاشة أو تعديل متغير خارجي عبر المرجع (سنراه لاحقاً في `call by reference`).

#### ⚖️ المقايضة: دالة ترجع قيمة مقابل void

| | **تُعيد قيمة (مثل int/float)** | **`void`** |
| --- | --- | --- |
| **المزايا** | يمكن استخدام الناتج في تعبيرات أخرى | مناسبة للمهام التي "تُنفَّذ" فقط (طباعة، تهيئة) |
| **العيوب** | تحتاج التعامل مع القيمة المُعادة دائماً | لا يمكن استخدام نتيجتها مباشرة في تعبير حسابي |
| **متى تختاره** | عندما تحتاج نتيجة رقمية/منطقية للاستخدام لاحقاً | عندما تريد تنفيذ أمر أو إجراء بدون حساب قيمة |

#### 🎯 الملخص السريع
- `void` = لا قيمة إرجاع.
- الآثار الجانبية (كالطباعة) لا تُعتبر قيمة مُعادة.
- مفيدة للمهام الإجرائية.

#### 📚 التطبيق
دوال العرض والتهيئة (`setup`, `print`, `initialize`) غالباً تُكتب كـ `void`.

#### 6.2. Parameters vs Arguments

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_6.1"} -->

#### ⬅️ الربط مع السابق
بعد أن عرَّفنا `Parameters`، نميّزها الآن عن `Arguments` التي ذكرناها سابقاً عند الاستدعاء.

#### 💡 الفكرة الأساسية
**`Parameters` موجودة في تعريف الدالة (متغيرات)، بينما `Arguments` هي القيم الفعلية المُمرَّرة عند الاستدعاء.**

#### ⚖️ مقارنة سريعة: Parameters مقابل Arguments

| المعيار | Parameters | Arguments |
| --- | --- | --- |
| **أين تظهر؟** | في تعريف الدالة | عند استدعاء الدالة |
| **طبيعتها** | متغيرات (أسماء شكلية) | قيم فعلية |
| **مثال** | `int a, int b` في `sum(int a, int b)` | `3, 5` في `sum(3, 5)` |
| **متى تستخدم المصطلح؟** | عند الحديث عن تصميم الدالة | عند الحديث عن استدعاء الدالة |

**الخلاصة:**
> فرّق بينهما بسؤال: هل أنا أكتب الدالة أم أستدعيها؟ إن كنت تكتبها فهي `Parameters`، وإن كنت تستدعيها فهي `Arguments`.

#### 📖 الشرح
هذا التمييز مصطلحي بحت لكنه مهم أكاديمياً — كثير من المبتدئين يستخدمون الكلمتين كمترادفتين، لكن في الامتحانات والتوثيق الرسمي (مثل توثيق لغات البرمجة) يُستخدم كل مصطلح في سياقه الدقيق.

#### 🎯 الملخص السريع
- `Parameters`: في تعريف الدالة، متغيرات.
- `Arguments`: عند الاستدعاء، قيم فعلية.

#### 📚 التطبيق
ستُستخدم هذه المصطلحات في كل نقاش عن الدوال لاحقاً، بما فيها رسائل الأخطاء التي يعطيها المترجم (مثل "wrong number of arguments").

### 7. طرق تمرير المعاملات

#### 7.1. الاستدعاء بالقيمة (Call by Value)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_6.2"} -->

#### ⬅️ الربط مع السابق
بعد أن عرفنا المعاملات، نتعلم الآن أول طريقتين لتمرير القيم لها.

#### 💡 الفكرة الأساسية
**في `Call by Value` يتم إرسال نسخة من المتغير، وأي تعديل داخل الدالة لا يؤثر على المتغير الأصلي.**

#### 💻 الكود
```cpp
void change(int x) {
    x = 10;   // modifies only the local copy of x
}
```

#### شرح كل سطر:
1. `void change(int x)` → `x` هنا نسخة مستقلة من أي متغير يُمرَّر عند الاستدعاء.
2. `x = 10;` → يُعدَّل فقط داخل هذه النسخة المحلية؛ المتغير الأصلي خارج الدالة يبقى كما هو.

#### 📖 الشرح
يتم إرسال نسخة من المتغير. أي تعديل داخل جسم الدالة يؤثر فقط على تلك النسخة، ولا يؤثر على المتغير الأصلي في مكان الاستدعاء. هذا هو السلوك الافتراضي لتمرير المتغيرات في `C++` ما لم تُحدِّد خلاف ذلك.

#### 🤔 تفعيل الفهم (اسأل نفسك):
> **سؤال:** لو استدعيت `change(myVar)` حيث `myVar = 5`، ما قيمة `myVar` بعد انتهاء الاستدعاء؟
> **لماذا هذا مهم؟** لأن الإجابة الصحيحة (`5` — لم تتغير) هي أكثر نقطة يخطئ فيها المبتدئون في هذا الموضوع.

#### 🎯 الملخص السريع
- يُرسَل نسخة من المتغير، ليس المتغير نفسه.
- التعديل داخل الدالة محلي فقط.
- هذا هو السلوك الافتراضي في `C++`.

#### 📚 التطبيق
هذا هو الأسلوب الافتراضي المستخدم في كل الأمثلة السابقة (`sum`, `square`, `average`).

<details>

#### 7.2. الاستدعاء بالمرجع (Call by Reference)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_7.1"} -->

#### ⬅️ الربط مع السابق
بعد `Call by Value`، نتعلم الطريقة المقابلة التي تسمح بالتعديل الفعلي على المتغير الأصلي.

#### 💡 الفكرة الأساسية
**في `Call by Reference` (باستخدام `&`) يتم إرسال عنوان المتغير، وأي تعديل داخل الدالة يؤثر مباشرة على المتغير الأصلي.**

#### 💻 الكود
```cpp
void change(int &x) {
    x = 10;   // modifies the original variable directly
}
```

#### شرح كل سطر:
1. `void change(int &x)` → الرمز `&` قبل `x` يعني أن `x` هو مرجع مباشر (اسم بديل) للمتغير الأصلي، وليس نسخة.
2. `x = 10;` → التعديل هنا يطال المتغير الأصلي نفسه في مكان الاستدعاء.

#### 📖 الشرح
يتم إرسال عنوان المتغير بدل نسخة منه. أي تعديل هنا يؤثر مباشرة على المتغير الأصلي، لأن `x` داخل الدالة و`المتغير الأصلي` خارجها يشيران فعلياً لنفس الموقع في الذاكرة.

#### 🔄 قبل / بعد: تعديل متغير بالقيمة مقابل بالمرجع

**قبل (Call by Value — لا تغيير فعلي):**
```cpp
void change(int x) { x = 10; }
int main() {
    int a = 5;
    change(a);
    cout << a;   // prints 5 — unchanged
}
```

**بعد (Call by Reference — تغيير فعلي):**
```cpp
void change(int &x) { x = 10; }
int main() {
    int a = 5;
    change(a);
    cout << a;   // prints 10 — changed!
}
```

**ماذا تغيّر؟** إضافة `&` قبل اسم المعامل حوّلت التعديل من محلي (بلا أثر خارجي) إلى تعديل فعلي على المتغير الأصلي.

#### 💡 التشبيه:
> `Call by Value` مثل إعطاء صديقك نسخة مصورة من مستندك ليكتب عليها؛ مستندك الأصلي يبقى نظيفاً. `Call by Reference` مثل إعطائه المستند الأصلي نفسه — أي تعديل يكتبه عليه سيبقى.
> **وجه الشبه:** النسخة المصورة = `by value`، المستند الأصلي = `by reference`.

#### 🎯 الملخص السريع
- `&` قبل اسم المعامل = تمرير بالمرجع.
- التعديل داخل الدالة ينعكس فعلياً خارجها.
- يُستخدم عندما نحتاج الدالة أن "تُعدِّل" أكثر من قيمة (لأن `return` تُعيد قيمة واحدة فقط).

#### 📚 التطبيق
سنستخدم هذا الأسلوب مباشرة في مثال `swap` التالي لتبديل قيمتي متغيرين فعلياً.

#### 7.3. مثال: تبديل قيمتي متغيرين (swap)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_7.2"} -->

#### ⬅️ الربط مع السابق
هذا مثال تطبيقي مباشر على `Call by Reference` — بدونها لن تعمل دالة `swap` أبداً.

#### 💡 الفكرة الأساسية
**دالة `swap` تُبدِّل قيمتي متغيرين باستخدام `Call by Reference` ومتغير مؤقت `temp`.**

#### 💻 الكود
```cpp
void swap(int &a, int &b) {
    int temp = a;   // save a's value temporarily
    a = b;          // put b's value into a
    b = temp;       // put the saved original a into b
}
```

#### شرح كل سطر:
1. `void swap(int &a, int &b)` → معاملان بالمرجع، أي أي تعديل عليهما يعكس على المتغيرات الأصلية.
2. `int temp = a;` → حفظ قيمة `a` مؤقتاً قبل أن تُفقد.
3. `a = b;` → إعطاء `a` قيمة `b`.
4. `b = temp;` → إعطاء `b` القيمة الأصلية لـ `a` المحفوظة في `temp`.

#### 🔍 تتبع التنفيذ: swap(x, y) حيث x=2, y=4

**المدخل:** `x = 2`, `y = 4`

| الخطوة | العملية | الحالة |
| --- | --- | --- |
| 1 | `int temp = a;` (أي `a=x=2`) | `temp = 2`, `a(x) = 2`, `b(y) = 4` |
| 2 | `a = b;` | `a(x) = 4`, `b(y) = 4`, `temp = 2` |
| 3 | `b = temp;` | `a(x) = 4`, `b(y) = 2` |

**النتيجة:** بعد الاستدعاء، أصبح `x = 4` و`y = 2` — تم التبديل فعلياً في المتغيرات الأصلية بفضل `&`.

#### 📖 الشرح
لو استخدمنا `Call by Value` هنا (بدون `&`)، لتبادلت النسخ المحلية فقط دون أي أثر على `x` و`y` الأصليين خارج الدالة — وهذا أشهر مثال يوضّح لماذا نحتاج `Call by Reference` أحياناً.

#### مهم للامتحان ⚠️:
> دالة `swap` بدون `&` (أي `void swap(int a, int b)`) هي **خطأ منطقي شائع جداً** في الامتحانات — الكود يترجم بدون خطأ لكنه لا يُبدّل شيئاً فعلياً.

#### 🎯 الملخص السريع
- `swap` مثال كلاسيكي يحتاج `Call by Reference` إلزامياً.
- المتغير المؤقت `temp` ضروري لعدم فقدان القيمة الأصلية.
- التتبع خطوة بخطوة يثبت أن التبديل حصل فعلياً على المتغيرات الأصلية.

#### 📚 التطبيق
هذا النمط (`swap`) أساسي في خوارزميات الفرز (`sorting algorithms`) التي ستراها لاحقاً.

#### 8.1. المعاملات الافتراضية (Default Arguments)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_7.3"} -->

#### ⬅️ الربط مع السابق
بعد أن أتقنّا طرق تمرير المعاملات، نتعلم الآن ميزة تجعل بعض المعاملات اختيارية عند الاستدعاء.

#### 💡 الفكرة الأساسية
**يمكن إسناد قيم افتراضية للمعاملات، تُستخدم تلقائياً إن لم يُمرَّر المستدعي قيمة لها، وهذه المعاملات يجب أن تكون آخر المعاملات في التعريف.**

#### 💻 الكود
```cpp
int add(int a, int b = 5) {
    return a + b;   // if b is not provided, it defaults to 5
}
```

#### شرح كل سطر:
1. `int add(int a, int b = 5)` → المعامل `b` له قيمة افتراضية `5`.
2. `return a + b;` → إن استُدعيت `add(3)` فقط، ستُستخدم `b = 5` تلقائياً؛ أما `add(3, 10)` فستستخدم `b = 10`.

**الناتج المتوقع (لقطة الشاشة):**
> `add(3)` تُعيد `8`، بينما `add(3, 10)` تُعيد `13`.

#### 📖 الشرح
يمكن إسناد قيم افتراضية إلى المعاملات بحيث يتم استخدامها في حال تم استدعاء التابع بدون إعطاء قيمة لهذه المعاملات. **قاعدة مهمة:** المعاملات الافتراضية يجب أن تكون آخر معاملات ضمن تعريف التابع — لا يمكن أن يأتي معامل عادي (بدون قيمة افتراضية) بعد معامل له قيمة افتراضية.

#### مهم للامتحان ⚠️:
> كتابة `int add(int a = 5, int b)` **خطأ ترجمة** — المعامل الافتراضي يجب أن يكون في النهاية دائماً.

#### 🎯 الملخص السريع
- صيغة `type name = value` تُعطي قيمة افتراضية.
- المعاملات الافتراضية تكون دائماً في آخر قائمة المعاملات.
- تُستخدم لتقليل عدد الحالات المكررة عند الاستدعاء.

#### 📚 التطبيق
مفيدة في دوال الإعدادات (`settings`) حيث معظم الاستدعاءات تستخدم قيماً شائعة ونادراً ما تحتاج تخصيصاً.

#### 8.2. التحميل الزائد للدوال (Function Overloading)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->

1. `int add(int a, int b);` → نسخة تعمل مع أعداد صحيحة.

#### 8.3. الدوال المضمنة (Inline Functions)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_8.2"} -->

#### ⬅️ الربط مع السابق
آخر ميزة إضافية في هذا الجزء، تخص كيفية معالجة المترجم للدالة عند تنفيذها.

#### 💡 الفكرة الأساسية
**كلمة `inline` تطلب من المترجم استبدال استدعاء الدالة بجسمها مباشرة في الكود، وتُستخدم للدوال الصغيرة فقط.**

#### 💻 الكود
```cpp
inline int cube(int x) {
    return x * x * x;   // small enough to be inlined
}
```

#### شرح كل سطر:
1. `inline int cube(int x)` → الكلمة المفتاحية `inline` قبل نوع الإرجاع.
2. `return x * x * x;` → جسم بسيط جداً، مناسب لتقنية `inline`.

#### 📖 الشرح
تطلب من المترجم استبدال الدالة بالكود مباشرة (بدل عملية استدعاء فعلية تتطلب قفزة في الذاكرة). تُستخدم للدوال الصغيرة، لأن استبدال دالة كبيرة في كل مكان تُستدعى فيه سيُضخِّم حجم البرنامج النهائي دون فائدة حقيقية بالأداء.

#### ⚖️ المقايضة: inline مقابل دالة عادية

| | **inline** | **دالة عادية** |
| --- | --- | --- |
| **المزايا** | أسرع تنفيذاً (لا قفزة استدعاء) | حجم برنامج أصغر |
| **العيوب** | يزيد حجم البرنامج إن استُخدمت لدوال كبيرة | أبطأ قليلاً بسبب آلية الاستدعاء |
| **متى تختاره** | دوال قصيرة جداً تُستدعى كثيراً | دوال متوسطة أو كبيرة الحجم |

#### 🎯 الملخص السريع
- `inline` = استبدال الاستدعاء بالكود الفعلي مباشرة.
- مناسبة فقط للدوال الصغيرة.
- المترجم قد يتجاهل طلب `inline` إن رأى الدالة كبيرة جداً.

#### 📚 التطبيق
شائعة في الدوال الحسابية القصيرة المتكررة كثيراً، مثل حساب مربع أو مكعب رقم.

### 9. نطاق المتغيرات (Scope)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_8.3"} -->

#### ⬅️ الربط مع السابق
بعد أن تعلمنا كل شيء عن كتابة الدوال، نحتاج لفهم "أين يعيش" كل متغير نستخدمه بداخلها أو خارجها.

#### 💡 الفكرة الأساسية
**المتغير المحلي `Local Variable` موجود داخل الدالة فقط، بينما المتغير العام `Global Variable` موجود خارج جميع الدوال ويمكن الوصول إليه من أي مكان في البرنامج.**

#### 💻 الكود
```cpp
int x = 5;   // Global variable — accessible from any function

void show() {
    int y = 10;    // Local variable — exists only inside show()
    cout << x + y; // can access both x (global) and y (local)
}
```

#### شرح كل سطر:
1. `int x = 5;` → متغير عام، مكتوب خارج أي دالة، يمكن لأي دالة في الملف الوصول إليه.
2. `int y = 10;` → متغير محلي، يُنشأ عند دخول الدالة `show()` ويختفي عند خروجها.

#### 📐 التعريف / الصيغة
- **Local Variable:** داخل الدالة فقط.
- **Global Variable:** خارج جميع الدوال.

#### 📖 الشرح
المتغير المحلي يُنشأ عند بدء تنفيذ الدالة ويُحذف من الذاكرة فور انتهائها — لا يمكن لأي دالة أخرى رؤيته. المتغير العام، على العكس، يُنشأ مرة واحدة عند بدء البرنامج ويبقى متاحاً لأي دالة طيلة عمر البرنامج.

#### 💡 التشبيه:
> المتغير المحلي مثل غرض تستخدمه داخل غرفة فندق وتتركه فيها عند مغادرتها؛ المتغير العام مثل غرض تحمله معك في حقيبتك أينما ذهبت في الفندق.
> **وجه الشبه:** الغرفة الواحدة = جسم الدالة (`local scope`)، الحقيبة التي ترافقك = النطاق العام (`global scope`).

#### مهم للامتحان ⚠️:
> استخدام المتغيرات العامة بكثرة يُعتبر ممارسة سيئة `bad practice` لأنه يصعّب تتبع من يُعدِّل المتغير ومتى — وهذا أحد أسباب استخدام الدوال والمعاملات أصلاً بدل الاعتماد على متغيرات عامة (راجع سبب "تخيل برنامجاً كبيراً بمئات المتغيرات العامة" في القسم 1.2).

#### 🎯 الملخص السريع
- `Local`: داخل الدالة فقط، يختفي بعد انتهائها.
- `Global`: خارج كل الدوال، متاح للجميع طيلة عمر البرنامج.
- كثرة المتغيرات العامة تُصعِّب الصيانة.

#### 📚 التطبيق
فهم `Scope` ضروري لتفادي تضارب أسماء المتغيرات لاحقاً في برامج أكبر متعددة الملفات.

### 10. أخطاء شائعة عند استخدام الدوال

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_9"} -->

#### ⬅️ الربط مع السابق
بعد تغطية كل جوانب الدوال العادية (غير العودية)، نجمع هنا أشهر الأخطاء التي تظهر عند تطبيقها فعلياً.

#### 💡 الفكرة الأساسية
**معظم أخطاء الدوال الشائعة تقع في أربع فئات: نسيان `return`، اختلاف نوع القيمة الراجعة، عدد معاملات خاطئ، أو استدعاء بدون تصريح مسبق.**

#### 📖 الشرح
- **نسيان `return`:** دالة معرَّفة لتُعيد قيمة (مثلاً `int`) لكن جسمها لا يحتوي `return` — يسبب سلوكاً غير معرّف (`undefined behavior`) أو تحذير من المترجم.
- **اختلاف نوع القيمة الراجعة:** مثل إعادة `float` من دالة معرَّفة كـ `int`، مما يفقد الجزء العشري.
- **عدد معاملات خاطئ:** استدعاء دالة تحتاج معاملين بمعامل واحد فقط (وبدون قيمة افتراضية لذلك المعامل الناقص) يسبب خطأ ترجمة.
- **تحقيق (تعريف) بدون تصريح:** استدعاء دالة معرَّفة لاحقاً في الملف دون كتابة `Prototype` مسبق لها.

#### الفهم الخاطئ الشائع ❌:
> "طالما البرنامج يترجم بدون أخطاء حمراء، فلا يوجد مشكلة في الدالة."

#### الفهم الصحيح ✅:
> بعض الأخطاء (مثل نسيان `&` في `Call by Reference`، أو فقدان الدقة عند اختلاف نوع الإرجاع) لا تُظهر خطأ ترجمة، بل تسبب نتيجة خاطئة صامتة يكتشفها المبرمج فقط عند اختبار الناتج فعلياً.

#### 🎯 الملخص السريع
- نسيان `return`.
- اختلاف نوع القيمة الراجعة عن نوعها المُعلن.
- عدد معاملات خاطئ عند الاستدعاء.
- تعريف بدون تصريح مسبق (عند الحاجة له).

#### 📚 التطبيق
هذه القائمة نفسها هي أساس قسم "Troubleshooting" الذي تراجعه كلما ظهر خطأ غامض في برنامجك.

### 11. الاستدعاء العودي Recursion

#### 11.1. ما هو Recursion ولماذا نستخدمه؟

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_10"} -->

#### ⬅️ الربط مع السابق
بعد أن أتقنّا الدوال "العادية" التي تستدعي بعضها، ننتقل الآن لحالة خاصة: دالة تستدعي *نفسها*.

#### 💡 الفكرة الأساسية
**الاستدعاء العودي `Recursion` هو أسلوب برمجي تقوم فيه الدالة باستدعاء نفسها، ويُستخدم لحل المسائل التي يمكن تقسيمها إلى مسائل أصغر من نفس النوع.**

#### 📖 الشرح
الاستدعاء العودي هو أسلوب برمجي تقوم فيه الدالة باستدعاء نفسها. ُيستخدم لحل المسائل التي يمكن تقسيمها إلى مسائل أصغر من نفس النوع، مثل حساب العاملي `Factorial` أو متسلسلة `Fibonacci` أو خوارزميات البحث في البنى الشجرية.

**لماذا نستخدم `Recursion`؟**
- تبسيط حل بعض المسائل المعقدة.
- مناسب لمسائل مثل: حساب العاملي `Factorial`، متسلسلة فيبوناتشي، خوارزميات البحث في البنى الشجرية (لاحقاً).
- يجعل الكود أقرب للوصف الرياضي للمشكلة.

#### 💡 التشبيه:
> تخيل دمى `matryoshka` الروسية المتداخلة — كل دمية تحتوي نسخة أصغر من نفسها، حتى تصل لأصغر دمية لا تحتوي شيئاً بداخلها (وهذه هي نقطة التوقف).
> **وجه الشبه:** الدمية الكبيرة تفتح لتكشف نسخة أصغر منها = الاستدعاء العودي، أصغر دمية بلا محتوى = `Base Case`.

#### 🎯 الملخص السريع
- الدالة تستدعي نفسها لحل نسخة أصغر من نفس المسألة.
- مفيدة للمسائل القابلة للتجزئة الرياضية (عاملي، فيبوناتشي، أشجار).
- تجعل الكود أقرب لصيغة المسألة الرياضية الأصلية.

#### 📚 التطبيق
سنستخدمها فوراً في أمثلة `Factorial` و`Fibonacci` و`Tower of Hanoi`.

#### 11.2. الشكل العام والمكونات الأساسية (Base Case / Recursive Case)

<!-- @render: {type: "code-first", visualization: "diagram", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_11.1"} -->

#### ⬅️ الربط مع السابق
بعد فهم فكرة `Recursion` عموماً، نحتاج الآن هيكلها الإلزامي حتى لا تدور الدالة إلى الأبد.

#### 💡 الفكرة الأساسية
**كل دالة عودية تتكوّن من جزأين أساسيين: الحالة الأساسية `Base Case` التي توقف الاستدعاء، والحالة العودية `Recursive Case` التي تستدعي الدالة نفسها بقيم أصغر.**

#### 💻 الكود
```cpp
return_type function_name(parameters) {
    if (base_condition) {
        return base_value;              // 1) Base Case: stops recursion
    }
    return function(smaller_problem);   // 2) Recursive Case: calls itself
}
```

#### شرح كل سطر:
1. `if (base_condition) { return base_value; }` → **الحالة الأساسية (Base Case):** توقف الاستدعاء العودي؛ بدونها يحدث استدعاء لا نهائي.
2. `return function(smaller_problem);` → **الحالة العودية (Recursive Case):** تستدعي الدالة نفسها بقيم أصغر تقترب تدريجياً من `base_condition`.

#### 📐 التعريف / الصيغة
1️⃣ **الحالة الأساسية (Base Case):** توقف الاستدعاء العودي. بدونها يحدث استدعاء لا نهائي.
2️⃣ **الحالة العودية (Recursive Case):** تستدعي الدالة نفسها بقيم أصغر.

#### 📊 المخطط التوضيحي: تدفق تنفيذ دالة عودية

#### ما هذا المخطط؟
> يوضّح تدفق القرار داخل أي دالة عودية: هل وصلنا لحالة التوقف أم علينا الاستمرار بالاستدعاء الذاتي؟

#### وصف العُقد:
| # | العُقدة | النوع | الشرح |
| --- | --- | --- | --- |
| 1 | Start | event | استدعاء الدالة بقيمة `n` |
| 2 | Check base_condition | decision | هل `n` وصل لحالة التوقف؟ |
| 3 | Return base_value | process | إعادة قيمة ثابتة معروفة وإنهاء هذا الاستدعاء |
| 4 | Call function(smaller_problem) | process | استدعاء الدالة نفسها بقيمة أصغر |
| 5 | Combine and return | process | دمج النتيجة القادمة من الاستدعاء الأصغر وإعادتها للمستدعي |

#### وصف الروابط:
| من | إلى | التسمية | نوع السهم | الشرح |
| --- | --- | --- | --- | --- |
| Start | Check base_condition | - | عادي | بداية كل استدعاء بفحص الشرط |
| Check base_condition | Return base_value | نعم | شرطي | حالة التوقف تحققت |
| Check base_condition | Call function(smaller_problem) | لا | شرطي | لم تتحقق بعد، نكمل بالتصغير |
| Call function(smaller_problem) | Combine and return | - | عادي | بعد عودة الاستدعاء الأصغر بنتيجته |

#### 📖 الشرح
بدون `Base Case`، ستستمر الدالة باستدعاء نفسها إلى الأبد (نظرياً) حتى تنفد ذاكرة المكدس `Stack Overflow` عملياً. `Recursive Case` يجب أن يقترب في كل مرة أكثر من `Base Case` (مثلاً `n-1` بدل `n`)، وإلا لن نصل أبداً لحالة التوقف رغم وجودها.

#### مهم للامتحان ⚠️:
> ترتيب الجزأين مهم: يجب فحص `Base Case` **قبل** إجراء الاستدعاء العودي، وليس بعده — وإلا سيحدث استدعاء واحد إضافي غير ضروري (أو لا نهائي) قبل أن يُفحص الشرط.

#### 🎯 الملخص السريع
- كل دالة عودية = `Base Case` + `Recursive Case`.
- `Base Case` يوقف السلسلة، `Recursive Case` يستدعي بقيمة أصغر تقترب من التوقف.
- غياب أي منهما يسبب استدعاء لا نهائي.

#### 📚 التطبيق
هذا القالب بالضبط هو ما سنملأه في كل الأمثلة القادمة: `Factorial`, `Fibonacci`, `print`, و`Tower of Hanoi`.

### 12. أمثلة على Recursion

#### 12.1. مثال 1: حساب العاملي Factorial

<!-- @render: {type: "code-first", visualization: "diagram", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_11.2"} -->

#### ⬅️ الربط مع السابق
أول تطبيق مباشر لمكوني `Recursion` اللذين رأيناهما في 11.2.

#### 💡 الفكرة الأساسية
**حساب العاملي `n!` عودياً: الحالة الأساسية `0! = 1`، والحالة العودية `n! = n × (n-1)!`.**

#### 💻 الكود
```cpp
int factorial(int n) {
    if (n == 0)
        return 1;                    // Base Case
    return n * factorial(n - 1);     // Recursive Case
}
```

#### شرح كل سطر:
1. `if (n == 0) return 1;` → الحالة الأساسية: عاملي الصفر يساوي 1 دائماً.
2. `return n * factorial(n - 1);` → الحالة العودية: نضرب `n` بنتيجة عاملي `n-1`، وهكذا يصغر `n` في كل استدعاء حتى يصل للصفر.

**الناتج المتوقع (لقطة الشاشة):**
> `factorial(4)` تُعيد `24`.

#### 📐 التعريف / الصيغة
$$
n! = n \times (n-1)! \qquad , \qquad 0! = 1
$$

**الشرح:**
> `n!` = عاملي العدد `n` المطلوب حسابه.
> `(n-1)!` = عاملي العدد الأصغر بواحد، وهو الاستدعاء العودي.
> `0!` = الحالة الأساسية، قيمتها ثابتة تساوي `1`.

#### 🔍 تتبع التنفيذ: factorial(4)

**المدخل:** `n = 4`

| الخطوة | العملية | الحالة |
| --- | --- | --- |
| 1 | `factorial(4)` → `4 * factorial(3)` | ينتظر نتيجة `factorial(3)` |
| 2 | `factorial(3)` → `3 * factorial(2)` | ينتظر نتيجة `factorial(2)` |
| 3 | `factorial(2)` → `2 * factorial(1)` | ينتظر نتيجة `factorial(1)` |
| 4 | `factorial(1)` → `1 * factorial(0)` | ينتظر نتيجة `factorial(0)` |
| 5 | `factorial(0)` → `1` ✅ | Base Case تحقق، بدء العودة للخلف |

**النتيجة:** بالعودة للخلف: `1×1=1` ← `2×1=2` ← `3×2=6` ← `4×6=24`. إذن `factorial(4) = 24`.

#### 📊 المخطط التوضيحي: تمثيل شجري للاستدعاء العودي

#### ما هذا المخطط؟
> يوضّح كيف تتفرّع الاستدعاءات المتتالية لـ `factorial(4)` حتى الوصول لـ `Base Case`، ثم كيف تعود النتائج للخلف.

| 4 | factorial(1) | process | استدعاء فرعي ثالث |
| 5 | factorial(0) | event | Base Case — نهاية التفرع |

#### 12.2. مثال 2: متسلسلة فيبوناتشي Fibonacci

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_12.1"} -->

#### ⬅️ الربط مع السابق
بعد `factorial` (استدعاء ذاتي واحد لكل مستوى)، نرى الآن مثالاً باستدعاءين ذاتيين لكل مستوى.

#### 💡 الفكرة الأساسية
**متسلسلة فيبوناتشي: كل عدد يساوي مجموع العددين السابقين له، وتُحسب عودياً بالصيغة `F(n) = F(n-1) + F(n-2)`.**

#### 💻 الكود
```cpp
long fib(long n) {
    if (n <= 1)
        return n;                       // Base Case
    return fib(n - 1) + fib(n - 2);      // Recursive Case (two calls!)
}
```

#### شرح كل سطر:
1. `if (n <= 1) return n;` → الحالة الأساسية: `F(0) = 0` و`F(1) = 1`.
2. `return fib(n - 1) + fib(n - 2);` → الحالة العودية: تستدعي الدالة نفسها **مرتين** لكل مستوى، وتجمع نتيجتيهما.

**الناتج المتوقع (لقطة الشاشة):**
> `fib(5)` تُعيد `5` (السلسلة: 0, 1, 1, 2, 3, 5, 8, …).

#### 📐 التعريف / الصيغة
هي سلسلة أعداد, كل عدد فيها يساوي مجموع العددين السابقين له. تبدأ السلسلة عادة بالرقمين 0، 1 وتكون على الشكل: 0، 1، 1، 2، 3، 5، 8، …

$$
F(n) = F(n-1) + F(n-2) \qquad , \qquad F(0) = 0 , F(1) = 1
$$

**الشرح:**
> `F(n)` = الحد المطلوب حسابه في السلسلة.
> `F(n-1)` و`F(n-2)` = الحدان السابقان مباشرة، والاستدعاءان العوديان.

#### 📖 الشرح
هذا الحل غير فّعال للأرقام الكبيرة، لأنه يسبب عدداً كبيراً جداً من الاستدعاءات المكررة (نفس القيمة تُحسب أكثر من مرة في فروع مختلفة من الشجرة). الهدف منه هنا تعليمي فقط لفهم الاستدعاء العودي `Recursion` بمثال يحتوي أكثر من استدعاء ذاتي واحد.

#### مهم للامتحان ⚠️:
> على عكس `factorial` الذي يستدعي نفسه **مرة واحدة** في كل مستوى، `fib` تستدعي نفسها **مرتين**، مما يجعل عدد الاستدعاءات الكلي ينمو أسّياً `exponential growth` مع زيادة `n`.

#### 🎯 الملخص السريع
- `Base Case`: `n ≤ 1` تُعيد `n` نفسها.
- `Recursive Case`: مجموع استدعاءين `fib(n-1) + fib(n-2)`.
- غير فعّال للأرقام الكبيرة بسبب تكرار الحسابات؛ الهدف هنا تعليمي فقط.

#### 📚 التطبيق
لاحقاً في مواد الخوارزميات ستتعرف على تحسينات مثل `memoization` أو `dynamic programming` لحل هذه المشكلة بكفاءة أعلى.

### 13. Recursion مقابل Loops

#### 13.1. مقارنة Recursion vs Loop

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_12.3"} -->

#### ⬅️ الربط مع السابق
بعد أن رأينا 3 أمثلة على `Recursion`، من المهم الآن مقارنته بالبديل الأكثر شيوعاً: الحلقات `Loops`.

#### 💡 الفكرة الأساسية
**`Recursion` أسهل للفهم في بعض المسائل لكنه يستهلك ذاكرة أكثر (عبر بنية المكدس `Stack`)، بينما `Loops` أسرع وأقل استهلاكاً للذاكرة.**

#### ⚖️ المقايضة: Recursion مقابل Loop

| | **Recursion (الاستدعاء العودي)** | **Loop (الحلقات)** |
| --- | --- | --- |
| **المزايا** | أسهل للفهم في بعض المسائل | أسرع في الأداء، أبسط في التنفيذ |
| **العيوب** | يستهلك ذاكرة أكثر، يعتمد على بنية المكدس `Stack` | أحياناً أقل وضوحاً لمسائل تفرّعية (كالأشجار) |
| **متى تختاره** | عند وجود مسألة تُقسَّم طبيعياً لمسائل أصغر من نفس النوع (أشجار، تفريعات) | عند وجود حل تكراري بسيط، أو عند الحاجة لسرعة تنفيذ وكفاءة في استخدام الذاكرة |

#### 📖 الشرح
كل دالة عودية تستهلك مساحة إضافية في ذاكرة المكدس `Stack` لكل استدعاء (لحفظ حالة الاستدعاء الحالي بانتظار عودة الاستدعاء الفرعي)؛ لذلك مع أعداد كبيرة جداً قد تحدث مشكلة `Stack Overflow`. الحلقات `Loops`، في المقابل، تستخدم عادة متغيراً واحداً فقط يتكرر تحديثه، دون تراكم ذاكرة إضافية.

#### 🎯 الملخص السريع
- `Recursion`: أسهل فهماً لمسائل تفرّعية، لكنه أثقل على الذاكرة.
- `Loop`: أسرع وأخف على الذاكرة، وأبسط تنفيذاً لمسائل تكرارية بسيطة.
- استخدم `Loops` عند وجود حل تكراري مباشر، واستخدم `Recursion` عند التعامل مع بنى متفرعة طبيعياً.

#### 📚 التطبيق
هذا القرار (اختيار `Recursion` أو `Loop`) ستأخذه باستمرار عند حل مسائل الخوارزميات لاحقاً في المساق.

#### 13.2. أخطاء شائعة في كتابة دالة عودية

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_13.1"} -->

#### ⬅️ الربط مع السابق
نختم موضوع `Recursion` بجمع أشهر الأخطاء التي تحدث عند كتابة دالة عودية، ومتى نتجنب `Recursion` أصلاً لصالح `Loops`.

#### 💡 الفكرة الأساسية
**أشهر أخطاء الدوال العودية: نسيان الحالة الأساسية، أو كتابتها بشكل غير صحيح، أو عدم تقليل حجم المشكلة في كل استدعاء.**

#### 📖 الشرح
- **نسيان الحالة الأساسية:** يسبب استدعاءً لا نهائياً حتى تنفد الذاكرة.
- **الحالة الأساسية غير صحيحة:** مثلاً وضع شرط لن يتحقق أبداً بسبب طريقة تصغير المعامل (كأن تُصغّر `n` بمقدار 2 بينما الشرط يتحقق فقط عند قيمة فردية غير قابلة للوصول).
- **عدم تقليل حجم المشكلة:** أي نسيان تغيير المعامل عند الاستدعاء الذاتي (مثل كتابة `factorial(n)` بدل `factorial(n-1)` بالخطأ)، مما يجعل كل استدعاء مطابقاً للسابق ولا يقترب أبداً من التوقف.

**استخدام الحلقات `Loops` بدل الاستدعاء العودي `Recursion`:**
- عند وجود حل تكراري بسيط.
- عند الحاجة لسرعة تنفيذ وكفاءة باستخدام الذاكرة.

#### الفهم الخاطئ الشائع ❌:
> "بما أن الحل العودي أقصر وأنيق أكثر، فهو دائماً الخيار الأفضل."

#### الفهم الصحيح ✅:
> الأناقة لا تعني الكفاءة — إن وُجد حل تكراري بسيط (`loop`) بنفس الوضوح تقريباً، يُفضَّل غالباً لأنه أسرع وأخف على الذاكرة، ويُحتفظ بـ `Recursion` للمسائل التي تُبنى طبيعياً على تفرعات (كالأشجار والبحث المتكرر).

#### 🎯 الملخص السريع
- 3 أخطاء رئيسية: نسيان `Base Case`، `Base Case` خاطئة، عدم تقليل حجم المشكلة.
- استبدل `Recursion` بـ `Loop` عند توفر حل تكراري بسيط أو عند أولوية الأداء والذاكرة.

#### 📚 التطبيق
هذه الأخطاء هي أول ما يُفحص عند تصحيح أي دالة عودية لا تعمل كما متوقع (تجمّد البرنامج أو خطأ `Stack Overflow`).

### 14. مسألة أبراج هانوي (Tower of Hanoi)

<!-- @render: {type: "code-first", visualization: "diagram", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_13.2"} -->

#### ⬅️ الربط مع السابق
خاتمة المحاضرة: مثال شامل ومتقدّم يجمع كل مفاهيم `Recursion` التي تعلمناها (Base Case، Recursive Case، تصغير المشكلة) في مسألة كلاسيكية شهيرة.

#### 💡 الفكرة الأساسية
**مسألة أبراج هانوي تنقل جميع الأقراص من البرج `A` إلى البرج `C` باستخدام البرج `B` كمساعد، بشرط عدم وضع قرص أكبر فوق قرص أصغر، وتُحل بأناقة باستخدام `Recursion`.**

#### 💻 الكود
```cpp
#include <iostream>
using namespace std;

void hanoi(int n, char src, char dist, char aux) {
    if (n == 1) {                          // Base Case
        cout << "Move disk 1 from "
             << src << " to " << dist << endl;
        return;
    }

    hanoi(n - 1, src, aux, dist);          // move n-1 disks: source -> auxiliary

    cout << "Move disk " << n << " from "
         << src << " to " << dist << endl; // move the biggest disk: source -> destination

    hanoi(n - 1, aux, dist, src);          // move n-1 disks: auxiliary -> destination
}

int main() {
    int n;
    cout << "Enter number of disks: ";
    cin >> n;

    hanoi(n, 'A', 'C', 'B');
    return 0;
}
```

#### شرح كل سطر:
1. `void hanoi(int n, char src, char dist, char aux)` → `n` عدد الأقراص، `src` البرج المصدر، `dist` البرج الهدف، `aux` البرج المساعد.
2. `if (n == 1) { ... return; }` → **الحالة الأساسية:** قرص واحد فقط ينتقل مباشرة من `src` إلى `dist`، بدون حاجة لخطوات إضافية.
3. `hanoi(n - 1, src, aux, dist);` → **الحالة العودية (جزء 1):** ننقل أول `n-1` قرصاً من `src` إلى `aux` (البرج المساعد يصبح مؤقتاً هدفاً وسيطاً).
4. `cout << "Move disk " << n ...` → ننقل القرص الأكبر (`n`) مباشرة من `src` إلى `dist` — هذا القرص هو الوحيد المتبقي على `src` بعد الخطوة السابقة.
5. `hanoi(n - 1, aux, dist, src);` → **الحالة العودية (جزء 2):** ننقل الأقراص الـ `n-1` من `aux` إلى `dist` باستخدام `src` كمساعد هذه المرة.

**المكتبات المطلوبة (Imports):**
> `#include <iostream>`

**الناتج المتوقع (لقطة الشاشة):**
> لإدخال `n = 4`، يطبع البرنامج تسلسل 15 خطوة نقل (`Move disk ...`)، وهو أقل عدد ممكن من الحركات لحل المسألة بأربعة أقراص.

#### 📐 التعريف / الصيغة
مسألة تقليدية ُتستخدم لشرح مفهوم الاستدعاء العودي `Recursion`. الهدف: نقل جميع الأقراص من البرج `A` إلى البرج `C` باستخدام البرج `B` كمساعد.

**القواعد:**
- نقل قرص واحد فقط في كل مرة.
- يسمح بنقل القرص العلوي فقط من أي برج.
- لا يجوز وضع قرص أكبر فوق قرص أصغر.

**أقل عدد حركات لحل المسألة:**
$$
\text{Minimum Moves} = 2^n - 1
$$

**الشرح:**
> `n` = عدد الأقراص.
> `2^n - 1` = أقل عدد ممكن من الحركات لحل المسألة بالكامل (فمثلاً 4 أقراص تحتاج `2⁴ - 1 = 15` حركة كما رأينا في المثال).

#### 📊 المخطط التوضيحي: تدفق حل أبراج هانوي بالاستدعاء العودي

#### ما هذا المخطط؟
> يوضّح كيف تُقسَّم مسألة نقل `n` قرص إلى ثلاث خطوات فرعية: نقل `n-1` قرص جانباً، نقل القرص الكبير، ثم نقل `n-1` قرص للهدف.

#### وصف العُقد:

| 3 | نقل القرص مباشرة | event | Base Case: قرص واحد ينتقل من src إلى dist |
| 4 | hanoi(n-1, src, aux, dist) | process | نقل n-1 قرص من src إلى aux |

#### 📖 الشرح
جمال هذا الحل يكمن في أنه لا يحتاج لأي متغير إضافي يحسب "الترتيب" — فقط بإعادة تعريف الأدوار (من هو المصدر ومن هو المساعد) في كل استدعاء فرعي، تُحل المسألة تلقائياً بأقل عدد ممكن من الحركات.

#### الدرس المستفاد:
> مسألة أبراج هانوي تلخّص فلسفة `Recursion` بأكملها: لا تحاول حل المسألة الكبيرة دفعة واحدة، بل عرّفها بدلالة نسخة أصغر من نفسها (`n-1` قرص) + خطوة واحدة بسيطة (نقل القرص الأكبر)، وثق أن الاستدعاءات الأصغر ستحل نفسها.

#### 🎯 الملخص السريع
- الهدف: نقل `n` قرص من `A` إلى `C` عبر `B`.
- القواعد: قرص واحد بالمرة، فقط القرص العلوي، لا قرص أكبر فوق أصغر.
- الحل العودي: انقل `n-1` جانباً → انقل القرص الكبير → انقل `n-1` للهدف.
- أقل عدد حركات = `2ⁿ - 1`.

#### 📚 التطبيق
مسألة أبراج هانوي مرجع كلاسيكي يظهر لاحقاً في مواد الخوارزميات وتحليل التعقيد الزمني (`time complexity`) لأنها مثال واضح على النمو الأسّي.

### السؤال 5 (hard)


أ) تغيير النوع إلى `int swap(int a, int b)`
ب) تغيير التوقيع إلى `void swap(int &a, int &b)`
ج) إضافة `return temp;` في النهاية

- ❌ **الخيار ج:** `return temp;` تُعيد قيمة واحدة فقط، بينما نحتاج تعديل متغيرين معاً.
- ❌ **الخيار د:** بصيغتها الحالية (`Call by Value`)، الدالة لا تُبدّل شيئاً في `main()` فعلياً.

## الجزء الثالث: بطاقات سؤال وجواب (Q&A Cards)

### البطاقة 1
**Q1:** ما هي الدالة `function` في `C++`؟
**A:** مجموعة تعليمات برمجية لها اسم محدد، تُستدعى لتنفيذ مهمة معينة داخل البرنامج.

### البطاقة 2
**Q2:** ما هي أول دالة تُنفَّذ تلقائياً في أي برنامج `C++`؟
**A:** الدالة `main()`.

### البطاقة 3
**Q3:** ما الفرق بين `Function Prototype` و`Function Definition`؟
**A:** `Prototype` يخبر المترجم بوجود الدالة قبل استخدامها بدون جسم، بينما `Definition` هو تحقيقها وتنفيذها الفعلي الكامل.

### البطاقة 4
**Q4:** متى نحتاج بالضرورة لكتابة `Function Prototype`؟
**A:** عندما تكون الدالة مُعرَّفة ومكتوبة بعد `main()` في الملف.

### البطاقة 5
**Q5:** ما الفرق بين `Parameters` و`Arguments`؟
**A:** `Parameters` متغيرات في تعريف الدالة، أما `Arguments` فهي القيم الفعلية المُمرَّرة عند الاستدعاء.

### البطاقة 6
**Q6:** في `Call by Value`، هل يؤثر التعديل داخل الدالة على المتغير الأصلي؟
**A:** لا، لأنه يتم إرسال نسخة من المتغير فقط.

### البطاقة 7
**Q7:** كيف نجعل الدالة تعدّل المتغير الأصلي فعلياً؟
**A:** باستخدام `Call by Reference`، عبر إضافة الرمز `&` قبل اسم المعامل.

### البطاقة 8
**Q8:** لماذا تحتاج دالة `swap` بالضرورة إلى `Call by Reference`؟
**A:** لأنها يجب أن تُعدِّل قيمتي متغيرين أصليين معاً، وهذا مستحيل مع `Call by Value` الذي يعمل على نسخ فقط.

### البطاقة 9
**Q9:** أين يجب أن تكون المعاملات الافتراضية `Default Arguments` ضمن قائمة معاملات الدالة؟
**A:** يجب أن تكون آخر معاملات ضمن تعريف الدالة.

### البطاقة 10
**Q10:** ما هو `Function Overloading`؟
**A:** وجود عدة دوال بنفس الاسم، تختلف فيما بينها في عدد أو نوع المعاملات.

### البطاقة 11
**Q11:** متى يُنصح باستخدام الكلمة المفتاحية `inline`؟
**A:** فقط مع الدوال الصغيرة، لأن المترجم يستبدل استدعاءها بجسمها مباشرة في كل مكان تُستدعى فيه.

### البطاقة 12
**Q12:** ما الفرق بين `Local Variable` و`Global Variable`؟
**A:** `Local Variable` موجود داخل الدالة فقط ويختفي بعد انتهائها، أما `Global Variable` فهو خارج كل الدوال ويبقى متاحاً طيلة عمر البرنامج.

### البطاقة 13
**Q13:** ما هما الجزآن الإلزاميان في أي دالة عودية `Recursion`؟
**A:** الحالة الأساسية `Base Case` التي توقف الاستدعاء، والحالة العودية `Recursive Case` التي تستدعي الدالة نفسها بقيمة أصغر.

### البطاقة 14
**Q14:** ما الذي يحدث إن نسينا `Base Case` في دالة عودية؟
**A:** يحدث استدعاء لا نهائي يؤدي عادة لخطأ `Stack Overflow`.

### البطاقة 15
**Q15:** لماذا يُعتبر حل `Fibonacci` العودي المباشر غير فعّال للأرقام الكبيرة؟
**A:** لأنه يسبب عدداً كبيراً جداً من الاستدعاءات المكررة لنفس القيم الفرعية.

### البطاقة 16
**Q16:** متى يُفضَّل استخدام `Loop` بدل `Recursion`؟
**A:** عند وجود حل تكراري بسيط، أو عند الحاجة لسرعة تنفيذ وكفاءة أفضل في استخدام الذاكرة.

### البطاقة 17
**Q17:** ما هو الهدف من مسألة أبراج هانوي `Tower of Hanoi` في سياق تعليمي؟
**A:** شرح مفهوم الاستدعاء العودي عملياً عبر مسألة كلاسيكية تتطلب تقسيم المشكلة الكبيرة لنسخ أصغر من نفسها.

### البطاقة 18
**Q18:** ما هي صيغة أقل عدد حركات ممكن لحل أبراج هانوي بعدد `n` من الأقراص؟
**A:** `2ⁿ - 1`.

## الجزء الرابع: ورقة المراجعة السريعة

### 🔑 خريطة التكامل (مختصرة)

| المفهوم | يعتمد على | يُستخدم لاحقاً في |
| --- | --- | --- |
| تعريف الدالة (Return Type/Name/Parameters/Body) | فهم أنواع البيانات (`int`, `float`, إلخ) | كل دالة ستكتبها لاحقاً في المساق |
| Function Prototype | ترتيب قراءة المترجم للكود تسلسلياً | تنظيم الملفات (`.h` / `.cpp`) في مشاريع كبيرة |
| Call by Value / Call by Reference | مفهوم المتغيرات والذاكرة | تمرير المصفوفات والكائنات لاحقاً بكفاءة |
| Recursion (Base Case + Recursive Case) | الجمل الشرطية `if` | خوارزميات البحث والفرز في البنى الشجرية |
| Tower of Hanoi | Recursion + Call by Value | تحليل التعقيد الزمني `time complexity` لاحقاً |

### 🔑 القواعد الذهبية

| # | القاعدة |
| --- | --- |
| 1 | استخدم `Prototype` عند استدعاء دالة قبل أن يراها المترجم مكتوبة بالكامل. |
| 2 | التمرير الافتراضي في `C++` هو `Call by Value`؛ استخدم `&` صراحة عندما تحتاج تعديل المتغير الأصلي. |
| 3 | المعاملات الافتراضية `Default Arguments` تكون دائماً في آخر قائمة المعاملات. |
| 4 | `Function Overloading` يعتمد على اختلاف عدد أو نوع المعاملات، وليس نوع الإرجاع فقط. |
| 5 | كل دالة عودية تحتاج `Base Case` يوقف الاستدعاء + `Recursive Case` يُصغِّر المشكلة تدريجياً. |
| 6 | فضِّل `Loop` عند وجود حل تكراري بسيط، وفضِّل `Recursion` عند وجود بنية تفرّعية طبيعية للمسألة. |

### 🔑 جداول مرجعية سريعة

| المصطلح | التعريف القصير |
| --- | --- |
| `Function` | تعليمات لها اسم محدد تُستدعى لتنفيذ مهمة |
| `Prototype` | تصريح بوجود الدالة قبل استخدامها، بدون جسم |
| `Parameters` | متغيرات شكلية في تعريف الدالة |
| `Arguments` | القيم الفعلية عند الاستدعاء |
| `Call by Value` | إرسال نسخة من المتغير، لا تعديل على الأصلي |
| `Call by Reference` | إرسال عنوان المتغير (`&`)، تعديل فعلي على الأصلي |
| `Default Argument` | قيمة تلقائية للمعامل إن لم يُمرَّر شيء |
| `Overloading` | عدة دوال بنفس الاسم، معاملات مختلفة |
| `Inline` | استبدال استدعاء الدالة بجسمها مباشرة |
| `Scope` | نطاق رؤية المتغير (`Local` أو `Global`) |
| `Recursion` | دالة تستدعي نفسها لحل مسألة أصغر من نفس النوع |
| `Base Case` | الشرط الذي يوقف الاستدعاء العودي |
| `Recursive Case` | الجزء الذي يستدعي الدالة نفسها بقيمة أصغر |

| المعيار | Call by Value | Call by Reference |
| --- | --- | --- |
| ماذا يُرسَل؟ | نسخة من المتغير | عنوان المتغير (`&`) |
| هل يؤثر على الأصلي؟ | لا | نعم |
| مثال شائع | `sum(int a, int b)` | `swap(int &a, int &b)` |

| المعيار | Recursion | Loop |
| --- | --- | --- |
| استهلاك الذاكرة | أكبر (بنية Stack) | أقل |
| السرعة | أبطأ نسبياً | أسرع |
| الأنسب لـ | مسائل تفرّعية (أشجار) | حل تكراري مباشر وبسيط |
