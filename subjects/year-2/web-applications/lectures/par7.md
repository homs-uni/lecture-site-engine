# المحاضرة 7 — Introduction to Git (مقدمة إلى Git)
> **المادة:** تطوير تطبيقات الويب (القسم العملي) | **الموضوع:** إدارة الإصدارات باستخدام `Git` — من الإعداد الأولي إلى أنماط التعاون في المشاريع الكبيرة

## الجزء الأول: ملخص منظم (اقرأ قبل المحاضرة!)

### 📍 عن هذه المحاضرة
> هذه المحاضرة تشرح `Git` كنظام لإدارة إصدارات الكود (`version control system`) — من أول أمر تكتبه بعد تثبيت `Git` إلى أنماط العمل الجماعي المستخدمة في مشاريع ضخمة مثل Linux Kernel.

### 🎯 ستتعلم
- كيف تُعِدّ هويتك في `Git` وتبدأ أول repository
- دورة العمل اليومية: `add` → `status` → `commit`
- كيف تنشئ فروعاً (`branches`) وتدمجها وتحل تعارضاتها
- كيف تتعاون مع فريق عبر `clone` و`push` و`pull` و`fetch`
- أدوات استكشاف التاريخ: `log`، `show`، `tag`، `diff`، `grep`، وحتى التراجع عبر `reset`
- الفرق بين أنماط التعاون الثلاثة: Subversion-Style، Integration Manager، Dictator and Lieutenants

### 📚 المتطلبات السابقة
- **أساسيات استخدام Terminal / Command Line** — لأن كل أوامر `Git` تُكتب في الطرفية، وبدون فهم أساسي لكيفية تنقّلك بين المجلدات (`cd`) وتنفيذ أوامر، ستشعر بالضياع
- لا يوجد اعتماد مباشر على HTML/CSS/JavaScript في هذه المحاضرة تحديداً، لكنها بنية تحتية ستحتاجها في كل محاضرات المشروع القادمة (مثل بناء REST API أو تطبيق React) — فكل مشروع سنبنيه سيُدار عبر `Git`

### 💡 الأفكار الرئيسية

خلّك تتخيل السيناريو التالي: أنت تكتب كوداً لمشروعك، وبعد ساعتين تكتشف إن الفكرة اللي طبّقتها غلط، وودّك ترجع للنسخة اللي كانت شغالة قبل ساعة. لو ما عندك أداة تتبع، حل وحيد هو إنك تتذكر يدوياً كل شيء غيّرته وتلغيه — وهذا شبه مستحيل في مشروع حقيقي. هذي بالضبط المشكلة اللي يحلّها `Git`: نظام يسجّل "لقطة" (`snapshot`) لمشروعك كل ما تطلب منه ذلك، وتقدر ترجع لأي لقطة قديمة وقتما تحتاج.

قبل ما تبدأ تستخدم `Git` فعلياً، لازم تعرّفه بنفسك: مين أنت؟ هذا يصير عبر `git config --global user.name` و`git config --global user.email`، والكلمة `--global` معناها إن هذا الإعداد بينطبق على كل مشاريعك في هذا الجهاز، مو مشروع وحيد بس. بعدها، تحوّل أي مجلد إلى مشروع مُدار بـ `Git` عبر أمر واحد: `git init`، اللي ينشئ مجلد مخفي اسمه `.git` يخزّن فيه كل تاريخ مشروعك.

الفكرة الجوهرية اللي لازم تفهمها بعمق هي إن `Git` **يتتبع المحتوى، لا الملفات نفسها**. يعني لما تعيد تسمية ملف، `Git` ما يشوفها "عملية إعادة تسمية" بشكل مباشر — هو بس يقارن المحتوى القديم بالجديد ويكتشف التشابه. هذا التفصيل يوضّح ليش `Git` قوي جداً في اكتشاف التغييرات، حتى لو نقلت كود من ملف لملف.

دورة العمل اليومية في `Git` تمر بثلاث مناطق: **working directory** (الملفات اللي تشتغل عليها فعلياً)، **staging area / index** (منطقة وسيطة تجهّز فيها التغييرات قبل حفظها)، و**repository** (التاريخ المحفوظ نهائياً). لما تعدّل ملف، التعديل يصير أول شي في working directory. تستخدم `git add file1 file2` عشان تنقل هالتعديلات إلى الـ staging area — يعني تقول لـ`Git`: "هذي التغييرات جاهزة أخذها بعين الاعتبار في اللقطة الجاية". قبل ما تثبّت أي شي، تقدر تتأكد وش بالضبط رح يتحفظ عبر `git diff --cached` (يعرض الفرق بين آخر commit والـ staging area)، أو `git diff` بدون `--cached` (يعرض التغييرات اللي ما زالت في working directory ولم تُضاف بعد). و`git status` يعطيك ملخص سريع لكل شي: أي ملفات معدّلة، أي منها staged، وأيها لسه ما لمسته.

لما تكون التغييرات جاهزة، تستخدم `git commit` لتثبيتها بشكل دائم في تاريخ المشروع — وهذا يفتح لك محرر نص تكتب فيه رسالة توضّح وش سويت. القاعدة الذهبية لرسائل الـ commit الجيدة: سطر أول قصير (أقل من 50 حرف) يلخّص التغيير، سطر فاضي، ثم وصف تفصيلي إذا احتجت. مثلاً "Fix login bug" كعنوان، وبعدها فقرة تشرح إنك أصلحت مشكلة انتهاء الجلسة وأضفت دعم refresh token. اختصار مفيد: `git commit -a` يدمج خطوتي `add` و`commit` في أمر واحد — لكن انتبه، هذا يشتغل بس على الملفات اللي `Git` يعرفها مسبقاً (يعني معدّلة أو محذوفة)، ما يضيف ملفات جديدة كلياً.

بعض الملفات ما ودّك `Git` يتتبعها إطلاقاً — زي ملفات `.env` اللي فيها أسرار، أو `node_modules/` اللي حجمها ضخم وقابلة لإعادة التوليد. هنا يجي دور `.gitignore`: ملف نصي تكتب فيه أنماط (`patterns`) زي `*.log` أو `node_modules/`، و`Git` يتجاهل أي ملف يطابقها تلقائياً.

كل تاريخ مشروعك تقدر تستعرضه عبر `git log`، اللي يعرض كل commit مع الـ hash الخاص فيه (معرّف فريد)، اسم المؤلف، التاريخ، ورسالة الـ commit — مرتبة من الأحدث للأقدم.

> 🎯 **جملة الامتحان:** `Git` يتتبع **محتوى** الملفات وليس أسماءها، ودورة العمل الأساسية تمر عبر ثلاث مناطق: `working directory` → `staging area (index)` → `repository`.

---

الفكرة الثانية الكبيرة في هذي المحاضرة هي **الفروع (Branches)**. فكّر في الفرع كخط زمني مستقل: تقدر تجرّب فكرة جديدة بدون ما تخرّب النسخة المستقرة (`main`). تنشئ فرع باسم مثلاً `experimental` عبر `git branch experimental`، وتشوف كل الفروع الموجودة عبر `git branch` بدون معاملات (والفرع الحالي يظهر عليه علامة `*`). للتنقل بين الفروع تستخدم `git switch experimental`، أو الطريقة الأقدم والأشمل `git checkout experimental`. واختصار عملي جداً: `git checkout -b experimental` ينشئ الفرع وينتقل إليه في أمر واحد.

لما تخلّص شغلك على الفرع التجريبي وتتأكد إنه شغال، تدمجه رجوع في `main`: أول شي `git checkout main` عشان ترجع للفرع الرئيسي، ثم `git merge experimental` عشان تدمج التغييرات. الناتج المتوقع شي زي `2 files changed, 2 insertions(+), 1 deletion(-)` — يعني `Git` يخبرك بالضبط كم ملف تأثر وكم سطر أُضيف أو حُذف.

أحياناً، لو فرعين عدّلوا نفس الجزء بالضبط من نفس الملف، `Git` ما يقدر يقرر تلقائياً أي نسخة تاخذ — وهذا يُسمى **merge conflict**. `Git` يعلّم مكان التعارض داخل الملف نفسه، وعليك تفتحه يدوياً، تقرر أي جزء تبقيه (أو تدمج الاثنين)، ثم تستخدم `git add <file>` لتأكيد إن التعارض انحل، وأخيراً `git commit` لإنهاء عملية الدمج.

وبعد ما تخلّص من فرع مو محتاجه، تحذفه: `git branch -d experimental` يحذفه بأمان (يرفض الحذف إذا فيه تغييرات غير مدموجة)، بينما `git branch -D` (حرف كبير) يفرض الحذف حتى لو فيه تغييرات ضايعة — استخدمها بحذر.

> 🎯 **جملة الامتحان:** إنشاء فرع جديد والانتقال إليه في خطوة واحدة يتم عبر `git checkout -b <branch-name>`، والدمج يتطلب الانتقال أولاً للفرع الهدف ثم تنفيذ `git merge <source-branch>`.

---

الفكرة الثالثة هي **التعاون (Collaboration)**، وهنا `Git` يُظهر طبيعته "الموزّعة" الحقيقية. لو باب (Bob) يبي يشتغل على مشروع أليس (Alice)، هو أول شي يعمل `git clone 'url_to_alice_repo' myrepo` — وهذا ما ينسخ بس الملفات الحالية، بل ينسخ **كامل تاريخ المشروع** بكل الـ commits. بعد ما يسوي تعديلاته ويثبّتها بـ `git commit -a`، يرفعها للسيرفر المشترك عبر `git push origin main`. من الجهة الثانية، أليس تسحب تعديلات باب عبر `git pull 'url_to_bob_repo' main`.

قبل ما تدمج تعديلات شخص ثاني بشكل أعمى، تقدر تراجعها أول: `git fetch https://github.com/bob/repo.git main` يجيب التعديلات بدون ما يدمجها تلقائياً، ثم `git log -p HEAD..FETCH_HEAD` يعرض لك بالضبط وش تغيّر قبل ما تقرر. ولأن كتابة الروابط الكاملة في كل مرة متعب، تقدر تعرّف اختصاراً دائماً: `git remote add bob https://github.com/bob/repo.git`، وبعدها بس تكتب `git fetch bob`.

الفرق الجوهري بين `fetch` و`pull`: **`pull` = `fetch` + `merge`**. يعني `fetch` بس يجيب التغييرات ويخزّنها محلياً بدون لمس فرعك الحالي، بينما `pull` يجيب التغييرات **ويدمجها فوراً** في فرعك الحالي. هذا فرق حرج يظهر كثير في الأسئلة.

> 🎯 **جملة الامتحان:** `git pull` هو اختصار لعمليتين متتاليتين: `git fetch` (جلب التغييرات) ثم `git merge` (دمجها في الفرع الحالي).

---

الفكرة الرابعة هي **أدوات استكشاف التاريخ المتقدمة**. `git show HEAD` يعرض تفاصيل آخر commit، و`HEAD^` يشير لأب هذا الـ commit (اللي قبله مباشرة)، و`HEAD~4` يشير للـ commit اللي قبل 4 خطوات. هذي الرموز (`^` و`~`) طريقة `Git` للتنقل في شجرة الأسلاف بدون ما تحتاج تكتب الـ hash الطويل كل مرة.

تقدر كمان تضع علامة (`tag`) على commit مهم — زي إصدار (`release`) — عبر `git tag v2.5 1b2e1d63ff`، وتقارن بين نسختين عبر `git diff v2.5 HEAD`، أو تنشئ فرع مستقر يبدأ من تلك العلامة بالضبط عبر `git branch stable v2.5`.

أداة قوية لكن خطيرة هي `git reset --hard HEAD^`: هذي تعيد `HEAD` (المؤشر لموقعك الحالي) إلى الـ commit السابق **وتحذف كل شي بعده نهائياً** — بلا رجعة سهلة. لازم تستخدمها بحذر شديد لأنها **تدمّر التاريخ** بعد النقطة اللي رجعت لها.

للبحث عن نص معيّن داخل كل ملفات المشروع (حتى في نسخة قديمة)، تستخدم `git grep "hello" v2.5` — يبحث عن الكلمة "hello" داخل نسخة `v2.5` تحديداً. ولمقارنة نسخة معينة من ملف واحد بس، تستخدم `git diff v2.5:Makefile HEAD:Makefile.in` أو `git show v2.5:Makefile` لعرض محتوى الملف كما كان وقتها. وأخيراً، `gitk` أداة رسومية (`GUI`) تعرض لك شجرة الفروع والدمج بشكل بصري — مفيدة جداً لما يصير عندك تاريخ معقّد وصعب تتخيله من النص بس.

> ⚠️ **مهم:** `git reset --hard` يحذف التغييرات نهائياً — تأكد قبل تنفيذه إنك ما تحتاج شي بعد النقطة اللي رح ترجع لها.

---

الفكرة الأخيرة والمهمة جداً هي إن **`Git` نظام موزّع (Distributed)** بطبيعته. كل مستخدم يعمل `clone` يحصل على **نسخة كاملة** من المشروع بكل تاريخه — مو بس آخر نسخة. هذا معناه لو السيرفر المركزي طاح أو انهار، أي نسخة عند أي مطوّر تقدر تسترجع المشروع كامل. ما فيه نقطة فشل وحيدة (`single point of failure`) إلا إذا كانت نسخة واحدة بس موجودة أصلاً. هذي الطبيعة الموزّعة تفتح الباب لأنماط تعاون متعددة، مو نمط واحد إجباري:

**نمط Subversion-Style (المركزي):** كل المطورين يرفعون (`push`) مباشرة لنفس السيرفر المشترك، و`Git` يفرض التزامن — يعني ما تقدر تعمل `push` إلا إذا كنت قد جلبت (`fetch`) آخر التغييرات أول. هذا أبسط نمط ويشبه أنظمة إدارة الإصدارات القديمة زي Subversion.

**نمط Integration Manager (شائع في المشاريع مفتوحة المصدر):** فيه "repository مبارَك" (`blessed repository`) واحد رسمي، وكل مطوّر يعمل `clone` منه وياخذ نسخته الخاصة، يشتغل عليها، ثم يطلب من شخص معيّن (الـ **Integrator**) يسحب (`pull`) تعديلاته إلى الـ repository الرسمي. هذا أشبه بآلية الـ Pull Request المعروفة اليوم في GitHub.

**نمط Dictator and Lieutenants (للمشاريع الضخمة جداً، زي Linux Kernel):** طبقات متعددة — كل **لوتننت (Lieutenant)** يدير subsystem معين (جزء محدد من المشروع)، **الدكتاتور (Dictator)** يسحب من اللوتننتات، وبعدين يحدّث الـ repository المبارك اللي الكل ينسخ منه. هذا النمط يسمح بتنظيم عمل آلاف المطورين بدون فوضى.

> 🎯 **جملة الامتحان:** الفرق الجوهري بين الأنماط الثلاثة هو **من يملك صلاحية الكتابة المباشرة على الـ repository الرسمي**: الكل في Subversion-Style، شخص واحد (Integrator) في Integration Manager، وطبقات هرمية (Lieutenants ثم Dictator) في Dictator and Lieutenants.

### الأخطاء اللي الناس دايماً تقع فيها

#### الفهم الخاطئ ❌:
كثير من المبتدئين يعتقدون إن `git commit -a` تساوي "احفظ كل شي في المشروع"، فيتفاجؤون إن ملف جديد أنشأوه ما انحفظ في الـ commit.

#### الفهم الصحيح ✅:
`git commit -a` تدمج بس الملفات اللي `Git` **يعرفها مسبقاً** (تراقبها فعلاً) وتم تعديلها أو حذفها. أما الملفات الجديدة كلياً (`untracked files`) فلازم تضيفها يدوياً مرة وحدة عبر `git add` قبل ما `-a` تشتغل عليها في المرات القادمة.

#### 💻 الأمر: `git help log`

| العنصر | التفصيل |
| --- | --- |
| **متى تستخدمه** | لما تنسى صياغة أمر معيّن أو تبي تعرف كل خياراته |
| **الصيغة الكاملة** | `git help <command>` أو `man git-<command>` |
| **الناتج المتوقع** | يفتح صفحة توثيق كاملة عن الأمر المطلوب |
| **تحذير شائع** | الطلاب ينسون إن `git help` يفتح متصفح أو viewer، بينما `man` يفتح في نفس الطرفية |

```bash
$ man git-log
$ git help log
```

#### شرح كل سطر:
1. `man git-log` → يعرض صفحة الدليل (`manual page`) الخاصة بأمر `log` مباشرة في الطرفية
2. `git help log` → تقوم بنفس الوظيفة لكن تسمح باستخدام أي `viewer` (عارض) تفضّله، مو بس الطرفية

#### 📖 الشرح
الأمران يوصلان لنفس المعلومة لكن بطريقة عرض مختلفة. `man` هو نظام التوثيق التقليدي في أنظمة Unix/Linux، بينما `git help` هو غلاف (`wrapper`) خاص بـ`Git` يعطيك مرونة أكثر في كيفية عرض المحتوى.

#### 💡 التشبيه:
> فكّر فيها زي فرق بين قراءة كتيّب تعليمات ورقي (`man`) وفتح نفس المحتوى في تطبيق قارئ إلكتروني (`git help`) — نفس المعلومة، أدوات عرض مختلفة.
> **وجه الشبه:** الكتيّب الورقي = `man`، القارئ الإلكتروني المرن = `git help`.

#### 🎯 الملخص السريع
- `man git-<command>` يفتح صفحة الدليل مباشرة
- `git help <command>` يفتح نفس المحتوى بمرونة أكبر في اختيار العارض
- الاثنان يعطيان نفس المعلومة بالضبط

> 🎯 **جملة الامتحان:** `git help <command>` و`man git-<command>` يعرضان نفس معلومات التوثيق لكن بطريقة عرض مختلفة.

#### 📚 التطبيق
ستستخدم هذا الأمر كل ما تواجه أمر `Git` جديد ما تتذكر خياراته بالضبط.

#### 1.2. إعداد هويتك في Git

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_1.1"} -->

#### 📍 أين نحن الآن؟
قبل أي `commit`، `Git` لازم يعرف اسمك وإيميلك عشان يسجّلهم مع كل تعديل تسويه.

#### ⬅️ الربط مع السابق
بعد ما تعلمنا كيف نطلب مساعدة `Git`، أول أمر فعلي نسويه هو تعريف هويتنا له.

#### 💡 الفكرة الأساسية
**`git config --global` يخزّن اسمك وإيميلك بشكل دائم لكل مشاريعك على هذا الجهاز.**

---

#### 💻 الكود

```bash
$ git config --global user.name "Your Name"
$ git config --global user.email "you@yourdomain.example.com"
```

#### شرح كل سطر:
1. `git config` → الأمر المسؤول عن ضبط إعدادات `Git`
2. `--global` → يطبّق الإعداد على كل الـ repositories في جهازك، مو مشروع وحيد
3. `user.name "..."` → القيمة اللي ستظهر كاسم المؤلف (`Author`) في كل `commit`
4. `user.email "..."` → الإيميل المرتبط بهويتك، يُستخدم أيضاً لربط حسابك في منصات زي GitHub

#### 📖 الشرح
كل `commit` في `Git` يحمل توقيعاً يحدد "مين سوّى هذا التغيير". لو ما ضبطت هذا الإعداد، `Git` غالباً يرفض إتمام أول `commit` أو يستخدم قيم افتراضية غير دقيقة من نظام التشغيل. `--global` يعني الإعداد يُكتب في ملف إعدادات عام (`~/.gitconfig`) يُقرأ تلقائياً من أي مشروع تفتحه — بعكس الإعداد بدون `--global` اللي يطبّق على مشروع واحد بس.

#### 💡 التشبيه:
> فكّرها زي كتابة اسمك على أول صفحة من كل دفتر ملاحظات تشتريه — مرة وحدة تسجّله في "إعدادات جهازك"، وبعدين كل دفتر (مشروع) جديد يعرف صاحبه تلقائياً.
> **وجه الشبه:** اسمك المكتوب على الدفاتر = `user.name` و`user.email` في `--global config`.

#### 🎯 الملخص السريع
- `--global` = ينطبق على كل المشاريع في الجهاز
- بدون `--global` = ينطبق على المشروع الحالي فقط
- الاسم والإيميل يظهران في كل `commit` تسويه

> 🎯 **جملة الامتحان:** `git config --global` يضبط إعداداً يسري على كل repositories المستخدم في الجهاز، بينما نفس الأمر بدون `--global` يقتصر على repository الحالي فقط.

#### 📚 التطبيق
هذا أول أمر تكتبه بعد تثبيت `Git` على أي جهاز جديد — قبل ما تبدأ أي مشروع.

#### ⚠️ أخطاء شائعة

#### الفهم الخاطئ ❌:
بعض الطلاب يظنون إنهم لازم يعيدوا هذا الإعداد في كل مشروع جديد.

#### الفهم الصحيح ✅:
بفضل `--global`، تسويه **مرة وحدة بس** على الجهاز، وكل مشروع جديد تنشئه بعدها يرث نفس الإعداد تلقائياً — إلا إذا احتجت إيميل مختلف لمشروع معيّن، فحينها تضبطه محلياً بدون `--global` داخل ذلك المشروع تحديداً.

#### 1.3. استيراد مشروع جديد إلى Git

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_1.2"} -->

#### 📍 أين نحن الآن؟
بعد ضبط هويتك، أول خطوة عملية هي تحويل مجلد عادي إلى `repository` يتتبعه `Git`.

#### ⬅️ الربط مع السابق
استخدمنا `git config` لتعريف هويتنا؛ الآن نستخدم أول أمر يهيّئ مشروعاً فعلياً تحت إدارة `Git`.

#### 💡 الفكرة الأساسية
**`git init` يحوّل أي مجلد إلى repository جديد فارغ عبر إنشاء مجلد مخفي `.git` بداخله.**

---

#### 💻 الكود

```bash
$ tar xzf project.tar.gz
$ cd project
$ git init
Initialized empty Git repository in .git/
```

#### شرح كل سطر:
1. `tar xzf project.tar.gz` → فك ضغط أرشيف المشروع (`tar` = أداة ضغط في Linux، `xzf` = extract + gzip + file)
2. `cd project` → الدخول إلى مجلد المشروع
3. `git init` → تهيئة repository فارغ جديد داخل هذا المجلد
4. `Initialized empty Git repository in .git/` → رسالة التأكيد؛ `.git/` هو المجلد المخفي اللي يخزّن فيه `Git` كل شي: التاريخ، الفروع، الإعدادات

#### 📖 الشرح
`git init` ما يلمس ملفاتك الموجودة إطلاقاً — هو بس يضيف طبقة تتبّع فوقها عبر مجلد `.git` الخفي. من هذي اللحظة، أي ملف في المجلد يصير "مرشّح" لأن يُتتبع، لكنه لن يُحفظ فعلياً في التاريخ إلا لما تعمل `add` ثم `commit` له لاحقاً.

#### 💡 التشبيه:
> فكّرها زي إنك تحط كاميرا مراقبة جديدة في غرفة موجودة أصلاً بأثاثها — الكاميرا (`git init`) ما تغيّر شي في الغرفة، بس تبدأ تسجّل أي تغيير يصير فيها من الآن فصاعداً.
> **وجه الشبه:** الغرفة الموجودة = ملفات مشروعك، الكاميرا الجديدة = `.git/` بعد `git init`.

#### 🎯 الملخص السريع
- `git init` يُنفَّذ مرة وحدة فقط في بداية المشروع
- ينشئ مجلد `.git/` المخفي الذي يخزّن كل التاريخ
- لا يحفظ أي ملف تلقائياً — لازم `add` و`commit` بعده

> 🎯 **جملة الامتحان:** `git init` ينشئ repository فارغاً جديداً عبر إضافة مجلد `.git/` المخفي، دون التأثير على الملفات الموجودة في المجلد.

#### 📚 التطبيق
كل مشروع تبدأه من الصفر — سواء تطبيق React أو خادم Express — يبدأ بـ `git init` (أو `git clone` إذا كان المشروع موجوداً مسبقاً على سيرفر).

#### 🤔 تفعيل الفهم (اسأل نفسك):
> **سؤال:** إذا نفّذت `git init` داخل مجلد فيه ملفات موجودة من قبل، هل تُحفظ هذي الملفات تلقائياً في أول commit؟
> **لماذا هذا مهم؟** لأنه يوضّح إن `git init` مجرد تهيئة، وليس حفظاً فعلياً — الحفظ يحتاج `add` و`commit` بشكل منفصل ومقصود.

#### 2.1. إجراء التغييرات ومراجعتها (add و diff)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_1.3"} -->

#### 📍 أين نحن الآن؟
بعد تهيئة المشروع، نتعلم كيف نجهّز التعديلات لتصير جزءاً من التاريخ.

#### ⬅️ الربط مع السابق
بعد `git init` صار عندنا repository فارغ؛ الآن نبدأ نعدّل ملفات ونجهّزها للحفظ.

#### 💡 الفكرة الأساسية
**`git add` ينقل التعديلات من working directory إلى staging area، و`git diff` يعرض لك بالضبط وش تغيّر قبل ما تثبّته.**

---

#### 💻 الكود

```bash
$ git add file1 file2 file3
$ git diff --cached
$ git diff
```

#### شرح كل سطر:
1. `git add file1 file2 file3` → يضيف نسخة "التعديلات الحالية" لهذي الملفات الثلاثة إلى الـ staging area (index)
2. `git diff --cached` → يعرض الفرق بين آخر commit والملفات الموجودة في الـ staging area (يعني وش رح يتحفظ فعلياً لو سويت commit الآن)
3. `git diff` (بدون `--cached`) → يعرض التغييرات اللي سويتها لكن **لسه ما أضفتها** بـ `add`

#### 📖 الشرح
هذي أهم نقطة تفهمها في `Git`: فيه **منطقتان مختلفتان** للتغييرات قبل الحفظ النهائي. `git diff` يريك التغييرات "الخام" في working directory، بينما `git diff --cached` يريك بس اللي وضعته في staging area عبر `add`. هذا الفصل يعطيك تحكم دقيق — تقدر تضيف بس جزء من تعديلاتك للـ commit القادم، وتترك الباقي لوقت لاحق.

#### 💡 التشبيه:
> فكّرها زي عربة تسوق: `working directory` هو الرف اللي فيه كل المنتجات، `git add` هو وضع منتج معيّن داخل العربة (staging)، و`git diff --cached` هو مراجعة وش داخل عربتك فعلاً قبل ما تروح للكاشير (`commit`).
> **وجه الشبه:** العربة = staging area، الكاشير = عملية `commit`.

#### 🎯 الملخص السريع
- `git add` ينقل تعديلات لمنطقة staging مؤقتة
- `git diff` = تغييرات غير مضافة بعد
- `git diff --cached` = تغييرات مضافة وجاهزة للـ commit

> 🎯 **جملة الامتحان:** `git diff` يعرض التغييرات غير المُضافة (unstaged)، بينما `git diff --cached` يعرض التغييرات المُضافة والجاهزة للتثبيت (staged).

#### 📚 التطبيق
ستستخدم هذي الدورة (`add` ثم `diff --cached` للمراجعة) قبل كل commit تقريباً، خصوصاً في مشاريع الفريق حيث الدقة مهمة.

#### ⚠️ أخطاء شائعة

#### الفهم الخاطئ ❌:
كثير يظنون `git diff` يعرض كل شي تغيّر بغض النظر عن حالته.

#### الفهم الصحيح ✅:
`git diff` بمفردها تتجاهل أي شي أضفته بـ `add` بالفعل — إذا أضفت ملف كامل وعدّلته مرة ثانية، بس التعديل الثاني (غير المضاف) يظهر في `git diff` العادي.

#### 2.2. فحص حالة المشروع (git status)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_2.1"} -->

#### 📍 أين نحن الآن؟
بدل ما تفحص كل ملف على حدة بـ `diff`، فيه أمر يعطيك ملخص شامل بنظرة وحدة.

#### ⬅️ الربط مع السابق
بعد ما استخدمنا `add` و`diff`، `git status` يجمع لك الصورة الكاملة في مكان واحد.

#### 💡 الفكرة الأساسية
**`git status` يعرض ملخصاً واضحاً لكل الملفات المعدّلة وحالتها (staged أو غير staged).**

---

#### 💻 الكود

```bash
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
	modified: file1
	modified: file2
	modified: file3
```

#### شرح كل سطر:
1. `git status` → الأمر المسؤول عن عرض الحالة الحالية للمشروع
2. `On branch main` → يخبرك أي فرع أنت عليه حالياً
3. `Changes to be committed:` → قائمة الملفات المضافة (staged) والجاهزة للـ commit القادم
4. `modified: file1/file2/file3` → قائمة الملفات المتأثرة تحديداً

#### 📖 الشرح
`git status` هو الأمر اللي رح تكتبه أكثر من أي أمر ثاني في `Git` — يعطيك نظرة سريعة قبل أي قرار (هل أضيف ملف؟ هل أثبّت الآن؟). لاحظ إنه حتى يقترح عليك الأمر المناسب لإلغاء الإضافة (`git restore --staged`) إذا غيّرت رأيك.

#### 💡 التشبيه:
> فكّرها زي لوحة تحكم في السيارة تعرض لك كل المؤشرات دفعة وحدة (وقود، حرارة، سرعة) بدل ما تفحص كل نظام لحاله.
> **وجه الشبه:** لوحة التحكم = `git status`، المؤشرات المنفردة = `git diff` لكل ملف.

#### 🎯 الملخص السريع
- يعرض الفرع الحالي
- يعرض الملفات staged (جاهزة للـ commit)
- يعرض الملفات المعدّلة وغير المضافة، والملفات الجديدة غير المتتبعة

> 🎯 **جملة الامتحان:** `git status` يعطي ملخصاً فورياً لحالة working directory وstaging area، بما في ذلك اسم الفرع الحالي.

#### 📚 التطبيق
عادة صحية: نفّذ `git status` قبل كل `commit` للتأكد إنك تضيف بالضبط الملفات اللي تبيها.

#### 2.3. تثبيت التغييرات (Commit)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_2.2"} -->

#### 📍 أين نحن الآن؟
بعد ما راجعنا التغييرات، الخطوة الأخيرة هي حفظها بشكل دائم في تاريخ المشروع.

#### ⬅️ الربط مع السابق
استخدمنا `add` لتجهيز التغييرات و`status` لمراجعتها؛ الآن `commit` يحفظها فعلياً.

#### 💡 الفكرة الأساسية
**`git commit` يسجّل لقطة دائمة من الملفات الموجودة حالياً في الـ staging area.**

---

#### 💻 الكود

```bash
$ git commit
$ git commit -a
```

#### شرح كل سطر:
1. `git commit` → يفتح محرر نص لكتابة رسالة تصف التغيير، ثم يسجّل لقطة جديدة تحتوي فقط على ما كان في staging area
2. `git commit -a` → يدمج خطوتي `add` و`commit` تلقائياً، لكن فقط للملفات المتتبَعة مسبقاً (معدّلة أو محذوفة، وليس ملفات جديدة كلياً)

#### 📖 الشرح
`git commit` هو اللحظة اللي فيها تعديلاتك تصير "دائمة" في تاريخ المشروع — تقدر ترجع لها لاحقاً بأي وقت. الفرق بين `commit` و`commit -a` مهم جداً: الأول يحتاج `add` سابق، والثاني اختصار لكنه محدود بالملفات المعروفة سلفاً لـ`Git`.

#### 💡 التشبيه:
> فكّرها زي التقاط صورة (`photo snapshot`) للمشروع في لحظة معيّنة — الصورة تُحفظ للأبد وتقدر ترجع لها، حتى لو المشروع تغيّر كثير بعدها.
> **وجه الشبه:** لحظة التقاط الصورة = `git commit`، ألبوم الصور = تاريخ المشروع كامل.

#### 🎯 الملخص السريع
- `git commit` يحفظ فقط ما تم `add`-ه مسبقاً
- `git commit -a` يضيف تلقائياً الملفات المعروفة (لا الجديدة) ثم يحفظ
- كل commit يحمل رسالة توضيحية

> 🎯 **جملة الامتحان:** `git commit -a` يدمج `add` و`commit` تلقائياً، لكن فقط للملفات المتتبَعة مسبقاً — لا يشمل الملفات الجديدة غير المتتبَعة (`untracked`).

#### 📚 التطبيق
هذي دورة العمل الأساسية اللي ستكررها عشرات المرات يومياً في أي مشروع برمجي.

#### ⚠️ أخطاء شائعة

#### الفهم الخاطئ ❌:
طالب أنشأ ملف جديد، عدّله، ثم استخدم `git commit -a` متوقعاً إن الملف الجديد بيتحفظ.

#### الفهم الصحيح ✅:
الملف الجديد لازم يمر بـ `git add` مرة وحدة أول (عشان يصير "معروفاً" لـ`Git`)؛ بعدها فقط `commit -a` تقدر تدمج تعديلاته المستقبلية تلقائياً.

#### 2.4. كتابة رسائل Commit جيدة

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_2.3"} -->

#### 📍 أين نحن الآن؟
مهارة يبدو تفصيلها بسيط لكنها تحدد جودة تاريخ مشروعك بالكامل على المدى الطويل.

#### ⬅️ الربط مع السابق
بعد ما تعلمنا `commit`، نتعلم الآن كيف نكتب رسالته بشكل احترافي.

#### 💡 الفكرة الأساسية
**رسالة الـ commit الجيدة تتكون من عنوان قصير (≤50 حرف)، سطر فاضي، ثم وصف تفصيلي.**

---

#### 💻 الكود

```text
Fix login bug

Fixed session timeout issue causing user logout.
Added refresh token support.
```

#### شرح كل سطر:
1. `Fix login bug` → العنوان: جملة فعل قصيرة تلخّص "وش تغيّر" بصيغة واضحة ومباشرة
2. (سطر فارغ) → يفصل بين العنوان والتفاصيل — هذا الفصل يسمح لأدوات `Git` (زي `git log --oneline`) بعرض العنوان فقط عند الحاجة
3. `Fixed session timeout...` و`Added refresh token support.` → تفاصيل إضافية توضح "ليش" و"كيف" تم التغيير

#### 📖 الشرح
تاريخ المشروع (`git log`) هو أهم مصدر توثيق لمشروعك — أهم حتى من التعليقات داخل الكود أحياناً، لأنه يوضّح **لماذا** تم تغيير معيّن وليس بس "ماذا" تغيّر. رسالة غامضة زي "fix stuff" ما تفيد أحد بعد 6 أشهر، بينما رسالة واضحة توفر وقت فريقك بالكامل.

#### 💡 التشبيه:
> فكّرها زي عنوان صحيفة (`headline`) يليه المقال الكامل — العنوان يعطيك الفكرة بسرعة، والمقال يشرح التفاصيل لمن يحتاجها.
> **وجه الشبه:** العنوان القصير = السطر الأول من رسالة الـ commit، المقال = الوصف التفصيلي تحته.

#### 🎯 الملخص السريع
- العنوان ≤ 50 حرف، فعل واضح
- سطر فاضي إلزامي بين العنوان والتفاصيل
- التفاصيل تشرح "لماذا" لا "ماذا" بس

> 🎯 **جملة الامتحان:** رسالة الـ commit الجيدة تتكون من عنوان قصير (٥٠ حرفاً أو أقل)، يليه سطر فارغ، ثم وصف تفصيلي اختياري.

#### 📚 التطبيق
كل مشروع فريق حقيقي (مفتوح المصدر أو شركة) يفرض هذا النمط، وأدوات زي `git log --oneline` تعتمد على وجود عنوان قصير مفصول.

#### 2.5. تتبع المحتوى لا الملفات، وتجاهل الملفات (.gitignore)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_2.4"} -->

#### 📍 أين نحن الآن؟
فكرتان مهمتان مرتبطتان بطبيعة تتبّع `Git`: كيف يفكر داخلياً، وكيف تستثني ملفات من تتبّعه أصلاً.

#### ⬅️ الربط مع السابق
بعد ما عرفنا كيف نحفظ تغييرات، نفهم الآن **كيف** `Git` يرى هذي التغييرات من الداخل.

#### 💡 الفكرة الأساسية
**`Git` يتتبع محتوى الملفات وليس أسماءها، و`.gitignore` يستثني ملفات معيّنة من التتبّع بالكامل.**

---

#### 💻 الكود

```text
# Example .gitignore
*.log
node_modules/
.env
```

#### شرح كل سطر:
1. `*.log` → نمط (`pattern`) يستثني أي ملف ينتهي بـ `.log` بغض النظر عن اسمه
2. `node_modules/` → يستثني مجلد كامل (الشرطة المائلة `/` تحدد إنه مجلد لا ملف)
3. `.env` → يستثني ملف محدد بالاسم (عادة يحتوي أسرار زي مفاتيح API)

#### 📖 الشرح
النقطة الأولى — "Git يتتبع المحتوى لا الملفات" — تعني إن `git add` تسجّل **محتوى** الملف، مو "اسم الملف" ككيان ثابت. فلو غيّرت اسم ملف، `Git` ما عنده أمر "rename" مباشر يسجّله كحدث — هو بس يقارن المحتوى القديم بالجديد في المرة القادمة ويكتشف التشابه تلقائياً (heuristic detection). هذا يفسر ليش `Git` سريع وذكي في تتبع الكود حتى لو انتقل بين ملفات.

أما `.gitignore`، فهو حل لمشكلة عملية: مو كل ملف في مشروعك تبي تحفظه في التاريخ. ملفات `.env` فيها أسرار حساسة ما ينبغي ترفع لسيرفر مشترك، و`node_modules/` مجلد ضخم يُعاد توليده تلقائياً من `package.json` فما فيه داعي لتتبّعه.

#### 💡 التشبيه:
> فكّر بـ `.gitignore` زي قائمة "ممنوع التصوير" في متحف — بعض القطع (الملفات الحساسة أو الضخمة) تُستثنى من أي "لقطة" يأخذها `Git` للمشروع.
> **وجه الشبه:** لافتة "ممنوع التصوير" = سطر في `.gitignore`، القطعة المستثناة = الملف أو المجلد المتجاهَل.

#### 🎯 الملخص السريع
- `Git` يقارن المحتوى، لا يتتبع "إعادة تسمية" كحدث مباشر
- `.gitignore` يستثني ملفات/مجلدات بأنماط نصية
- الشرطة المائلة `/` بعد الاسم تعني "مجلد كامل"

> 🎯 **جملة الامتحان:** `Git` يتتبع محتوى الملفات وليس أسماءها؛ لاستثناء ملفات معيّنة من التتبّع نستخدم ملف `.gitignore` بصيغة أنماط نصية.

#### 📚 التطبيق
كل مشروع Node.js/React ستنشئه لاحقاً سيحتاج `.gitignore` يستثني `node_modules/` و`.env` كخطوة أولى بعد `git init`.

#### 🤔 تفعيل الفهم (اسأل نفسك):
> **سؤال:** إذا أضفت ملف `.env` إلى `Git` قبل ما تضيفه لـ `.gitignore`، هل إضافته لاحقاً في `.gitignore` كافية لحذفه من التاريخ؟
> **لماذا هذا مهم؟** لأن `.gitignore` يمنع فقط تتبّع ملفات **جديدة** — الملفات المتتبَعة مسبقاً تحتاج أمراً إضافياً (`git rm --cached`) لإزالتها فعلياً، وهذا يوضّح فرق دقيق يقع فيه كثير من المطورين.

#### 2.6. استعراض تاريخ المشروع (git log)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_2.5"} -->

#### 📍 أين نحن الآن؟
بعد ما صار عندنا عدة commits، نحتاج أداة لاستعراض كل هذا التاريخ.

#### ⬅️ الربط مع السابق
كل `commit` سويناه في الأقسام السابقة يظهر الآن مرتباً زمنياً عبر هذا الأمر.

#### 💡 الفكرة الأساسية
**`git log` يعرض كل commits المشروع مرتبة من الأحدث للأقدم، مع الـ hash والمؤلف والتاريخ والرسالة.**

---

#### 💻 الكود

```bash
$ git log
commit 89abcde...
Author: Your Name <you@example.com>
Date: Thu Apr 29 12:00 2025

    Updated file1, file2, file3

commit 0123456...
Author: Your Name <you@example.com>
Date: Thu Apr 29 11:00 2025

    Initial commit
```

#### شرح كل سطر:
1. `git log` → الأمر المسؤول عن عرض تاريخ الـ commits
2. `commit 89abcde...` → معرّف فريد (`hash`) لكل commit، يُستخدم للإشارة إليه لاحقاً في أوامر زي `git show`
3. `Author: ...` → القيمة اللي ضبطناها سابقاً عبر `git config user.name/email`
4. `Date: ...` → توقيت إنشاء الـ commit بالضبط
5. رسالة الـ commit → تظهر تحت باقي المعلومات، وهي اللي كتبناها في الجزء 2.4

#### 📖 الشرح
`git log` هو نافذتك على "قصة" المشروع بالكامل. كل commit مرتبط بأبيه (الـ commit اللي قبله) عبر الـ hash، وهذا يشكّل سلسلة (أو شجرة، لو فيه فروع ودمج) تقدر تتنقل فيها لاحقاً باستخدام رموز زي `HEAD^` و`HEAD~4` (اللي رح نشرحها في قسم لاحق).

#### 💡 التشبيه:
> فكّرها زي دفتر يوميات (`diary`) لمشروعك — كل صفحة (commit) مؤرخة، موقّعة، وفيها ملاحظة عن وش صار ذلك اليوم.
> **وجه الشبه:** صفحة اليوميات = commit واحد، دفتر اليوميات كامل = `git log`.

#### 🎯 الملخص السريع
- كل commit له hash فريد، مؤلف، تاريخ، ورسالة
- الترتيب من الأحدث للأقدم
- الـ hash يُستخدم للإشارة لأي commit في أوامر أخرى

> 🎯 **جملة الامتحان:** `git log` يعرض تاريخ الـ commits مرتباً من الأحدث للأقدم، وكل commit يحمل معرّفاً فريداً (`hash`) يمكن استخدامه لاحقاً للإشارة إليه.

#### 📚 التطبيق
تستخدمه للتحقق من آخر التغييرات، إيجاد commit معيّن للرجوع له، أو فهم من غيّر ماذا ومتى في مشروع جماعي.

### 3. إدارة الفروع (Branching & Merging)

#### 3.1. إنشاء الفروع والتنقل بينها

<!-- @render: {type: "code-first", visualization: "tree", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_2.6"} -->

#### 📍 أين نحن الآن؟
بعد إتقان دورة العمل الأساسية على فرع واحد، نتعلم كيف نعمل بشكل متوازٍ على أفكار متعددة.

#### ⬅️ الربط مع السابق
كل الـ commits اللي سويناها لحد الآن كانت على فرع واحد ضمني اسمه `main`؛ الآن نتعلم كيف ننشئ فروعاً إضافية.

#### 💡 الفكرة الأساسية
**فرع (`branch`) هو مجرد مؤشر متحرك يشير إلى commit معيّن، ويسمح لك بتطوير خط عمل مستقل دون التأثير على الفروع الأخرى.**

---

#### 💻 الكود

```bash
$ git branch experimental
$ git branch
* main
  experimental
$ git switch experimental
Switched to branch 'experimental'
```

#### شرح كل سطر:
1. `git branch experimental` → ينشئ فرعاً جديداً باسم `experimental` يشير لنفس الـ commit الحالي، لكن **لا ينتقل إليه**
2. `git branch` (بدون معاملات) → يعرض قائمة كل الفروع الموجودة
3. `* main` → العلامة `*` تحدد الفرع الحالي النشط
4. `git switch experimental` → ينقلك فعلياً للفرع الجديد

#### 📖 الشرح
لاحظ الفرق الدقيق بين `git branch experimental` (ينشئ الفرع بس) و`git switch experimental` (ينتقل إليه). هذا الفصل بين "الإنشاء" و"الانتقال" مفيد لو تبي تنشئ عدة فروع دفعة وحدة بدون التنقل بينها فوراً.

#### 💡 التشبيه:
> فكّر في `main` كخط زمني رئيسي في فيلم خيال علمي، و`experimental` كخط زمني بديل ينشق منه — أي حدث يصير في الخط البديل ما يأثر على الخط الرئيسي إلا لو قررت تدمجهم لاحقاً.
> **وجه الشبه:** الخط الزمني الرئيسي = `main`، الخط البديل = `experimental`، نقطة الانشقاق = الـ commit اللي أنشأت منه الفرع.

#### 🎯 الملخص السريع
- `git branch <name>` ينشئ فرعاً بدون الانتقال إليه
- `git switch <name>` أو `git checkout <name>` ينقلك للفرع
- `*` أمام اسم الفرع في `git branch` يحدد الفرع الحالي

> 🎯 **جملة الامتحان:** الفرع في `Git` هو مؤشر خفيف يشير إلى commit معيّن؛ `git branch <name>` ينشئه فقط، بينما `git switch <name>` ينقلك فعلياً إليه.

---

#### 💻 الأمر البديل: `git checkout -b`

| العنصر | التفصيل |
| --- | --- |
| **متى تستخدمه** | لما تبي تنشئ فرعاً جديداً وتنتقل إليه في خطوة واحدة |
| **الصيغة الكاملة** | `git checkout -b <branch-name>` |
| **الناتج المتوقع** | `Switched to a new branch '<branch-name>'` |
| **تحذير شائع** | `git checkout` بدون `-b` على فرع موجود مسبقاً يُستخدم للتنقل فقط، لا للإنشاء |

```bash
$ git checkout -b experimental
Switched to a new branch 'experimental'
```

#### 📚 التطبيق
تستخدم الفروع لتجربة ميزة جديدة، إصلاح باگ عاجل، أو عمل عدة أعضاء فريق بالتوازي دون تعارض.

#### 3.2. دمج التغييرات (Merge)

<!-- @render: {type: "code-first", visualization: "tree", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_3.1"} -->

#### 📍 أين نحن الآن؟
بعد ما جرّبنا فكرة على فرع منفصل وتأكدنا إنها شغالة، نحتاج نرجّعها لخط العمل الرئيسي.

#### ⬅️ الربط مع السابق
أنشأنا فرع `experimental` وعدّلنا عليه؛ الآن ندمج تلك التعديلات رجوع في `main`.

#### 💡 الفكرة الأساسية
**الدمج يتطلب الانتقال أولاً إلى الفرع الهدف (الذي تريد استقبال التغييرات)، ثم تنفيذ `git merge` مع اسم الفرع المصدر.**

---

#### 💻 الكود

```bash
$ git checkout main
$ git merge experimental
2 files changed, 2 insertions(+), 1 deletion(-)
```

#### شرح كل سطر:
1. `git checkout main` → الانتقال للفرع الذي سيستقبل التغييرات (`main`)
2. `git merge experimental` → دمج كل commits الفرع `experimental` داخل `main`
3. `2 files changed, 2 insertions(+), 1 deletion(-)` → ملخص إحصائي: عدد الملفات المتأثرة، الأسطر المضافة (+)، والأسطر المحذوفة (-)

#### 📖 الشرح
ترتيب الخطوات هنا **حرج جداً**: لازم تكون واقف على الفرع اللي تبي "يستقبل" التغييرات (الهدف) قبل ما تنفذ `merge`، وتذكر اسم الفرع "المصدر" (اللي فيه التغييرات الجديدة) كمعامل للأمر. لو عكست الاتجاه غلط.

#### 💡 التشبيه:
> فكّرها زي رافدين نهر (`main` و`experimental`) ينفصلان لفترة ثم يلتقيان مرة ثانية في نقطة واحدة — كل مياه (تغييرات) الرافد الثانوي تنضم للرافد الرئيسي عند الالتقاء.
> **وجه الشبه:** الرافد الرئيسي = `main`، الرافد الثانوي = `experimental`، نقطة الالتقاء = merge commit.

#### 🎯 الملخص السريع
- الانتقال للفرع الهدف أولاً (عادة `main`)
- `git merge <source-branch>` يدمج المصدر داخل الهدف
- الناتج يعرض عدد الملفات والأسطر المتأثرة

> 🎯 **جملة الامتحان:** لدمج فرع `experimental` داخل `main`، يجب أولاً الانتقال إلى `main` عبر `git checkout main`، ثم تنفيذ `git merge experimental`.

#### 📚 التطبيق
هذا الأمر تستخدمه بعد كل مرة تكمّل فيها ميزة على فرع منفصل وتتأكد من جاهزيتها للدمج في الخط الرئيسي.

#### 🤔 تفعيل الفهم (اسأل نفسك):
> **سؤال:** لو نفّذت `git merge main` وأنت واقف على فرع `experimental` بدل العكس، وش رح يصير؟
> **لماذا هذا مهم؟** لأنك رح تدمج تغييرات `main` **داخل** `experimental`، عكس الاتجاه المطلوب — نفس المفهوم، اتجاه مقلوب تماماً، وهذا خطأ شائع جداً.

#### 3.3. حل تعارضات الدمج (Merge Conflicts)

<!-- @render: {type: "code-first", visualization: "none", coverage: "95%"} -->
<!-- @connectivity: {prerequisite: "section_3.2"} -->

#### 📍 أين نحن الآن؟
الدمج مو دايماً ينجح تلقائياً — أحياناً `Git` يحتاج مساعدتك للقرار.

#### ⬅️ الربط مع السابق
بعد ما تعلمنا الدمج الناجح، نتعلم الآن وش يصير لما الدمج يفشل تلقائياً.

#### 💡 الفكرة الأساسية
**التعارض يحدث عندما يعدّل فرعان نفس الجزء بالضبط من نفس الملف؛ `Git` يعلّم التعارض في الملف نفسه ويطلب منك حله يدوياً.**

---

#### 💻 الأمر: خطوات حل التعارض

| العنصر | التفصيل |
| --- | --- |
| **متى تستخدمه** | بعد ما `git merge` يفشل ويطبع رسالة `CONFLICT` |
| **الصيغة الكاملة** | تعديل الملف يدوياً، ثم `git add <file>`، ثم `git commit` |
| **الناتج المتوقع** | commit جديد يمثّل "دمج" يحوي القرار النهائي لكل تعارض |
| **تحذير شائع** | نسيان `git add` بعد حل التعارض — `Git` يبقى يعتبر الملف "غير محلول" |

```bash
$ git add <file>
$ git commit
```

#### شرح كل سطر:
1. `git add <file>` → يخبر `Git` إن التعارض في هذا الملف انحل يدوياً وقرارك النهائي جاهز
2. `git commit` → يثبّت commit خاص يمثّل نتيجة الدمج بعد حل كل التعارضات

#### 📖 الشرح
لما `Git` يواجه تعارض، هو يضيف علامات خاصة داخل الملف نفسه (زي `<<<<<<<`، `=======`، `>>>>>>>`) تفصل بين النسختين المتنازعتين. مهمتك تفتح الملف، تقرر أي نسخة صحيحة (أو تدمج الاثنين يدوياً)، تحذف تلك العلامات، ثم تتبع الخطوتين المذكورتين أعلاه.

#### 💡 التشبيه:
> فكّرها زي محرر مستندات مشترك اثنان عدّلا نفس الجملة بنفس الوقت — البرنامج ما يقدر يقرر مين على صح، فيعرض لك النسختين ويطلب منك تختار.
> **وجه الشبه:** النسختان المتعارضتان = التغييرات المتضاربة من الفرعين، اختيارك اليدوي = تعديل الملف وحل التعارض.

#### 🎯 الملخص السريع
- التعارض يحدث فقط عند تعديل **نفس الجزء** من نفس الملف في فرعين
- `Git` يعلّم التعارض داخل الملف مباشرة
- الحل: تعديل يدوي → `add` → `commit`

> 🎯 **جملة الامتحان:** تعارض الدمج (`merge conflict`) يحدث عندما يعدّل فرعان نفس الجزء من نفس الملف؛ يُحل الأمر بتعديل الملف يدوياً ثم `git add` و`git commit`.

#### 📚 التطبيق
سيحدث معك حتماً في أي مشروع جماعي حقيقي — التعامل معه بثقة مهارة أساسية.

#### ⚠️ أخطاء شائعة

#### الفهم الخاطئ ❌:
بعض المبتدئين يخافون من التعارض ويعتقدون إنه "خطأ" يعني فشل المشروع.

#### الفهم الصحيح ✅:
التعارض جزء طبيعي جداً من العمل الجماعي، وليس خطأً — هو ببساطة `Git` يطلب منك قراراً بشرياً لأنه ما يقدر يخمّن الصحيح تلقائياً.

#### 3.4. حذف الفروع

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_3.3"} -->

#### 📍 أين نحن الآن؟
بعد ما دمجت فرعاً بنجاح، غالباً ما تحتاجه بعد الآن — تنظيف المشروع خطوة مهمة.

#### ⬅️ الربط مع السابق
دمجنا `experimental` داخل `main`؛ الآن نحذف الفرع القديم لأنه أصبح زائداً.

#### 💡 الفكرة الأساسية
**`-d` يحذف بأمان (يرفض لو فيه تغييرات غير مدموجة)، بينما `-D` يفرض الحذف حتى لو ستضيع تغييرات.**

---

#### 💻 الكود

```bash
$ git branch -d experimental
Deleted branch experimental (was 89abcde).
$ git branch -D crazy-idea
Deleted branch crazy-idea (was deadbeef).
```

#### شرح كل سطر:
1. `git branch -d experimental` → حذف آمن؛ `Git` يتحقق أول إن كل commits الفرع مدموجة في مكان آخر
2. `git branch -D crazy-idea` → حذف قسري (`force`)؛ يحذف الفرع حتى لو فيه commits غير مدموجة ستضيع للأبد

#### 📖 الشرح
الحرف الصغير `d` (safe delete) هو خيارك الافتراضي دايماً. الحرف الكبير `D` (force delete) يُستخدم فقط لما تكون متأكد 100% إنك ما تحتاج تلك التغييرات — مثلاً فرع "فكرة مجنونة" جرّبتها وقررت التخلي عنها كلياً.

#### 💡 التشبيه:
> فكّرها زي سلة المهملات في الكمبيوتر: `-d` يشبه نقل ملف للسلة بعد ما تتأكد إنك نسخته في مكان آمن (مدموج)، بينما `-D` يشبه حذف نهائي فوري بدون تحقق.
> **وجه الشبه:** الحذف الآمن مع تحقق = `-d`، الحذف القسري الفوري = `-D`.

#### 🎯 الملخص السريع
- `-d` = حذف آمن، يرفض إذا فيه تغييرات غير مدموجة
- `-D` = حذف قسري، يحذف بلا شروط
- الناتج يعرض الـ hash الأخير للفرع المحذوف (فرصة أخيرة للرجوع له لو لزم)

> 🎯 **جملة الامتحان:** `git branch -d` يحذف الفرع بأمان فقط إذا كانت تغييراته مدموجة بالفعل، بينما `git branch -D` يفرض الحذف بغض النظر عن ذلك.

#### 📚 التطبيق
ممارسة جيدة: احذف أي فرع مباشرة بعد دمجه بنجاح للحفاظ على قائمة فروع نظيفة.

#### ⚠️ أخطاء شائعة

#### الفهم الخاطئ ❌:
استخدام `-D` كعادة دائمة "لأنها تشتغل دايماً" دون التفكير في العواقب.

#### الفهم الصحيح ✅:
استخدم `-d` كخيار افتراضي دائماً؛ إذا رفض `Git` الحذف، هذا **تحذير مقصود** يستحق التحقق منه قبل اللجوء لـ `-D`.

### 4. التعاون باستخدام Git (Collaboration)

#### 4.1. Clone و Push للتعاون الأساسي

<!-- @render: {type: "code-first", visualization: "sequence", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_3.4"} -->

#### 📍 أين نحن الآن؟
كل ما تعلمناه لحد الآن كان على مشروع محلي وحيد؛ الآن ندخل عالم العمل مع فريق حقيقي.

#### ⬅️ الربط مع السابق
بعد إتقان `add`/`commit`/`branch`/`merge` محلياً، نطبّق نفس المفاهيم عبر أكثر من جهاز/شخص.

#### 💡 الفكرة الأساسية
**`git clone` ينسخ repository كامل (بكل تاريخه) إلى جهازك، و`git push` يرفع تعديلاتك المحلية إلى السيرفر المشترك.**

---

#### 💻 الكود

```bash
bob$ git clone 'url_to_alice_repo' myrepo
Cloning into 'myrepo'...
done.
bob$ git commit -a
[main 89abcde] Bob's changes
bob$ git push origin main
```

#### شرح كل سطر:
1. `git clone 'url_to_alice_repo' myrepo` → ينسخ كامل repository أليس (بكل الـ commits والفروع) إلى مجلد محلي اسمه `myrepo`
2. `git commit -a` → باب يعدّل ملفات ويثبّت تعديلاته محلياً (كما شرحنا في القسم 2.3)
3. `git push origin main` → يرفع commits الفرع `main` المحلي إلى الريموت المسمى `origin` (الاسم الافتراضي لمصدر الـ clone)

#### 📖 الشرح
النقطة الحرجة هنا: `git clone` ما ينسخ بس آخر نسخة من الملفات — هو ينسخ **كامل التاريخ**. هذا معناه إن باب، من اللحظة الأولى، عنده نفس القدرة اللي عند أليس على استعراض كل commit قديم، كل فرع، وكل تاريخ المشروع بالكامل — هذي هي الطبيعة "الموزّعة" اللي رح نشرحها بالتفصيل في القسم 6.

#### 💡 التشبيه:
> فكّرها زي نسخ مكتبة كاملة (بكل رفوفها وكتبها القديمة) لبيتك، بدل ما تاخذ بس آخر كتاب صدر — عندك نفس الأرشيف الكامل اللي عند المكتبة الأصلية.
> **وجه الشبه:** المكتبة الأصلية = repository أليس، نسختك الكاملة في البيت = نتيجة `git clone`.

#### 🎯 الملخص السريع
- `clone` ينسخ كامل التاريخ، لا آخر نسخة فقط
- `origin` هو الاسم الافتراضي لمصدر الـ clone
- `push origin main` يرفع تعديلات فرع `main` المحلي للريموت

> 🎯 **جملة الامتحان:** `git clone` ينسخ repository كاملاً بكل تاريخه إلى الجهاز المحلي، وليس فقط أحدث نسخة من الملفات.

#### 📚 التطبيق
هذا أول أمر تكتبه للانضمام لأي مشروع فريق موجود مسبقاً على GitHub أو أي سيرفر آخر.

#### 4.2. فحص تغييرات الريموت واختصارات الريموت

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_4.1"} -->

#### 📍 أين نحن الآن؟
قبل ما تدمج تعديلات شخص ثاني بشكل أعمى، من الأفضل تراجعها أول — وهذا ما يوفره `fetch`.

#### ⬅️ الربط مع السابق
باب رفع تعديلاته عبر `push`؛ الآن أليس (أو أي زميل) يحتاج يرى وش تغيّر قبل الدمج.

#### 💡 الفكرة الأساسية
**`git fetch` يجلب التغييرات من الريموت دون دمجها تلقائياً، مما يسمح لك بمراجعتها أولاً.**

---

#### 💻 الكود

```bash
$ git fetch https://github.com/bob/repo.git main
$ git log -p HEAD..FETCH_HEAD
$ git remote add bob https://github.com/bob/repo.git
$ git fetch bob
```

#### شرح كل سطر:
1. `git fetch https://github.com/bob/repo.git main` → يجلب الفرع `main` من repository باب، ويخزّنه محلياً تحت مرجع خاص اسمه `FETCH_HEAD` — بدون لمس فرعك الحالي
2. `git log -p HEAD..FETCH_HEAD` → يعرض بالتفصيل (`-p` = patch) كل الفرق بين موقعك الحالي (`HEAD`) وما تم جلبه (`FETCH_HEAD`)
3. `git remote add bob https://github.com/bob/repo.git` → يعرّف اختصاراً دائماً باسم `bob` لهذا الرابط
4. `git fetch bob` → نفس عملية الجلب، لكن باستخدام الاسم المختصر بدل كتابة الرابط الكامل كل مرة

#### 📖 الشرح
الفرق الجوهري بين `fetch` و`pull`: **`fetch` لا يغيّر أي شي في working directory أو فرعك الحالي** — هو فقط يحدّث "معرفة" `Git` بما هو موجود على الريموت. هذا يعطيك فرصة مراجعة التغييرات (عبر `git log -p`) قبل ما تقرر دمجها فعلياً. `git remote add` بعدها هو حل عملي لتوفير الوقت — بدل كتابة الرابط الكامل كل مرة.

#### 💡 التشبيه:
> فكّرها زي فحص بريدك الإلكتروني قبل الرد عليه: `git fetch` = تحميل الرسائل الجديدة لتقرأها، `git log -p HEAD..FETCH_HEAD` = فتح كل رسالة ومراجعة محتواها، وبعدها فقط تقرر ترد (تدمج) أو لا.
> **وجه الشبه:** الرسائل غير المقروءة = التغييرات المجلوبة (`FETCH_HEAD`)، قراءتها قبل الرد = مراجعة الفرق قبل الدمج.

#### 🎯 الملخص السريع
- `git fetch` يجلب دون دمج تلقائي
- `FETCH_HEAD` يشير لآخر شي تم جلبه
- `git remote add <name> <url>` يعرّف اختصاراً دائماً لتوفير الوقت

> 🎯 **جملة الامتحان:** `git fetch` يجلب التغييرات من الريموت ويخزّنها في `FETCH_HEAD` دون دمجها تلقائياً في الفرع الحالي، مما يسمح بمراجعتها قبل الدمج.

#### 📚 التطبيق
ممارسة أكثر أماناً من `git pull` المباشر في مشاريع فريق كبيرة، حيث تفضّل تراجع كل تغيير قبل دمجه.

#### 4.3. السحب من فرع ريموت (Pull)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_4.2"} -->

#### 📍 أين نحن الآن؟
بعد ما راجعنا التغييرات عبر `fetch`، الخطوة الطبيعية التالية هي دمجها — أو نختصر الخطوتين معاً بأمر واحد.

#### ⬅️ الربط مع السابق
تعلمنا `fetch` (جلب بدون دمج)؛ الآن `pull` يجمع الجلب والدمج في أمر واحد.

#### 💡 الفكرة الأساسية
**`git pull` = `git fetch` + `git merge` في خطوة واحدة.**

---

#### 💻 الكود

```bash
$ git pull . remotes/bob/main
```

#### شرح كل سطر:
1. `git pull` → الأمر المركّب: يجلب ثم يدمج تلقائياً
2. `.` → يشير للـ repository المحلي نفسه (وليس رابط خارجي) — يعني نسحب من مرجع محلي مخزّن مسبقاً
3. `remotes/bob/main` → المرجع المحلي الذي يمثّل فرع `main` عند الريموت المسمى `bob` (اللي عرّفناه بـ `git remote add` في القسم السابق)

#### 📖 الشرح
هذا المثال يوضّح إن `pull` مو محصور بس بجلب من رابط خارجي مباشرة — تقدر كمان تسحب من مرجع ريموت محلي مخزّن مسبقاً (`remotes/bob/main`) بعد ما تكون عملت `fetch` له سابقاً. الفكرة الأهم اللي لازم تحفظها: **كل مرة تستخدم `pull`، أنت فعلياً تنفذ `fetch` ثم `merge` تلقائياً** — وهذا يعني إنه ممكن يسبب نفس تعارضات الدمج اللي شرحناها في القسم 3.3 لو فيه تضارب.

#### 💡 التشبيه:
> ارجع لتشبيه البريد الإلكتروني: لو `fetch` هو "تحميل الرسائل الجديدة بس"، فـ `pull` هو "تحميل الرسائل **ودمجها تلقائياً** في صندوق واردك الرئيسي بدون ما تراجعها فرداً فرداً أول".
> **وجه الشبه:** الدمج التلقائي الفوري = `pull`، المراجعة المتأنية قبل الدمج = `fetch` ثم `merge` يدوياً.

#### 🎯 الملخص السريع
- `pull = fetch + merge` تلقائياً
- يمكن السحب من رابط خارجي أو من مرجع محلي مخزَّن
- قد يسبب تعارضات دمج تماماً مثل `git merge` العادي

> 🎯 **جملة الامتحان:** `git pull` هو اختصار لعمليتين متتاليتين: `fetch` (جلب) ثم `merge` (دمج) — بعكس `fetch` وحدها التي لا تدمج شيئاً تلقائياً.

#### 📚 التطبيق
الأمر الأكثر استخداماً يومياً للحصول على آخر تعديلات الفريق مباشرة في فرعك المحلي.

#### 🤔 تفعيل الفهم (اسأل نفسك):
> **سؤال:** لو أنت وزميلك عدّلتوا نفس السطر بالضبط في نفس الملف، وعملت `git pull`، وش الاحتمال المتوقع؟
> **لماذا هذا مهم؟** لأن `pull` تدمج تلقائياً، فلو فيه تضارب حقيقي، رح تحصل بالضبط على `merge conflict` كما شرحنا في القسم 3.3 — نفس الآلية بالضبط، بس محفّزة من أمر مختلف.

#### ⚠️ أخطاء شائعة

#### الفهم الخاطئ ❌:
كثير من المبتدئين يستخدمون `pull` دائماً دون تفكير، ثم يتفاجؤون بتعارضات غير متوقعة.

#### الفهم الصحيح ✅:
بما إن `pull` تدمج تلقائياً، فالأفضل أحياناً استخدام `fetch` ثم مراجعة `git log -p HEAD..FETCH_HEAD` قبل الدمج اليدوي، خصوصاً في مشاريع فيها تعديلات كثيرة متوازية.

- ✓ تم شرح بالكامل: تعريف `pull` وعلاقته بـ `fetch` و`merge`

### 5. استكشاف واستعلام التاريخ (History Exploration)

#### 5.1. عرض commits محددة (git show) والتنقل بالأسلاف

<!-- @render: {type: "code-first", visualization: "tree", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_4.3"} -->

#### 📍 أين نحن الآن؟
بعد ما صار عندنا تاريخ غني من الـ commits، نحتاج أدوات دقيقة للتنقل فيه.

#### ⬅️ الربط مع السابق
استخدمنا `git log` لاستعراض التاريخ بشكل عام؛ الآن نتعلم كيف نستهدف commit محدد بدقة.

#### 💡 الفكرة الأساسية
**الرمز `^` يشير لأب الـ commit مباشرة، بينما `~N` يشير لسلف على بُعد N خطوات.**

---

#### 💻 الكود

```bash
$ git show HEAD
commit 89abcde...
$ git show HEAD^
commit 0123456...
$ git show HEAD~4
```

#### شرح كل سطر:
1. `git show HEAD` → يعرض تفاصيل الـ commit الحالي (`HEAD` = موقعك الحالي في التاريخ)
2. `git show HEAD^` → يعرض تفاصيل الـ commit **السابق مباشرة** (أب الـ HEAD)
3. `git show HEAD~4` → يعرض تفاصيل الـ commit الذي يبعد **4 خطوات للخلف** عن `HEAD`

#### 📖 الشرح
هذي الرموز تعطيك طريقة مختصرة للإشارة لأي commit بدون ما تحتاج تنسخ الـ hash الطويل كل مرة. `^` بمفردها (بدون رقم) تعني "أب واحد للخلف"، ونفس الشي `~1`. أما `~4` فيعني "4 آباء متتالية للخلف" — يعني تمشي في الخط الزمني الرئيسي 4 خطوات للوراء.

#### 💡 التشبيه:
> فكّرها زي شجرة عائلة: `HEAD` هو أنت، `HEAD^` هو أبوك مباشرة، و`HEAD~4` هو جدّك الرابع في نفس الخط المباشر للأجداد.
> **وجه الشبه:** أنت = `HEAD`، أبوك = `HEAD^`، جدّك الرابع = `HEAD~4`.

#### 🎯 الملخص السريع
- `HEAD` = الموقع الحالي
- `HEAD^` أو `HEAD~1` = الأب المباشر
- `HEAD~N` = السلف على بعد N خطوات في نفس الخط

> 🎯 **جملة الامتحان:** الرمز `HEAD^` يشير إلى الأب المباشر للـ commit الحالي، بينما `HEAD~N` يشير إلى السلف الذي يبعد N خطوات على نفس الخط الزمني.

#### 📚 التطبيق
تستخدم هذي الرموز في أوامر كثيرة زي `git diff`، `git reset`، `git checkout` للإشارة لنسخ قديمة بدقة.

#### 5.2. وضع العلامات ومقارنة الإصدارات (Tag و Diff)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_5.1"} -->

#### 📍 أين نحن الآن؟
بعض النقاط في التاريخ مهمة بشكل خاص (زي إصدار رسمي) وتستحق اسماً ثابتاً بدل hash طويل.

#### ⬅️ الربط مع السابق
بعد ما تعلمنا التنقل بالرموز (`^`، `~`)، نتعلم الآن تسمية نقاط محددة بشكل دائم.

#### 💡 الفكرة الأساسية
**`git tag` يعطي اسماً ثابتاً لـ commit معيّن (عادة لإصدار رسمي)، ويمكن استخدام هذا الاسم لاحقاً في المقارنة أو إنشاء فروع.**

---

#### 💻 الكود

```bash
$ git tag v2.5 1b2e1d63ff
$ git diff v2.5 HEAD
$ git branch stable v2.5
```

#### شرح كل سطر:
1. `git tag v2.5 1b2e1d63ff` → يضع علامة (`tag`) باسم `v2.5` على الـ commit اللي hash-ه يبدأ بـ `1b2e1d63ff`
2. `git diff v2.5 HEAD` → يقارن الفرق بين تلك النسخة القديمة (`v2.5`) والموقع الحالي (`HEAD`)
3. `git branch stable v2.5` → ينشئ فرعاً جديداً باسم `stable` يبدأ **من نقطة `v2.5` بالضبط**، وليس من `HEAD` الحالي

#### 📖 الشرح
الفرق بين `tag` و`branch` مهم: الـ `tag` **مرجع ثابت** لا يتحرك أبداً (يمثل نقطة تاريخية محددة، زي "إصدار 2.5")، بينما الـ `branch` **مؤشر متحرك** يتقدم مع كل commit جديد تضيفه عليه. لهذا نستخدم `tag` للإصدارات الرسمية و`branch` للعمل النشط المستمر.

#### 💡 التشبيه:
> فكّر بالـ `tag` زي علامة مرجعية (`bookmark`) دائمة في كتاب — تبقى في نفس الصفحة للأبد. بينما الـ `branch` زي إصبعك وأنت تقرأ — يتحرك مع كل صفحة جديدة تقلبها.
> **وجه الشبه:** العلامة الثابتة = `tag`، الإصبع المتحرك = `branch`.

#### 🎯 الملخص السريع
- `tag` = مرجع ثابت لنقطة تاريخية (عادة إصدار)
- `branch` = مؤشر متحرك يتقدم مع كل commit جديد
- تقدر تنشئ فرعاً يبدأ من `tag` معيّن بدل `HEAD`

> 🎯 **جملة الامتحان:** الفرق الجوهري بين `tag` و`branch` هو إن الـ `tag` مرجع ثابت لا يتحرك، بينما الـ `branch` مؤشر متحرك يتقدم مع كل commit جديد.

#### 📚 التطبيق
تستخدم `tags` لتوثيق إصدارات المشروع الرسمية (`v1.0`, `v2.5`, إلخ) بحيث تقدر ترجع لها بسهولة لاحقاً.

#### 5.3. التراجع عن Commits (Reset)

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_5.2"} -->

#### 📍 أين نحن الآن؟
أداة قوية جداً لكنها خطيرة — تحتاج فهم كامل قبل استخدامها.

#### ⬅️ الربط مع السابق
تعلمنا كيف نتنقل بالتاريخ (`^`، `~`) ونقارنه (`diff`)؛ الآن نتعلم كيف "نمحو" جزءاً منه.

#### 💡 الفكرة الأساسية
**`git reset --hard` يعيد `HEAD` إلى commit سابق ويحذف كل التغييرات بعده نهائياً.**

---

#### 💻 الكود

```bash
$ git reset --hard HEAD^
HEAD is now at 0123456 Initial commit
```

#### شرح كل سطر:
1. `git reset --hard HEAD^` → يرجّع `HEAD` (وفرعك الحالي) إلى الـ commit الأب مباشرة
2. `--hard` → يحذف أي تغييرات في working directory وstaging area، مو بس يحرّك مؤشر `HEAD`
3. `HEAD is now at 0123456 Initial commit` → رسالة تأكيد توضح الـ commit الجديد اللي أنت واقف عليه الآن

#### 📖 الشرح
هذا أخطر أمر شرحناه في المحاضرة كلها. `--hard` تحديداً تعني إنك **تفقد أي تغييرات غير محفوظة** بشكل نهائي — لا working directory ولا staging area يحتفظان بأي أثر. الخيارات الأقل خطورة زي `--soft` أو `--mixed` (لم تُذكر في هذي المحاضرة تحديداً) تحافظ على التغييرات في مناطق مختلفة، لكن `--hard` يمحو كل شي.

#### 💡 التشبيه:
> فكّرها زي زر "Undo" في محرر نصوص، لكن بدل ما يتراجع خطوة واحدة، هو يمسح **كل** التاريخ بعد نقطة معيّنة بلا رجعة — مو مجرد إخفاء، بل حذف فعلي.
> **وجه الشبه:** نقطة الرجوع = `HEAD^`، الحذف النهائي بلا أرشيف = تأثير `--hard`.

#### 🎯 الملخص السريع
- `git reset --hard <target>` يرجّع `HEAD` ويحذف كل شي بعده
- التغييرات المحذوفة صعبة الاسترجاع (وليست دائماً مستحيلة، لكن معقدة)
- استخدمه فقط عندما تكون متأكد 100% أنك لا تحتاج التغييرات

> 🎯 **جملة الامتحان:** `git reset --hard HEAD^` يعيد الفرع الحالي إلى الـ commit السابق مباشرة، ويحذف نهائياً أي تغييرات في working directory وstaging area بعد تلك النقطة.

#### 📚 التطبيق
يُستخدم في حالات نادرة ومقصودة، مثل التخلص الكامل من تجربة فاشلة قبل ما تُدمج مع أي فرع آخر.

#### ⚠️ أخطاء شائعة

#### الفهم الخاطئ ❌:
استخدام `git reset --hard` بشكل روتيني ظناً إنه "مجرد تراجع بسيط" مثل `Ctrl+Z`.

#### الفهم الصحيح ✅:
`git reset --hard` أخطر بكثير من `Ctrl+Z` العادي — هو يحذف تغييرات working directory كاملة، وليس فقط تراجع خطوة تحرير واحدة. راجع دايماً `git status` و`git log` قبل تنفيذه للتأكد من النقطة الصحيحة.

#### 5.5. تصور التاريخ ومقارنة ملفات محددة

<!-- @render: {type: "code-first", visualization: "tree", coverage: "100%"} -->

#### 📍 أين نحن الآن؟

#### ⬅️ الربط مع السابق
بعد كل أدوات البحث والمقارنة النصية، نضيف الآن أداة بصرية (GUI) وأمراً لمقارنة ملف واحد بدقة.

#### 💡 الفكرة الأساسية
**`gitk` يعرض شجرة الفروع والدمج بصرياً، و`git diff a:file b:file` يقارن نسخة محددة من ملف واحد بين نقطتين مختلفتين.**

---

#### 💻 الكود

```bash
$ gitk

$ git show v2.5:Makefile
```

1. `gitk` → يفتح نافذة رسومية (GUI) تعرض شجرة كاملة لكل commits والفروع والدمج بصرياً

3. `git show v2.5:Makefile` → يعرض محتوى ملف `Makefile` بالضبط كما كان في نسخة `v2.5`، دون الحاجة لعمل `checkout`

#### 📖 الشرح
لما تاريخ المشروع يصير معقد (فروع متعددة، دمج متكرر)، النص وحده يصعب فهمه بسرعة — هنا `gitk` يعطيك صورة بصرية واضحة تشبه المخططات اللي شفناها في شرائح المحاضرة (شرائح 12، 13، 16). أما `git diff` بصيغة `<ref>:<path>`، فيسمح لك بمقارنة **ملفين مختلفين الاسم** (زي `Makefile` مقابل `Makefile.in`) من نقطتين مختلفتين في التاريخ — مرونة إضافية عن مقارنة نفس الملف بس.

#### 💡 التشبيه:
> فكّر بـ `gitk` زي خريطة مترو بصرية بدل جدول محطات نصي طويل — نفس المعلومة، لكن العين تلتقطها أسرع بكثير لما تكون الشبكة معقدة.
> **وجه الشبه:** الجدول النصي الطويل = ناتج `git log`، الخريطة البصرية الواضحة = `gitk`.

#### 🎯 الملخص السريع
- `gitk` أداة رسومية لعرض شجرة التاريخ بصرياً
- `git diff <ref1>:<path1> <ref2>:<path2>` يقارن ملفات محددة من نقطتين مختلفتين
- `git show <ref>:<path>` يعرض محتوى ملف كما كان في نسخة معيّنة

> 🎯 **جملة الامتحان:** `gitk` أداة رسومية تعرض شجرة الفروع والدمج بصرياً، بينما صيغة `git diff <ref>:<path>` تسمح بمقارنة ملفات محددة من نقطتين مختلفتين في التاريخ حتى لو اختلفت أسماء الملفات.

#### 📚 التطبيق
تستخدم `gitk` لفهم تاريخ معقد بسرعة، و`git show <ref>:<path>` لاسترجاع محتوى ملف قديم بدون تغيير حالة working directory الحالية.

### 6. Git كنظام موزّع وأنماط سير العمل

#### 6.1. الطبيعة الموزّعة لـ Git

<!-- @render: {type: "code-first", visualization: "none", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_5.5"} -->

#### 📍 أين نحن الآن؟
قبل ما نشرح أنماط التعاون المختلفة، لازم نفهم أول ليش `Git` أصلاً يسمح بها كلها.

#### ⬅️ الربط مع السابق
كل أدوات `clone`/`fetch`/`pull` اللي تعلمناها ممكنة بسبب خاصية جوهرية واحدة: `Git` موزّع.

#### 💡 الفكرة الأساسية
**كل من يعمل `clone` يحصل على نسخة كاملة من المشروع بكل تاريخه، مما يلغي وجود نقطة فشل وحيدة.**

---

#### 💻 الشرح المفاهيمي (لا يوجد كود لهذا القسم)

النقاط الأساسية من المحاضرة:
1. `Git` نظام **موزّع (Distributed)** بطبيعته
2. عملية `clone` تعطي كل مستخدم **نسخة احتياطية كاملة** من الـ repository الرئيسي
3. لو السيرفر المركزي طاح، أي نسخة عند أي مستخدم تقدر تسترجع المشروع بالكامل
4. **لا توجد نقطة فشل وحيدة** (`no single point of failure`) — إلا في حالة نادرة جداً: وجود نسخة واحدة فقط أصلاً
5. هذي الطبيعة الموزّعة تفتح الباب لتطبيق أنماط عمل (`workflows`) لا محدودة، وليس نمط واحد إجباري

#### 📖 الشرح
هذا يختلف جوهرياً عن أنظمة إدارة إصدارات "مركزية" أقدم (زي Subversion الكلاسيكي)، حيث السيرفر المركزي يحتوي **التاريخ الوحيد الكامل**، وكل مستخدم عنده بس نسخة عمل جزئية بدون تاريخ. في `Git`، كل نسخة `clone` = نسخة كاملة الأهلية، قادرة تعمل كل شي (بما فيها إنشاء سيرفر بديل لو احتجت).

#### 💡 التشبيه:
> فكّرها زي مكتبة عامة تعطي كل قارئ نسخة كاملة من كل كتاب فيها (مو بس آخر إصدار)، بدل ما يكون فيه نسخة وحيدة أصلية في خزنة والباقي بس يقرأون منها بدون امتلاكها. لو المكتبة احترقت، أي قارئ يقدر يعيد بناء المكتبة كاملة من نسخته.
> **وجه الشبه:** المكتبة المركزية القابلة للاحتراق = سيرفر مركزي وحيد، القرّاء اللي عندهم نسخ كاملة = المطورون بعد `clone`.

#### 🎯 الملخص السريع
- كل `clone` = نسخة كاملة (تاريخ + فروع + كل شي)
- لا نقطة فشل وحيدة طالما فيه أكثر من نسخة
- الطبيعة الموزّعة تسمح بأنماط تعاون متعددة، لا نمط واحد

> 🎯 **جملة الامتحان:** كون `Git` نظاماً موزّعاً يعني أن كل مستخدم يمتلك نسخة كاملة من الـ repository (بما فيها كامل التاريخ) بعد عملية `clone`، ما يلغي وجود نقطة فشل مركزية وحيدة.

#### 📚 التطبيق

#### 6.2. نمط Subversion-Style (المركزي)

<!-- @render: {type: "code-first", visualization: "tree", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_6.1"} -->

#### 📍 أين نحن الآن؟
أبسط أنماط التعاون الثلاثة، وأقربها لأنظمة إدارة الإصدارات التقليدية.

#### ⬅️ الربط مع السابق
بعد ما فهمنا إن `Git` يسمح بأنماط متعددة، نبدأ بأبسطها.

#### 💡 الفكرة الأساسية
**كل المطورين يرفعون (push) مباشرة لنفس السيرفر المشترك، و`Git` يفرض التزامن قبل السماح بالرفع.**

---

#### 💻 الشرح المفاهيمي (لا يوجد كود لهذا القسم)

النقاط الأساسية:
1. يوجد `shared repository` واحد يمثّل المصدر المشترك للجميع
2. كل المطورين (`developer 1`، `developer 2`، `developer 3`) يرفعون تعديلاتهم مباشرة لنفس هذا السيرفر
3. `Git` يمنعك من الرفع (`push`) إذا لم تكن قد جلبت (`fetch`) أحدث التغييرات أولاً — هذا يفرض التزامن ويقلل التعارضات المفاجئة

#### 📖 الشرح
هذا النمط أشبه ما يكون بأنظمة زي Subversion (SVN) القديمة، حيث السيرفر المركزي هو "الحقيقة الوحيدة". الفرق إن `Git` (بفضل طبيعته الموزّعة) يعطي كل مطوّر نسخة كاملة محلياً، لكن **اتفاقياً** (لا تقنياً إجبارياً) كل الفريق يوافق على استخدام سيرفر واحد كمرجع مشترك للرفع والسحب.

#### 💡 التشبيه:
> فكّرها زي سبورة مشتركة في اجتماع فريق — الكل يكتب عليها مباشرة، لكن قبل ما تكتب لازم تتأكد إنك قرأت آخر ما كتبه زميلك، وإلا قد تمحو شي مهم بدون قصد.
> **وجه الشبه:** السبورة المشتركة = `shared repository`، قراءة آخر إضافة قبل الكتابة = `fetch` قبل `push`.

#### 🎯 الملخص السريع
- سيرفر مشترك واحد، الكل يرفع له مباشرة
- `Git` يفرض `fetch` قبل `push` الناجح
- أبسط الأنماط الثلاثة وأقربها للأنظمة المركزية التقليدية

> 🎯 **جملة الامتحان:** في نمط Subversion-Style، يرفع كل المطورين تعديلاتهم مباشرة إلى نفس السيرفر المشترك، ويفرض `Git` التزامن بمنع الرفع قبل جلب أحدث التغييرات.

#### 📚 التطبيق
مناسب لفرق صغيرة إلى متوسطة الحجم تعمل بثقة عالية بين أعضائها ولا تحتاج طبقة مراجعة إضافية.

#### 6.3. نمط Integration Manager

<!-- @render: {type: "code-first", visualization: "tree", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_6.2"} -->

#### 📍 أين نحن الآن؟
نمط أكثر شيوعاً في المشاريع مفتوحة المصدر، ويقدّم طبقة مراجعة إضافية.

#### ⬅️ الربط مع السابق
بعد نمط "الكل يرفع مباشرة"، هذا النمط يضيف "بوابة" (شخص مسؤول) قبل دمج أي تعديل في المصدر الرسمي.

#### 💡 الفكرة الأساسية
**كل مطوّر يستنسخ (`clone`) الـ repository الرسمي ("المبارَك")، يشتغل على نسخته الخاصة، ثم يطلب من الـ Integrator سحب تعديلاته.**

---

#### 💻 الشرح المفاهيمي (لا يوجد كود لهذا القسم)

النقاط الأساسية:
1. يوجد `blessed repository` واحد — النسخة الرسمية المعتمدة للمشروع
2. يوجد `integration manager` (المسؤول عن الدمج) يمتلك صلاحية الرفع المباشر للـ blessed repository
3. المطورون (`developer public/private`) يستنسخون الـ blessed repository، يعملون في نسخهم الخاصة، ثم **يطلبون** من الـ integration manager يسحب تعديلاتهم — لا يرفعونها هم مباشرة

#### 📖 الشرح
الفرق الجوهري عن النمط السابق: لا أحد غير الـ Integrator يملك صلاحية الكتابة المباشرة على الـ repository الرسمي. هذا يضيف طبقة مراجعة بشرية (`review`) قبل دخول أي كود للمشروع الرسمي — وهو بالضبط ما يشبه آلية الـ Pull Request المستخدمة اليوم في منصات زي GitHub وGitLab.

#### 💡 التشبيه:
> فكّرها زي دار نشر لمجلة: أي كاتب يقدر يكتب مقالاً في مسودته الخاصة، لكن بس رئيس التحرير (الـ Integrator) هو من يقرر أي مقال يُنشر فعلياً في العدد الرسمي.
> **وجه الشبه:** المسودة الخاصة = نسخة المطوّر بعد `clone`، العدد الرسمي المنشور = `blessed repository`، رئيس التحرير = `integration manager`.

#### 🎯 الملخص السريع
- `blessed repository` = النسخة الرسمية الوحيدة
- `integration manager` هو الوحيد صاحب صلاحية الكتابة المباشرة عليها
- بقية المطورين يطلبون سحب تعديلاتهم بدل رفعها مباشرة

> 🎯 **جملة الامتحان:** في نمط Integration Manager، يمتلك شخص واحد فقط (الـ Integrator) صلاحية الرفع المباشر إلى الـ blessed repository، بينما بقية المطورين يطلبون منه سحب تعديلاتهم.

#### 📚 التطبيق
هذا هو النمط الأقرب لتجربتك اليومية على GitHub لاحقاً — عبر آلية الـ Pull Requests في مشاريعك القادمة.

#### 6.4. نمط Dictator and Lieutenants

<!-- @render: {type: "code-first", visualization: "tree", coverage: "100%"} -->
<!-- @connectivity: {prerequisite: "section_6.3"} -->

#### 📍 أين نحن الآن؟
النمط الأكثر تعقيداً وهرمية، مصمّم للمشاريع الضخمة جداً بآلاف المساهمين.

#### ⬅️ الربط مع السابق
بعد "شخص واحد يراجع كل شي" في النمط السابق، هذا النمط يوزّع مسؤولية المراجعة على طبقات متعددة لأن الحجم أكبر من طاقة شخص واحد.

#### 💡 الفكرة الأساسية
**اللوتننتات (`Lieutenants`) يديرون subsystems محددة، الدكتاتور (`Dictator`) يسحب منهم، ثم يحدّث الـ blessed repository لينسخ منها الجميع.**

---

#### 💻 الشرح المفاهيمي (لا يوجد كود لهذا القسم)

النقاط الأساسية:
1. مستخدم في مشاريع كبيرة جداً — المثال المذكور صراحة: **Linux Kernel**
2. **اللوتننتات (Lieutenants)** — كل واحد مسؤول عن جزء محدد (`subsystem`) من المشروع
3. **الدكتاتور (Dictator)** يسحب التغييرات المُراجَعة من اللوتننتات
4. الـ **blessed repository** يُحدَّث من قبل الدكتاتور، وهو المصدر اللي يستنسخ منه الجميع

#### 📖 الشرح
هذا النمط طبقة إضافية فوق Integration Manager: بدل شخص واحد يراجع كل التعديلات من كل المطورين، المشروع يُقسَّم لأجزاء (`subsystems`) — مثلاً نظام الملفات، إدارة الذاكرة، تعريفات الأجهزة — وكل جزء له لوتننت مسؤول عنه يراجع تعديلات مطوري ذلك الجزء تحديداً. الدكتاتور بعدين يثق بمراجعة اللوتننتات ويدمج أعمالهم في القمة.

#### 💡 التشبيه:
> فكّرها زي شركة ضخمة فيها مدراء أقسام (اللوتننتات) كل واحد يراجع عمل قسمه (المحاسبة، التسويق، الهندسة)، وبعدين المدير التنفيذي (الدكتاتور) يعتمد قرارات كل قسم دون ما يراجع كل تفصيلة بنفسه — يثق بمدراء الأقسام.
> **وجه الشبه:** مدراء الأقسام = Lieutenants، المدير التنفيذي = Dictator، القرار النهائي المعتمد = تحديث الـ blessed repository.

#### 🎯 الملخص السريع
- طبقات هرمية: مطورون → Lieutenants → Dictator → blessed repository
- كل Lieutenant مسؤول عن subsystem محدد فقط
- يُستخدم في مشاريع بحجم Linux Kernel

> 🎯 **جملة الامتحان:** في نمط Dictator and Lieutenants، يدير اللوتننتات subsystems محددة ويراجعون التعديلات ضمنها، ثم يسحب الدكتاتور من اللوتننتات ويحدّث الـ blessed repository الذي ينسخ منه الجميع.

#### 📚 التطبيق
تفهم هذا النمط جيداً لو خططت تساهم يوماً في مشروع مفتوح المصدر بحجم ضخم مثل نواة Linux.

#### ⚖️ مقارنة سريعة: أنماط التعاون الثلاثة

| المعيار | Subversion-Style | Integration Manager | Dictator and Lieutenants |
| --- | --- | --- | --- |
| **من يرفع مباشرة للمصدر الرسمي** | كل المطورين | شخص واحد (Integrator) فقط | الدكتاتور فقط (بعد سحبه من اللوتننتات) |
| **طبقات المراجعة** | لا توجد طبقة مراجعة منفصلة | طبقة واحدة | طبقتان (Lieutenants ثم Dictator) |
| **الحجم المناسب** | فرق صغيرة إلى متوسطة | مشاريع مفتوحة المصدر متوسطة إلى كبيرة | مشاريع ضخمة جداً (مثل Linux Kernel) |

**الخلاصة:**
> اختيار النمط يعتمد على حجم الفريق وحساسية المشروع لمراجعة الكود — كلما كبر المشروع، زادت طبقات المراجعة قبل دخول أي تعديل للمصدر الرسمي.

### السؤال 1 (medium)

ما الفرق الأساسي بين `git diff` و`git diff --cached`؟

أ) `git diff` يعرض تغييرات فرع آخر، بينما `--cached` يعرض تغييرات الفرع الحالي
ب) `git diff` يعرض التغييرات غير المُضافة (unstaged)، بينما `--cached` يعرض التغييرات المُضافة (staged) الجاهزة للـ commit
ج) لا فرق بينهما، الخياران يعطيان نفس النتيجة دائماً
د) `--cached` يعرض تاريخ commits قديمة فقط

**الإجابة الصحيحة: ب**

**التعليل:**
- ✅ **الخيار ب:** صحيح لأن `git diff` تقارن working directory بالـ staging area (تعديلات لم تُضف بعد)، بينما `--cached` تقارن الـ staging area بآخر commit (تعديلات جاهزة للحفظ)
- ❌ **الخيار أ:** خاطئ — الأمران عن نفس الفرع، الخلاف في المنطقة المقارَنة لا الفرع
- ❌ **الخيار ج:** خاطئ — هذا يخلط بين مفهومي unstaged وstaged اللي هما مختلفان جوهرياً
- ❌ **الخيار د:** خاطئ — يخلط بين `diff --cached` وبين أوامر استكشاف التاريخ زي `git log`

### السؤال 3 (hard)

Which of the following is **NOT** a valid outcome of running `git commit -a`?

أ) It stages and commits modifications to files already tracked by Git
ب) It stages and commits deletions of tracked files
ج) It automatically stages and commits a brand-new, never-tracked file
د) It requires you to write a commit message (unless `-m` is used)

**الإجابة الصحيحة: ج**

**التعليل:**
- ✅ **الخيار ج:** هذا هو الخيار الصحيح كإجابة على سؤال "NOT" — لأن `commit -a` لا يشمل ملفات جديدة كلياً (`untracked`)؛ هذي لازم تُضاف يدوياً بـ `git add` مرة أولى
- ❌ **الخيار أ:** هذا فعلياً صحيح كسلوك لـ `-a` — الخلط هنا مع فكرة إن `-a` "ما تسوي شي على الإطلاق"
- ❌ **الخيار ب:** هذا فعلياً صحيح كسلوك لـ `-a` — حذف ملف متتبَع مسبقاً يُعتبر تعديلاً معروفاً لـ `Git`
- ❌ **الخيار د:** هذا صحيح فعلياً — `commit` بدون `-m` يفتح محرر نص لكتابة الرسالة

### السؤال 4 (medium)

ب) `pull` = `fetch` + `merge` تلقائياً، بينما `fetch` وحدها لا تدمج شيئاً في الفرع الحالي
ج) `fetch` يحذف الفرع المحلي، `pull` يحافظ عليه
د) لا فرق، هما اسمان لنفس الأمر

**الإجابة الصحيحة: ب**

**التعليل:**
- ✅ **الخيار ب:** صحيح تماماً حسب المحاضرة — `pull` تنفذ `fetch` ثم `merge` تلقائياً
- ❌ **الخيار أ:** خاطئ — لا علاقة لعدد الريموتات بالفرق الجوهري بين الأمرين
- ❌ **الخيار ج:** خاطئ — لا أحد الأمرين يحذف أي فرع
- ❌ **الخيار د:** خاطئ — الخلط الشائع بينهما هو تحديداً موضوع هذا السؤال؛ هناك فرق جوهري في الدمج التلقائي

### السؤال 5 (medium)

- ❌ **الخيار ج:** خاطئ — `Git` لا يحوّل الأوامر تلقائياً؛ عليك أنت تختار `-D` يدوياً إذا أردت الحذف القسري

## الجزء الرابع: ورقة المراجعة السريعة (Cheat Sheet)

### 🔑 Git — التعاريف السريعة
| المصطلح | التعريف القصير |
| --- | --- |
| `working directory` | الملفات كما تراها فعلياً على جهازك، قبل أي `add` |
| `staging area (index)` | منطقة وسيطة تجهّز فيها التغييرات قبل الحفظ النهائي |
| `repository` | التاريخ الكامل المحفوظ في مجلد `.git/` |
| `commit` | لقطة دائمة ومحفوظة من حالة المشروع في لحظة معيّنة |
| `branch` | مؤشر متحرك يشير إلى commit، يتقدم مع كل commit جديد عليه |
| `tag` | مرجع ثابت لا يتحرك، يشير لنقطة تاريخية محددة (عادة إصدار) |
| `merge conflict` | تعارض يحدث عند تعديل فرعين لنفس الجزء من نفس الملف |
| `origin` | الاسم الافتراضي للريموت الذي تم عمل `clone` منه |
| `HEAD` | مؤشر يشير لموقعك الحالي في تاريخ المشروع |
| `blessed repository` | النسخة الرسمية المعتمدة للمشروع في أنماط التعاون المتقدمة |

| المعيار | `git fetch` | `git pull` |
| --- | --- | --- |

### 🔑 مقارنة أنماط التعاون الثلاثة

| المعيار | Subversion-Style | Integration Manager | Dictator and Lieutenants |
| --- | --- | --- | --- |

### 🔑 القواعد الذهبية لا تُنسى

| # | القاعدة |
| --- | --- |
| 1 | `Git` يتتبع المحتوى، لا أسماء الملفات |
| 2 | `git commit -a` لا يشمل ملفات جديدة كلياً غير متتبَعة |
| 3 | الدمج يتطلب الانتقال للفرع الهدف أولاً، ثم دمج الفرع المصدر |

| 6 | `.gitignore` يمنع تتبّع ملفات جديدة فقط، لا يزيل ملفات متتبَعة مسبقاً |
| 7 | `tag` مرجع ثابت، `branch` مؤشر متحرك |

### 🔑 الخطوات السريعة (Procedures)

#### إنشاء ودمج فرع جديد
```algorithm
1 | إنشاء والانتقال للفرع | git checkout -b <name> | فرع جديد جاهز للعمل
2 | تعديل وتثبيت التغييرات | git add . / git commit | التغييرات محفوظة على الفرع
3 | الانتقال للفرع الرئيسي | git checkout main | جاهز لاستقبال الدمج
4 | الدمج | git merge <name> | التغييرات مدموجة في main
5 | حذف الفرع (اختياري) | git branch -d <name> | تنظيف الفروع المنتهية
```

#### دورة العمل اليومية الأساسية
```algorithm
1 | فحص الحالة | git status | معرفة الملفات المعدّلة
2 | مراجعة التغييرات | git diff | التأكد من التعديلات قبل الإضافة
3 | إضافة للـ staging | git add <files> | التغييرات جاهزة للحفظ
4 | تثبيت التغييرات | git commit | لقطة جديدة محفوظة في التاريخ
5 | رفع للريموت (إن وجد) | git push origin <branch> | التغييرات مشاركة مع الفريق
```

## الجزء الخامس: بطاقات سؤال وجواب (Q&A Cards)

### البطاقة 1
**Q1:** What is the difference between `git add` and `git commit`?
**A:** `git add` moves changes from the working directory into the staging area, while `git commit` permanently saves whatever is currently in the staging area as a new snapshot in the project's history.

### البطاقة 2
**Q2:** Which command creates a new branch and switches to it in a single step?
**A:** `git checkout -b <branch-name>`.

### البطاقة 3
**Q3:** What is the difference between `git fetch` and `git pull`?
**A:** `git fetch` downloads remote changes without merging them, while `git pull` downloads them and merges automatically (`pull = fetch + merge`).

### البطاقة 4
**Q4:** When do you use `git branch -D` instead of `git branch -d`?
**A:** Only when you're certain you want to force-delete a branch even if it has unmerged changes that will be permanently lost.

### البطاقة 5
**Q5:** What does `git commit -a` NOT do that plain `git add` + `git commit` would require separately for new files?
**A:** It does not stage brand-new, never-tracked files — only modifications and deletions to files Git already tracks.

### البطاقة 6
**Q6:** What is the difference between `git tag` and `git branch`?
**A:** A tag is a fixed reference to a specific point in history (it never moves), while a branch is a moving pointer that advances with every new commit made on it.

### البطاقة 7
**Q7:** Which command shows what will actually be included in the next commit?
**A:** `git diff --cached`, since it compares the staging area against the last commit.

### البطاقة 8
**Q8:** What causes a merge conflict?
**A:** Two branches modifying the exact same part of the same file, so Git cannot automatically decide which version to keep.

### البطاقة 9
**Q9:** What is the purpose of `.gitignore`?
**A:** It lists file and folder patterns (like `*.log` or `node_modules/`) that Git should never track, commonly used for sensitive or auto-generated files.

### البطاقة 10
**Q10:** When would you use `git checkout main` before `git merge experimental`?
**A:** Always — you must be on the target branch (the one receiving the changes) before running `git merge <source-branch>`.

### البطاقة 11
**Q11:** What is the key difference between the Subversion-Style and Integration Manager collaboration workflows?
**A:** In Subversion-Style, all developers push directly to the shared server; in Integration Manager, only the Integrator has direct push access, and other developers request their changes be pulled.

### البطاقة 12
**Q12:** Why is `git reset --hard` considered dangerous?
**A:** Because it permanently discards all working directory and staging area changes made after the target commit, with no easy way to recover them.

### البطاقة 13
**Q13:** What does it mean that Git is a "distributed" version control system?
**A:** Every user who clones a repository gets a full copy of the entire project history, not just the latest files — eliminating any single point of failure.

### البطاقة 14
**Q14:** What role do "Lieutenants" play in the Dictator and Lieutenants workflow?
**A:** Each Lieutenant manages and reviews changes for a specific subsystem before the Dictator pulls their reviewed work into the blessed repository.

### البطاقة 15
**Q15:** What is the difference between `HEAD^` and `HEAD~4`?
**A:** `HEAD^` refers to the immediate parent commit (one step back), while `HEAD~4` refers to the ancestor four steps back along the same line.
